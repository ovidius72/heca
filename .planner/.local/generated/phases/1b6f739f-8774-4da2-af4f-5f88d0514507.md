The library's missing text capability, recorded as an open gap in AGENTS for months and worked around four separate times.

Two small widget capabilities that four call sites have been hand-rolling because the library never had them.

## Why it exists

AGENTS.md records it plainly: *"truncation/ellipsis + wrapping (a long label overflows its box today)"* — in a **prose list of open gaps, never filed as a task**, which is precisely how it stayed open while four hand-written truncations grew around it:

- `heca/src/chrome/mod.rs:1428` `truncate_sidebar_git_branch` (a fixed char cap);
- the command palette's `fit()` (F003/P085/T358).

`heca/src/providers/workspaces/mod.rs:1231` even carries a comment deferring to *"when label truncation/wrapping is settled"*.

## What already exists — nothing new is needed underneath

- `Label::remeasure` sizes itself `chars × font × MONO_ADVANCE_RATIO` wide and `font × MONO_LINE_RATIO` tall, and `paint` draws into `base.bounds`. Fitting to the box is therefore a paint-time cut against the same measure the layout used.
- `Layout::flex_shrink` and `min_size` exist (taffy 0.7), and `style.rs:423` documents `Px(0.0)` as the way to let a node go below its content size — so "may be given less than its natural width" needs no engine change.
- `Item` **already composes**: its label is a real `Label` child (index 1) between two slot `Flex`es, and its own doc says the label "can be swapped or extended without touching `Item::paint`". The second line is another `Label`, never text drawn by `Item`.

## Scope

`Label` gains truncation (End and Start ellipsis) and `Item` gains a description line. **Both stay in `heca-grid-ui`** — a widget is what can be built there, and these can. The four app-side copies are deleted by F011/P089/T376, which is blocked on this.

## Behaviors to preserve

Existing labels are unaffected unless they opt in — a `Label` with no truncation set keeps its current natural size and overflow behaviour, or every layout in the app shifts at once. `Item`'s row height only changes when a description is present. Measure stays the shared `MONO_ADVANCE_RATIO` (a Phase-A approximation until cosmic-text shaping lands — centralising it here is what makes that a one-place fix later).

### ✅ 4845ea12-be54-4cae-9e0c-059252d2b65f — T379 — Label fits its box — .truncate(End | Start), measured once

Status: ✅ `done`

The capability four call sites have been hand-writing.

## What exists

`heca-grid-ui/src/widgets/label.rs`:
- `remeasure()` sets `width = chars × font × MONO_ADVANCE_RATIO`, `height = font × MONO_LINE_RATIO` — the label's **natural** size.
- `paint()` draws `self.text` into `self.base.bounds` with the resolved colour/align/style, then draws decorations over the **run** (`run_rect()`), not the box.
- Builders today: `align`, `color`, `bold`, `italic`, `underline`, `strikethrough`, `font_size`, `font_scale`, `text_signal`.

`heca-grid-ui/src/style.rs`: `Layout::flex_shrink` (`None` ⇒ `0.0`) and `min_size`, with `Px(0.0)` documented at :423 as the way to allow shrinking below content size.

## What to build

`Label::truncate(Ellipsis)` where `Ellipsis` is `End` (labels, descriptions — cut the tail) or `Start` (paths, git branches — keep the tail, cut the head). Two behaviours together, and the second is the one that makes it work:

1. **Layout**: a truncating label declares itself shrinkable — `flex_shrink = 1.0` and `min_size.width = Px(0.0)` — so the engine may hand it less than its natural width. Without this it keeps its full width and simply overflows, and the paint-time cut never triggers. This is the same trap as F003/P067's `flex_grow` lesson: a size that cannot shrink does not participate.
2. **Paint**: fit the text to `bounds.size.w` using the *same* `MONO_ADVANCE_RATIO` cell the measure used, cutting from the end or the start and appending/prepending `…`. Cells `0` ⇒ nothing, `1` ⇒ `…` alone.

`run_rect()` must follow the **drawn** text, or an underline/strikethrough would span the untruncated width.

## Edge cases

- Not truncating (the default) leaves `remeasure`, layout and paint exactly as they are — no existing label may move.
- A signal-driven text that changes still re-measures; the cut is computed at paint from the current bounds, so it follows a resize with no rebuild.
- Multi-byte text: count **chars**, never bytes (`truncate_path_left` already does).

## Test (assert the drawn thing)

Paint into a `Scene` and read the `DrawCommand::Text`: wide box ⇒ the full string; narrow box ⇒ a shorter string ending (or starting) in `…`; `Start` keeps the tail — `…/deep/path` — and `End` keeps the head. A test asserting only a flag is the F004 lesson repeated (a `grow` flag once passed while the layout was visibly broken); assert the text and the run rect.

### ✅ 5408f2d8-b2fa-47dd-867e-e4d5cbf1964d — T382 — Label wraps — height from width, the other half of the gap

Status: ✅ `done`

The second half of AGENTS.md's open gap (*"truncation/ellipsis **+ wrapping**"*). `Label::truncate` (T379) closed the first half; this is the harder one.

## Why it is harder than truncation

Truncation is a **paint-time** cut against the box the engine already gave the label — the measure never changes. Wrapping changes the measure itself: a wrapped label's **height depends on its resolved width**, which a fixed `Length::Px` measure cannot express.

`heca-grid-ui/src/widgets/label.rs::remeasure` today sets:

```
width  = chars × font × MONO_ADVANCE_RATIO      // one line, natural width
height = font × MONO_LINE_RATIO                 // exactly one line
```

Taffy (0.7, `heca-grid-ui/src/layout.rs`) supports content-driven sizing through a **measure function** on leaf nodes — that path is what this task has to reach; the engine does not use it for labels today. Check whether `LayoutEngine` already wires one for any widget before adding a second mechanism.

## What to build

`Label::wrap(bool)` (or `Wrap::{None, Word}`) — mutually exclusive with `truncate`, since a label either cuts or reflows:
- break on **word** boundaries, falling back to a hard break for a word longer than the line;
- height = `lines × font × MONO_LINE_RATIO`, computed from the width the engine offers;
- the run rect / decorations follow the **last** line, or span each line, whichever the existing `run_rect` contract can honour — decide and document it.

## The consumer that asked for it (2026-07-30)

The command palette wraps **the selected row's description only**, and the list **reflows** — rows below shift down as the cursor moves, CSS-style, which the maintainer chose explicitly over a fixed two-line allowance. So the palette needs per-row heights that change with selection; row geometry there is already per-row (`row_rects`), so the reflow follows from the label's height being honest.

## Behaviors to preserve

A label that sets neither `wrap` nor `truncate` keeps today's single-line measure exactly — every existing layout in the app depends on it. Wrapping must not silently change the natural width either: a wrapped label still asks for its full width and only *accepts* less.

## Test

Assert the drawn lines, not a flag: the same text in a wide box paints one text run, in a narrow box paints N runs at increasing y, and the label's measured height is N line-heights. A long unbreakable word still fits (hard break) rather than overflowing.

### ✅ 7dae47ea-461b-49be-b1ad-517005312d80 — T383 — The palette keeps a margin below it — the vertical counterpart of PANEL_VIEWPORT_FRAC

Status: ✅ `done`

🔴 Reported in the app on 2026-07-30, right after the height fix (`7475a81`): **the palette panel touches the very bottom of the window.**

## Why

`heca-grid-ui/src/widgets/command_palette.rs:325` — `visible_rows` fills the list down to

```rust
let mut room = (vp.h * (1.0 - TOP_FRAC) - chrome).max(0.0);
```

and `layout()` (:445) places the panel at `py = vh * TOP_FRAC` (:486) with `panel_h = PAD + query_h + PAD + list_h + PAD` (:479). `chrome` is exactly that non-list part, so the bound resolves to

    panel_bottom ≤ vh * TOP_FRAC + vh * (1 - TOP_FRAC) = vh

— the window's bottom edge, to the pixel. Nothing reserves room **below** the panel, so on a short window the last row sits flush against the screen edge.

The horizontal axis already has this: `PANEL_VIEWPORT_FRAC = 0.92` (:97) caps the panel at 92% of the window width, leaving 4% clear on each side. The vertical axis has no equivalent — `TOP_FRAC` (:99) is an offset, not a margin, and it only guards the top.

## What to build

A `BOTTOM_FRAC` constant beside `TOP_FRAC`, documented as the vertical counterpart of the side gap `PANEL_VIEWPORT_FRAC` leaves: `(1.0 - 0.92) / 2.0 = 0.04` of the viewport, so the gap under the panel matches the gap beside it as a fraction of its own axis. Subtract it in `visible_rows`:

```rust
let mut room = (vp.h * (1.0 - TOP_FRAC - BOTTOM_FRAC) - chrome).max(0.0);
```

One place only — `layout()` derives `panel_h` from the rows `visible_rows` admitted, so the panel shrinks with it and no second clamp is needed.

## Edge cases

- **The gap is quantised by the row height.** A row is two lines (described list) or taller (stacked bindings), so dropping one row can leave far more than 4% clear. That is the floor being a floor, not a target — do not try to distribute the remainder.
- **The one-row floor still wins** (:344): a window too short for even a single row keeps showing one clipped row rather than an empty panel, and that row may still reach past the margin. Keep that behaviour and keep the test viewports above it.
- **Non-finite viewport** (:328) returns early, before any of this — unchanged.

## Test

Extend `the_palette_never_runs_off_a_short_window` (`heca-grid-ui/tests/phase_a.rs:3701`). It asserts `bottom <= viewport.h + 0.5` today, which the flush panel passes — that is why the bug shipped. Assert a **gap**: `bottom <= viewport.h * (1.0 - 0.04) + 0.5`, at the three viewports it already sweeps (1280x900, 1280x480, 900x320), with the failure message reporting the measured gap.

Visual verification is the user's — a test can prove the number, not that it looks like breathing room.

### ✅ e29d2d8a-6616-4423-82a1-38a9dfb90446 — T387 — Label marks matched characters — the last thing about text the palette hand-draws

Status: ✅ `done`

The prerequisite for the palette's rows becoming composed widgets. Without it a composed `Label` cannot show a fuzzy match, and the palette has to keep painting its own text.

## What the palette does today

`heca-grid-ui/src/widgets/command_palette.rs:688-714` — it draws the row's label, then **over-draws each matched character in the accent colour**, positioning each by index against the monospace cell:

```
// Label, then over-draw matched chars in accent.
for &hi in &m.hits { … }
```

`Match.hits` (`:90`) is the list of matched char indices the fuzzy matcher returns. This is the third capability the palette hand-rolled because `Label` lacked it — truncation was the first (T379), wrapping the second (T382).

## What to build

`Label::marks(Vec<usize>)` + `Label::mark_color(Color)` (or one `marks(indices, color)` — pick one and say why): the listed **character indices** are drawn in the mark colour, the rest in the label's resolved colour.

Generic on purpose: any search surface highlights matches, and the indices come from `search::fuzzy` (P092/T384), which returns them for exactly this. Nothing here knows what a command is.

## Where it interacts

- **Truncation** (`drawn_text`, `:124`): the drawn string is a *cut* of the original, so an index into the original text is not an index into the drawn one. `Ellipsis::End` keeps a prefix (indices survive, past the cut are dropped); `Ellipsis::Start` drops `len - n + 1` from the head (every surviving index shifts). Get this wrong and the highlight lands on the wrong letters — visible, and exactly the kind of thing a test must assert on the drawn output.
- **Wrapping** (T382, `drawn_lines`): an index must be mapped to (line, column). `wrap_lines` collapses runs of whitespace, so the mapping cannot be recovered by counting characters in the output — either return the source offsets from the wrap, or mark before wrapping. Decide and document.
- **Decorations** (`run_rects`): unaffected — a mark is a colour, not a rect.

## Edge cases

- An index past the end of the text is ignored, not a panic — the caller's indices and the label's text can disagree by a frame when a signal updates.
- Multi-byte text: indices are **chars**, never bytes, like every other measure in this widget.
- No marks ⇒ one text run exactly as today. This must not split the draw into per-character runs for ordinary labels.

## Test

Paint and read the `DrawCommand::Text` runs: the marked characters come out in the mark colour and the rest in the label colour, with the concatenation still equal to the drawn text. With `truncate(Start)` the marks follow the characters they were attached to, not their original positions. Unmarked labels still paint exactly one run.

2. **Measured heights replace the arithmetic.** `row_h`/`row_lines` go away; a row's height is what the engine measured, captured in `on_layout` as Select does. This is what makes the reflow work — a wrapping description reports its own height and the rows below shift with no palette code for it.
3. **`place_rows`** mirroring `place_options`: visible rows shifted to absolute targets inside the panel rect, off-window rows collapsed to zero.
4. `visible_rows` and `layout` read measured heights. **Keep `BOTTOM_FRAC`** (T383) — a property of the panel, not of the rows.

## Behaviours to preserve

- The query line stays the hand-driven `Input` — a separate seam, not in scope.
- Panel placement, `panel_metrics` size variants (`:124`) and the bottom margin unchanged.
- Hit-testing: paint, hover-select and the click hit-test all read one `row_rects` today, which is what keeps a row from being drawn in one place and clicked in another. With real children the **bounds are** that single source — do not add a second geometry path beside them.
- Rows outside the visible window must not be clickable (Select's zero-collapse).
- A description-less list stays one line per row.
- Filtering still matches the label only, and the arity/`offerable` rule lives in the host.

## Edge cases

- The palette is rebuilt on every open (`heca/src/chrome/palette.rs:185`), so children are built once per open — but **the row count changes as the query filters**, which `Select` never faces. Hide and re-place rather than rebuilding a hundred widgets per keystroke.
- Different row heights mean the running sum must come from measured heights, not one height times an index.
- First frame: Select notes its measured heights come from the previous layout pass (`:532`) and falls back to a font-derived height. The palette opens and paints immediately, so it needs the same fallback or the first frame is wrong.

## Test

- Drawn output unchanged for a list without descriptions: same rows, same texts, same geometry as before the refactor.
- Selecting a row whose description wraps moves the rows below it (assert their painted y) and grows the panel — the reflow, measured.
- A click at a row's painted rect runs that row's command; a click where a collapsed off-window row used to be runs nothing.
- Marks still land on the matched characters, now via `Label::marks`.
