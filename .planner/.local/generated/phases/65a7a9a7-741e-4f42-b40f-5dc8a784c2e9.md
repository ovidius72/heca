# 65a7a9a7-741e-4f42-b40f-5dc8a784c2e9 — P088 — The dock row — the shape a second dock and every plugin needs

**Status:** 📋 `planned`
**Created:** 2026-07-30T13:27:40.358Z
**Updated:** 2026-07-30T13:38:14.127Z

Extract pane_card / column_view out of the workspaces provider into named row components, and make the workspaces dock the first consumer.

The row that only one file can build today, made a thing with a name — **before** F003/P085/T359 puts a second container on screen and it gets copied instead.

## What exists

`heca/src/providers/workspaces/mod.rs`:
- `pane_card()` :728 — the dock's pane row, **eleven parameters** (entry, mount, programs, theme, emit, active pane, container state, signals, drag, hints). It registers a drag source **and** drop target (`drag.register(ChromeDragItem::Pane(..))`), a hint target, a `nav_key`, an active marker driven by a signal, the info segments and the badges.
- `column_view()` :1008 — the column row: the same shape written separately, with a `MarkerGroup` grip as its drag source.
- `build_workspaces_container()` :1084 and `build_body()` :624 assemble them.

Nothing of this is reachable from outside that file. A Docker dock — the phase's own worked example — cannot draw a row that looks or behaves like heca's.

## What to build

Row components in `heca/src/components/`, taking plain data + the seams (`Intent`, emitter, `&mut BuildCx`) — **not** `&AppState`, not the workspaces model. The row must be able to say:
- what it shows (leading glyph, label, trailing badges/segments),
- what it *is* for navigation (`nav_key`), for selection (the active/cursor signal, per mount), for drag (a payload the registry keys), and for the context menu (`ContextTarget::Row { container, key }`),
- what a press means (a named `Intent`, per item kind — never inherited between kinds; see the settled rule in F003/P085/P086).

The workspaces provider becomes its **first consumer** in the same task: `pane_card` and `column_view` are deleted, not left beside the new component.

## Watch for

- `ChromeDragItem` is a closed `Pane | Column | Workspace` (`heca/src/chrome/contribution.rs` records this as workspace-shaped) — a generic row cannot key its drag payload through it as-is. F003/P085/T360 (`58SE7`) is the open row about keying registries by `(mount, nav_key)` the way `row_nav` already is. Land that first or the component will be workspaces-shaped by construction.
- `Row` and `Item` **activate on mouse-down and report the press handled** — any press-consuming row fights drag detection (the whole of F003/P086/T368). Check the press order in `heca/src/mouse.rs` before changing a row's press behaviour.
- Per-mount cursors mirror across seatings of one component (`mirror_cursor_to_siblings`, `heca/src/providers/actions.rs:115`) — the row reads its state per `(mount, nav_key)`, never a global.

## Behaviors to preserve

Pixel-identical rows; drag and drop unchanged (source **and** target); hint ids monotonic; the active outline still driven by a signal rather than a rebuild.
