STUB. A top-bar Menu/menubar is a separate activity, similar to the contextual menu. Not scoped yet — recorded so the shared infrastructure built for context-menu is made reusable, not forked.

Top/Bottom Bar Widget System + mainmenu — vision registered under Pluggable Chrome (where it is born: reuses open_dropdown, Contribution, OverlayHost). To be split into separate phases in a later review; for now this single stub phase holds the whole vision.

VISION (2026-07-09):
A. Bar containers: TopBar and BottomBar become generic, pluggable widget containers — specular in functioning, each with independent widgets (like the VSCode bottom bar: icons, buttons, text, often from plugins). Today the TopBar hosts only 2 sidebar-toggle buttons and is misnamed "tab bar". Flesh out the placeholder Contribution::ToolbarGroup / Contribution::StatusSegment (chrome/contribution.rs) with real build hooks like ContainerContribution::build, OR introduce a generic Contribution::BarWidget { region: Top|Bottom, build: Fn(&ChromeCtx)->WidgetModel, weight }. Each bar hosts an ordered list of widgets.

B. mainmenu widget (rename from "menubar"): the application menu, a built-in widget mounted in the TopBar. Minimal now — e.g. a "Close" entry that confirms via the central gate, following the standard action architecture (ActionRegistry + KeyBindingRegistry + RPC, like every WmAction). Future: conventional File/Edit/View/... top-level groups. Reuses (do NOT fork) context-menu infra: open_dropdown/DropdownSpec, entries-as-intents, ActionCatalog icon/label/tooltip, menu-nav (extended with left/right to move between top-level menus). Plugin entry contribution is Contribution::MainMenu, sibling of Contribution::ContextMenu (reuse the context-menu-5 dotted-context + weight Vec<i64> Dewey merge design).

C. Plugin bar-widget contribution: plugins add buttons/widgets to top/bottom bars that execute EXISTING actions (icon+label from ActionCatalog). Plugins/developers must have an easy path to register new actions into ActionRegistry + KeyBindingRegistry from code (relates to plugin-04 dynamic action registry).

D. Topbar enrichment: built-in widgets for operations on the current pane/column/workspace (action buttons).

Config-driven widget add/remove: users add/remove bar widgets from config.toml by listing widget kinds in order, analogous to [appearance.pane] title_actions = ["split","close"] (Vec<PaneAction> enum, [] hides). E.g. [appearance.bar] top_widgets = [...].

Token/placeholder integration (plugin-06): tmux-style tokens (#{pane}, #{fg:...}) let users build small widgets or alter labels, like tmux statusline replacement.

PHASE SPLIT DEFERRED: this stub holds the vision; A/B/C/D + config surface + token integration will be split into separate phases when the work becomes active.
