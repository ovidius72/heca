User-reported 2026-06-23: with the global border set to 0, toasts/modals/bracketed panes still show a hairline, and raising it adds no border to a plain Pane.

Rescued from PLAN.md 2026-07-26 before that file was deleted. Reported by the user 2026-06-23,
analysed then, never tracked. The analysis below is theirs and the line numbers are from that date —
re-verify before building.

═══ WHAT THE USER SAW ═══
- With the global BORDER set to **0**: notifications (`Toast`), `Modal`, and `Bracketed` panes
  **still show a hairline border**, and the showcase demo panes keep a 2px border.
- Raising BORDER **adds no border** to the default `DASHBOARD` `Pane`.

═══ WHY — THREE BORDER PATHS THAT DISAGREE ═══
1. **`theme.border_width`-driven** — `Button`, `Input`, `Select`, `Checkbox`, `Tag`, `Card`.
   `PaintCx::border()` (component.rs, ~line 567 as of 2026-06-23) returns `None` at width 0.
   **This one is already correct: 0 means none.**
2. **`PaintCx::bracket_frame`** — used by `Toast` (toast.rs ~332), `Modal` (modal.rs ~257) and
   `Pane::Bracketed` (pane.rs ~143). At `border_width == 0` it deliberately falls back to a solid
   hairline (`BRACKET_HAIRLINE_WIDTH` / `BRACKET_HAIRLINE_ALPHA`) so the container "stays framed".
   **That fallback is why Toast/Modal/Bracketed keep a border at 0.**
3. **Hardcoded literals in the showcase** — `heca-renderer/examples/showcase.rs` (~762, 771, 793,
   819): `.border(theme.accent, 2.0)`. Ignores the global control entirely.

Plus: a `Bordered` `Pane` draws `style.visual.border`, which comes from an explicit
`.border(color, width)` call. A pane that never called it (the DASHBOARD pane, showcase.rs ~635)
shows no border whatever the global setting says.

NOTE 2026-07-26: border now lives at `style.visual.border` after the Layout/Visual split
(F003/P017/T1, commit 8718718). Re-check the line numbers above against current code.

═══ THE PROPOSED MODEL (designed 2026-06-23, NOT built — the user chose "plan, don't code") ═══
- `theme.border_width` becomes the ONE global control.
- **`border_width == 0` means no border anywhere.** That means dropping the `bracket_frame`
  hairline fallback AND updating the test that currently asserts it:
  `bracket_frame_zero_border_is_a_uniform_hairline_not_broken_corners` in
  `heca-grid-ui/tests/phase_a.rs`.
- A container's border **width always comes from `theme.border_width`**; a widget picks only the
  colour. A `Bordered` pane with no explicit colour uses the theme border colour.
- The showcase reads `theme.border_width` instead of the literal `2.0`.

═══ THE OPEN DECISION — SETTLE WITH THE USER BEFORE BUILDING ═══
Does an explicit `.border(color, width)` still override the global width, or is width **always**
theme-driven? Both are defensible and the answer changes the widget API.
This ties into the planned config options (memory `border-style-config-options`:
`sidebar_border_style` / `pane_border_style`).
