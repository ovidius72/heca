### 📋 a21e7e5e-a8f4-482a-90d9-8ca55003cb6c — T381 — A declined action says so — the producer for "nothing happened, and here is why"

Status: 📋 `planned`

An action that runs but **declines** currently vanishes. From a keypress that is tolerable; from the command palette, where the user deliberately picked the entry out of a list, it reads as a broken command.

## The report that produced this task (2026-07-30)

The maintainer chose **Move Column Up** in the palette and nothing happened. The action is not dead: `handle_move_column_up` (`heca/src/handlers.rs:356`) moves the active column **to the workspace above** and returns early when `current_ws == 0`; `handle_move_column_down` :370 does the same at the last workspace. Correct behaviour, invisible outcome.

It is not one action. The same silent early return is everywhere a precondition can fail:
- no workspace above/below (`move_column_up` / `move_column_down`, `move_pane_*`),
- nothing under the cursor (a component's `perform` returns `Handled::No` — `heca/src/providers/mod.rs` documents "a silent decline is a real answer, not an error"),
- no link under the caret (`open_link_at_caret`), no selection (`copy_selection`), no scrollback to page through,
- a component action whose owner is not mounted (`IntentOutcome::NotRunnable`), one the domain refuses (`IntentOutcome::Blocked`), and one called without its required arguments (`IntentOutcome::MissingArgs`, added F003/P085/T358) — those three are already **named outcomes** on the dispatch path and today only reach a `#[cfg(debug_assertions)] eprintln!`.

## What to build here

A notification producer on the dispatch path: when an intent resolves to `Blocked`, `NotRunnable` or `MissingArgs`, or a handler declines, raise a low-severity notification saying which action and why. `dispatch_view_intent` (`heca/src/app/interaction.rs`) already computes exactly those outcomes and throws them away for every caller but RPC — that is the seam, and it needs no new plumbing.

The gap to close is the **handler** case: an early `return` inside `handle_move_column_up` is invisible to the dispatcher. Either handlers gain a way to report a decline (a return value, or a `cx`-style sink), or the well-known preconditions are checked before dispatch. That choice is this task's real content — do not paper over it by special-casing the two column actions.

## The related, deliberately separate question

**Prevention, not just reporting**: an optional `can_perform(&self, id) -> bool` would let the palette render an entry *disabled* rather than let it be chosen and then decline. `DropdownItem` already carries an `enabled` flag, so the menu half exists. That was deferred in F003/P085/T358 ("Do not build it now") and belongs with the palette work, not here — this task is about telling the user what happened, not about greying entries out.

## Behaviors to preserve

A decline is **not an error** and must not read as one: severity low, no modal, no sound. Silence stays correct for a keypress that repeats (holding `j` at the end of a list must not spray toasts) — rate-limit or suppress repeats of the same action, which is the store's job (`notification-02`), not a special case here.

- [ ] low severity, no modal; repeats of the same action suppressed (key-hold must not spray)
