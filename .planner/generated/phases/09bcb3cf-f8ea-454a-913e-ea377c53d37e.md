### 📋 4280790f-e55b-48cc-b4c1-1a7a5d1773b0 — T071 — Plugin action registration API

Status: 📋 `planned`

Registrazione action IDs e dispatch per plugin WASM.

## LA SEAM È GIÀ PRONTA (costruita in plugin-04/T3 + action-task-C, 2026-07-15)
Non serve inventare il modello di registrazione azioni: esiste già e aspetta solo l'adapter WASM. Costruire QUI sopra queste basi, NON un secondo registry.

- **`ActionRegistry` + `ActionCatalog`** (`heca/src/actions.rs`): registry unico runtime. Un'azione name-keyed (senza variante `WmAction`) si registra con `register_dynamic(registry, catalog, meta, handler)`.
- **`Dispatch::Declarative`** (già esiste): `register_dynamic(..., handler: None)` registra un'azione DICHIARATA — ha id/metadata/policy, appare in menu e introspection, ma l'host NON la esegue. È ESATTAMENTE il caso WASM: il plugin possiede l'esecuzione oltre il confine. `dispatch_view_intent` (`heca/src/app/interaction.rs`) già gestisce il no-op con warning quando un `Declarative` viene dispatchato host-side.
- **`ActionMeta`** (`heca/src/actions.rs`) è tutto dati serializzabili TRANNE il `confirm.Callback` (closure nativa): `name/label/description/category/default_binding/icon/policy` + `confirm: Option<ConfirmSpec>`. Un plugin WASM dichiara la sua azione + confirm come DATI serializzati; gli `Outcome` sono limitati a `Proceed/Cancel/Dispatch` (NIENTE `Callback` — non attraversa il confine, per costruzione). Vedi §5.6/§6 nella descrizione della fase `action-interaction` (3e04a8f5).
- **`policy: ActionPolicy` è OBBLIGATORIA** sull'`ActionMeta` (decisione G1): il plugin la DICHIARA come dato; l'host la onora (G2 — la fiducia diventa reale qui, al confine WASM sandboxed).
- **Introspection già pronta**: `ActionCatalog::describe_all()/describe(name)` → `ActionInfo` (serde). Un `Callback` outcome NON viene mai serializzato (reso opaco). L'adapter WASM può riusare questo per far scoprire al plugin le azioni esistenti.
- **RAII unregister**: `unregister_dynamic(registry, catalog, id)` ritira handler + meta. `register_dynamic` restituisce un `ActionHandle`; l'aggancio a `ProviderHandles` (drop → unregister) è la decisione G5, ANCORA DA FARE (plugin-05, vedi sotto).

## LAVORO DI QUESTA TASK (l'adapter WASM)
1. Host adapter first-party: riceve dal plugin WASM `{ action_id, metadata serializzata (ActionMeta senza Callback), confirm serializzato }` e chiama `register_dynamic(..., handler: None)` → `Dispatch::Declarative`.
2. Marshalling del dispatch: quando un `Declarative` di quel plugin viene invocato (da keybinding/menu/RPC via la porta unica `dispatch_view_intent`), inoltrare `Intent { action_id, args }` al plugin oltre il confine WASM invece del no-op attuale.
3. Marshalling del `ConfirmSpec` serializzato (outcomes `Proceed/Cancel/Dispatch` soltanto).
4. Test: un'azione dichiarata da un finto plugin appare nel catalogo/introspection, e il suo dispatch raggiunge il plugin.

## DIPENDENZA
`ProviderHandles` (heca/src/providers/mod.rs) deve tenere l'`ActionHandle` e chiamare `unregister_dynamic` al drop (G5). Oggi tiene solo le `subscriptions`. Quel gancio è previsto in plugin-05; se non è ancora fatto quando si arriva qui, farlo prima (o qui).

### 📋 be8f26e6-b572-4e5f-a851-15d6fa82f3e4 — T083 — Design WASM host API facade

Status: 📋 `planned`

API host esposta ai plugin WASM.

═══ SETTLE THIS BEFORE DESIGNING THE FACADE (cross-reference added 2026-07-25) ═══
Full write-up: F003/P017/T9 (deferred there on purpose — this is where it gets decided).

For a plugin author to get ANY editor completion, the builder types must live somewhere their crate
can depend on. Today they cannot:
- The declarative model — `ViewNode`, `WidgetKind`, `PropValue`, `Intent` — lives INSIDE THE APP at
  heca/src/chrome/view.rs. A plugin is a separate program and cannot depend on the app.
- The workspace has six members and none is a plugin kit: heca-core, heca-renderer, heca-config,
  heca-grid-ui, heca, heca-theme (Cargo.toml:2). docs/chrome-and-ui.md never names one
  either.
- F003/P011/T006 (typed builder SDK) says "the WASM SDK re-exports it". With the model in the app
  crate, that sentence cannot currently be true of anything.

This IS the phase that has to answer it, because the host API facade is exactly the boundary in
question. Do not design the facade around types a plugin cannot import.

NOT the forbidden thing: AGENTS.md:744 rejects `heca-grid-ui` owning `ViewNode` (it inverts the
crate graph, and `ViewNode` cannot carry the closures/signals native chrome needs). A separate small
crate ALONGSIDE, depended on by both the app and plugins, inverts nothing — a different question,
and the user's to decide. Do not treat the settled rule as having already answered it, and do not
treat this note as permission.

Also in scope for the same decision: a plugin written in JavaScript or Python gets no Rust
completion regardless. The widget vocabulary is a CLOSED list with a coverage guard already walking
it (`WidgetKind::ALL`), so matching definitions for other languages could be generated from it —
uncosted. Check whether F003/P017/T3's generated property tables are reusable for that rather than
private to the app.

### 📋 f1f49b8b-9874-46dc-a097-75787222c520 — T316 — Generate plugin-facing type definitions (.d.ts / JSON Schema) from the widget vocabulary

Status: 📋 `planned`

User's proposal, 2026-07-25: a script that emits a `.d.ts` so plugin authors working in TypeScript
get real types instead of hand-writing untyped JSON.

═══ WHY IT FITS ═══
A `ViewNode` is data with a tag on it, which is what TypeScript's discriminated unions are for. One
generated file gives per-widget checking with no builder objects at all:

    export type PropValue = boolean | number | string;
    export type Intent = { action: string; args?: Record<string, PropValue> };

    export type ViewNode =
      | { kind: "column"; props?: { gap?: number; padding?: number; align?: Align };
          children?: ViewNode[] }
      | { kind: "input";  props?: { text?: string; placeholder?: string; name?: string };
          events?: { change?: Intent } }
      | { kind: "scroll"; props?: { axes?: "vertical" | "horizontal" | "both" };
          children?: ViewNode[] }
      | { kind: "button"; props?: { text?: string; variant?: Variant };
          events?: { press?: Intent }; children?: ViewNode[] }
      // …all 30 kinds

An author then writes plain objects and is still caught:
    { kind: "label", props: { placeholder: "…" } }
    // Object literal may only specify known properties — 'placeholder' does not exist on
    // type '{ text?: string; bold?: boolean; ... }'
Same guarantee as the Rust builders, and events are typed too — `press` exists only on widgets that
can be pressed.

═══ HARD CONDITION — GENERATED FROM THE ONE SOURCE, AND GUARDED ═══
A hand-written `.d.ts` would be a FOURTH place to forget a property, which is the exact defect
F003/P017 exists to remove, restated in another language. It must be generated from the same
property table that F003/P017/T3 produces, and it needs the same style of guard: regenerate during
the build and FAIL if the checked-in file differs from what the source produces. Without that it is
stale the first time someone adds a widget.
⇒ PREREQUISITE: F003/P017/T3 (generated translation + drift test). Before that table exists there is
nothing to generate from. Check there that T3's tables are reusable outside the app rather than
private to it — that check is already noted in F003/P017/T9.
The existing `WidgetKind::ALL` coverage guard (heca/src/chrome/view.rs:78) already guarantees the
kind list is complete, so the generator can trust it.

═══ THE REAL BLOCKER: WHAT IS A PLUGIN, TECHNICALLY? ═══
TypeScript does NOT compile to WebAssembly. A TS plugin needs either a JavaScript engine running
inside WASM, or a different plugin model where the plugin is a separate process. Nobody has decided
which. Until that is settled we would be generating types for a plugin that cannot run.
This is the SAME underlying question as T1's (where the plugin-facing types live) and
F003/P017/T9's. Answer "what is a plugin" once, and the artifact choice falls out of it.
DO NOT start this task before that decision.

═══ WHICH ARTIFACT — DECIDE WITH THE USER, DO NOT ASSUME ═══
- `.d.ts` — for TypeScript plugin authors. Blocked on the question above.
- JSON Schema — the cheaper cousin, generated from the same table. Serves TOML/JSON tooling and any
  schema-aware editor TODAY, and is the better fit for F003/P009 (plugin-07: simple config.toml
  plugins), which are TOML and would otherwise get no help at all.
- Both, from one generator with two emitters.
Recommendation to put to the user: JSON Schema first (it has a consumer that exists), `.d.ts` when
the plugin model is settled.

═══ STATE OF THE CONSUMERS (verified 2026-07-25) ═══
- No schema/type export exists anywhere: no `schemars`, no `JsonSchema`, no `.d.ts`, no typescript
  reference in heca, heca-grid-ui or heca-config.
- `heca/src/rpc.rs` is rich — it takes action names and returns JSON, and `describe-action` already
  returns structured `ActionInfo`. But NOTHING in it accepts a description tree, so there is no
  external caller for these types yet. If an RPC command that accepts a `ViewNode` is ever added,
  that becomes an immediate consumer and this task gets much more valuable.

═══ ACCEPTANCE (once unblocked) ═══
- Type definitions are generated from the same table as the Rust side; no hand-maintained list.
- A build-time check fails when the checked-in output does not match a fresh generation.
- Every one of the 30 kinds appears, with its properties AND its events, per-kind — a property on
  the wrong widget must be a type error, not silently accepted.
- Enum-valued properties emit as string unions (e.g. "vertical" | "horizontal" | "both"), matching
  how they travel in the model.
- Documented for authors wherever the plugin authoring guide ends up after F003/P017/T8.
