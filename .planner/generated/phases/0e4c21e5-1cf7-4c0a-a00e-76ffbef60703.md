# 0e4c21e5-1cf7-4c0a-a00e-76ffbef60703 — P084 — gridui-10: A widget cannot drop a child's event — framework-owned routing + a self-contained ScrollRegion

**Status:** 🚧 `in-progress`
**Created:** 2026-07-26T16:49:11.138Z
**Updated:** 2026-08-07T17:29:15.224Z

The framework walks children, not the widget; ScrollRegion owns its whole gesture and reports position through scroll_start/scroll/scroll_end

## The defect, stated once

A `ScrollRegion` mounted in a new surface arrives dead, and nothing fails. It lays out, paints and
hit-tests perfectly; the wheel does nothing and a thumb drag never ends, so the thumb stays welded
to the cursor. The user has reported this three times, in three surfaces, and each time it was
fixed in that one surface.

It is not a bug in the widget. `ScrollRegion` (heca-grid-ui/src/widgets/scroll_region.rs) already
implements the wheel, the thumb drag, the click-in-track page and the press-and-hold repeat, and has
for months. The failure is that it is never handed the events:

- `Event::Scroll` never arrives  => the wheel does nothing.
- `Event::PointerReleased` never arrives => `thumb_grab` is never cleared => the drag never ends.

Two independent causes, each an omission rather than a mistake:

1. **The host picks a subset.** As of 2026-07-26 `heca/src/app/events.rs` delivered `PointerMoved`
   + `PointerPressed` to an open modal layer and nothing else; `WindowEvent::MouseWheel` had no
   modal branch at all; `chrome_dispatch_*` (heca/src/chrome/mod.rs:3108, :3123) has no wheel;
   `dispatch_pane_header_*` (heca/src/chrome/mod.rs:1193, :1214) has no release. Every seam picked a
   DIFFERENT subset.
2. **Each container picks a subset.** `Component::event`'s contract is "if you override it, you own
   routing to your children". 24 widgets override it. `Dialog::event`
   (heca-grid-ui/src/widgets/dialog.rs:347) carries hand-written arms for `PointerReleased` and
   `Scroll` whose comments describe exactly these two symptoms — the fix was already written there,
   which is why it was invisible everywhere else.

## The decision (with the user, 2026-07-26)

**The framework routes to children; a widget only declares what IT does.** Forwarding stops being a
line anyone writes, so it stops being a line anyone can forget. `Component` loses `fn event` and
gains `on_event_capture` (before children) + `on_event` (after children), with one free function
`dispatch(node, ev)` performing the only child walk in the library.

Widgets whose routing genuinely is not a child walk — `Select` (option rows are placed children that
must not see input while the list is closed) and `Dialog` (routes through an overlay-aware
`FocusManager` scan) — keep their current code and declare `routes_own_subtree() -> true` with the
reason. That is an exception, not a loophole: the pointer-delivery conformance test applies to them
and fails if they drop a kind.

**`ScrollRegion` is not an exception** — it maps onto the two hooks exactly: capture takes the
press/thumb-grab and the hover gate (the thumb must beat any child under the cursor), bubble takes
the wheel and the release (children first, so the innermost hovered region wins and nesting works
for free). The nested-region rule that used to be a comment about calling `route_event` first
becomes simply which hook the code sits in.

**Position is reported, never implemented by the caller.** `on_scroll_start` / `on_scroll` /
`on_scroll_end` carry full browser-shaped metrics (offset_x/offset_y, max_x/max_y, content,
viewport) plus `Option<&Event>` — `None` means the host's own `scroll_to` moved it, which is what
lets a scroll-into-view call avoid fighting the user's wheel. A wheel gesture has no natural end, so
`on_scroll_end` needs an idle timer in `tick`, the same way browsers implement `scrollend`.

## Edge cases that will bite

- **Order flips.** Today most overriding widgets handle first and never route; `Component::event`'s
  default routed to children and did nothing else. Under `dispatch`, own-handling runs AFTER
  children unless it is in capture. A widget that consumed a press before its children now needs
  capture, or its children start stealing clicks.
- **Gates become consumes.** `ScrollRegion` only forwards a press to children *when hovered*. With
  automatic routing that gate must be expressed as capture consuming the press, and the new failure
  mode is over-consuming — equally silent. Test both directions.
- `Tooltip` is transparent to events and must stay so (it only adds paint).
- Focus-barrier widgets (`Button`, `Item`, `Choice`) are one click target and one Tab stop; children
  must not become independently clickable.
- `Handled::No` from `on_event_capture` must not be confused with "not interested" — the walk
  continues either way.

### ✅ d3be3b18-5bb2-4670-8468-adbb118988a9 — T342 — ScrollRegion reports its position — scroll_start / scroll / scroll_end, with full metrics

Status: ✅ `done`

Nobody using a scroll area implements scrolling. This is the other half of that promise: watching it
must not require implementing it either.

## Decided with the user (2026-07-26)

Three callbacks, all optional. A host that just wants a working scroll area attaches none.

```rust
pub struct ScrollInfo<'a> {
    pub offset_x: f32, pub offset_y: f32,   // scrollLeft / scrollTop
    pub max_x: f32,    pub max_y: f32,      // furthest it can travel
    pub content: Size,                       // scrollWidth / scrollHeight
    pub viewport: Size,                      // clientWidth / clientHeight
    pub event: Option<&'a Event>,            // the wheel/press that moved it; None = host's scroll_to
}
```

Borrowed, so no clone on a path that fires at frame rate. The user rejected a synthesized
`ScrollSource` enum in favour of carrying the real event: `event.is_none()` is exactly "this was my
own `scroll_to`", which is what keeps a scroll-into-view call from fighting the user's wheel.

## Current state

- Half-written and uncommitted (2026-07-26): `ScrollInfo` + a `ScrollSource` enum, an `on_scroll`
  field/builder, and `set_offset_y` / `set_offset_x` chokepoints that every path now funnels through
  (wheel scroll_region.rs, thumb drag, `page_toward`, `ensure_visible`, the public `scroll_to*`).
  **The enum must be replaced by `Option<&Event>` per the decision above.**
- `scroll_by` gained a source parameter; revisit as the event is threaded instead.

## Build

1. Replace `ScrollSource` with `event: Option<&Event>` on `ScrollInfo`; thread the `&Event` from the
   handling site into the chokepoint. `scroll_to`/`scroll_to_x`/`ensure_visible`/`scroll_to_child`
   pass `None`.
2. Fire `on_scroll` from the chokepoint **only when the value actually changed** (a clamped no-op at
   either end must not spam).
3. `on_scroll_start` — the first movement of a gesture. Gesture state exists already for the thumb
   (`thumb_grab`, `h_thumb_grab`) and the held track press (`track_repeat`); the wheel has none.
4. `on_scroll_end` — release for thumb/track. **A wheel gesture has no end event**, so it needs an
   idle timer in `tick(dt)`: fire when nothing has scrolled for ~100ms, which is how browsers
   implement `scrollend`. `tick` already runs for every layer (heca/src/app/lifecycle.rs:133) and
   already returns `true` while the track repeat is armed — extend that so a pending scroll-end keeps
   requesting frames.
5. All three are `#[host_only("behaviour crosses as an Intent, never a callback")]` for the property
   macro.

## Edge cases

- **Re-entrancy**: the callback fires inside the mutation. A listener calling `scroll_to` from
  `on_scroll` either loops or fights the gesture — document it, and consider deferring the fire to
  the end of the event.
- The higher-ranked bound (`for<'a> Fn(ScrollInfo<'a>)`) makes the stored closure type uglier than
  the library's other callbacks; check it stays usable at a call site before committing to it.
- `max_x`/`max_y` are derivable from `content - viewport`; keep them consistent.
- A relayout re-clamps both axes (`on_layout`) — decide whether that counts as a scroll (it moves
  the offset without anyone asking). Leaning yes, with `event: None`.

## Done when

- The three callbacks fire from every path: wheel, thumb, track click, held-track repeat, and the

- Tests: fires on change only; `event.is_some()` for input and `None` for `scroll_to`; the wheel's

- The USER sees it: `on_scroll_end` firing once at the end of a wheel gesture, not per notch.

   scroll event would be RPC and the app's own screens, and neither needs one.
2. **We would build the wrong half.** Sending the event out is the awkward part (a name on the wire,
   arguments, routing it back to the right node). The pleasant part — the author writing a plain
   function — belongs to the plugin toolkit, which does not exist yet either.
3. **Nothing in today's work blocks it.** The listeners, the metrics payload and the single
   chokepoint they fire from are all in place.

## What it should look like when the runtime lands

The plugin author attaches a function to the scroll area, and that is the whole API. No id, no name,
no arguments — attaching to the region IS how you know which region fired:

```ts
Scroll({ axes: "both", onScrollEnd: (s) => { if (s.offsetY === s.maxY) loadMore() } })
```

The user pushed back on an earlier design where the author supplied an identifying argument, and was
right to: that was machinery from underneath the API surfacing in it. If the API ever makes an author
name their own scroll area, that is a bug in the API.

Underneath, the toolkit keeps the function on the plugin's side and gives heca a name for it. heca
sends that name back when the region scrolls. This is R4 in `docs/chrome-and-ui.md` and is the same
path `press` and `change` already take — no new mechanism.

## Which of the three events should cross

`scroll_start` and `scroll_end` only. The continuous `scroll` fires on every movement (each wheel
notch, each pointer move during a drag), and one message per movement to another program is too many.
`scroll_end` carries the full position, so anything that needs to know where it stopped gets it. If a
plugin ever genuinely needs live tracking, decide on a rate limit then rather than guessing one now.

## Still to settle when built

- An action does not describe the arguments it takes (`ActionMeta` has label, icon, policy, confirm —
  no argument list). So a wrong or misspelled argument is ignored in silence. That is the same shape
  of defect this phase fixed twice, and it is worth fixing before adding more argument-carrying
  events.
- The declarative event vocabulary is documented as three words (`press`, `change`, `toggle`) in both
  `docs/widgets.md` and `heca/src/chrome/view.rs`. Update both, and say why scrolling earns its own:
  it is the only widget event with a beginning and an end rather than a single moment.

### 📋 6dfe4acd-c706-485c-91b1-8b13aa163652 — T361 — A modal freezes hover state: the pane-header tooltip appears after the pointer has left

Status: 📋 `planned`

# The bug

Click an action button in a pane's top info bar that opens a modal. Move the mouse away. The
button's **tooltip appears anyway**, over a button the pointer left, while a modal owns the screen.

Reported by the user 2026-07-29.

# Why — the pointer stops being delivered, and hover is edge-triggered

`Tooltip` decides it is hovered from `PointerMoved` **transitions**
(`heca-grid-ui/src/widgets/tooltip.rs:239-250`): entering starts a wall-clock
`hover_since`, leaving clears it, and `shown()` (`:141`) is true once `hover_since` is older than
`delay` (default 0.5s). It never asks "is the pointer over me *now*" — it only reacts to a move that
crosses its bounds.

So it needs a leave event to un-hover, and while a modal is open it never gets one. In
`heca/src/app/events.rs`, the `WindowEvent::CursorMoved` arm **returns early** as soon as a modal
takes the move:

```rust
if crate::chrome::dispatch_modal_pointer(state, &Event::PointerMoved { pos }) {
    return;                       // ← the header trees never hear another move
}
…
crate::chrome::chrome_dispatch_move(state, pos);
crate::chrome::dispatch_pane_header_move(state, pos);   // ← unreached
```

The header's `Tooltip` therefore keeps the `hover_since` it had at the moment of the click, the
delay elapses, `tick` crosses the show boundary, and the bubble appears over a button nobody is
pointing at.

**It is not tooltip-specific.** Every hover affordance in every non-modal retained tree freezes the
same way: a `Row`'s hover highlight, a `Button`'s hover fill, the `MarkerGroup` grip cue. The
tooltip is just the one that *appears* rather than merely persisting, so it is the one that got
noticed. The same staleness exists after the modal closes until the user happens to move the mouse.

# The fix — tell the other trees the pointer left

When a layer takes ownership of the pointer, every tree that no longer receives moves must be told
the pointer is gone, exactly as a real move out of bounds would tell it. One place, all affordances.

Candidate shape (decide with the maintainer):

- an explicit `Event::PointerLeft` in `heca-grid-ui/src/component.rs`'s `Event` enum, broadcast to
  the non-modal trees when an overlay opens (and to the modal's tree when it closes), OR
- reuse `PointerMoved` with a position outside every bound — cheaper, but "a move to nowhere" is a
  lie the next reader has to decode, and a widget that tracks the last position would store garbage.

Prefer the explicit event: hover is a real state, and "the pointer is no longer yours" is a real
transition that today has no vocabulary.

Dispatch sites to cover (all in `heca/src/chrome/mod.rs`): `chrome_dispatch_move` (:3479),
`dispatch_pane_header_move` (:1261), `dispatch_pane_viewport_move`. The overlay open/close path is
`heca/src/chrome/overlay.rs`.

# Also worth checking while here

- `Tooltip` has no `visible`/`disabled` gate on `shown()` — a tooltip on a widget that becomes
  hidden between the hover and the reveal will still paint. Same class of bug.
- The `Attention`/`Flash` and `Row` hover paths should be verified against the same scenario rather
  than assumed correct.

# Acceptance

### 📋 8f13b870-62c4-4556-a33f-377073527b4f — T397 — The complete Phosphor iconset + a generated name↔Glyph mapping

Status: 📋 `planned`

**Filed 2026-08-07 from `BACKLOG.md:1718` (`plugin-task-ui-8`), which was never in the planner.** It came up while deciding where a context-menu row's icon comes from (T395) and where a *plugin's* icon could come from. Transferred here in full; the backlog entry's two stale details are corrected below.

# Why this is small, and why it unlocks a lot

**~1,500 icons already ship in the binary and 52 are reachable.** The embedded face
`heca-grid-ui/assets/Phosphor-Duotone.ttf` (family `Phosphor-Duotone`, MIT, loaded via
`ICON_FONT_BYTES` at `heca-grid-ui/src/font.rs:56`) has **3025 codepoints** — measured with
`fontTools`, not estimated. Phosphor Duotone pairs each icon consecutively
(`PRIMARY_OFFSET = 1`, `heca-grid-ui/src/widgets/icon.rs:27`), so that is roughly **1,512 icons**.
The `Glyph` enum (`heca-grid-ui/src/widgets/icon.rs:33`) exposes **52** — about 3%.

So "a plugin wants a Docker whale / a database / a cloud" needs **no new font, no new asset, no
licensing question**: the glyph is already in the binary. The only thing missing is a way to *name*
it. That is this task.

This is also why **Nerd Font is the wrong answer** for pictograms: `FontRole::NerdFont`
(`heca-grid-ui/src/scene.rs:325`) exists for the keyboard glyphs Phosphor has none of (`⇧ ⌘ ⎋`),
and routing plugin icons through it would put plugin UI in a different visual language from the app.

# Current state

- `Glyph` — a hand-transcribed curated enum, 52 variants, `heca-grid-ui/src/widgets/icon.rs:33`.
  `secondary()` gives the `:before` codepoint; `primary_char()` adds `PRIMARY_OFFSET`.
- `glyph_from_name` — the name→`Glyph` lookup the declarative path uses, at
  **`heca-view-realize/src/lib.rs:1077`** (the backlog says `heca/src/chrome/realize.rs`; it moved
  when the model became its own crate). Its own doc calls it "a **curated stopgap of ~35 icons**"
  (the enum is now 52 — the two already disagree, which is the drift this task exists to end).
- `heca-renderer/tests/font_coverage.rs` — reads the embedded faces' `cmap` and fails the build when
  a named codepoint has no glyph. Hand-maintained today.
- **The transcription has already been wrong once**: `Glyph::PlusSquare` was removed because its
  codepoint drew something else, and `CaretLeft`/`CaretUp` still carry "confirm visually" comments —
  because, per the P085 handoff, *"the Phosphor codepoint table is not in the repo"*.

# What to build

1. **Get Phosphor's name↔codepoint table into the repo.** It ships with the Phosphor release (the
   CSS/JSON map). This single piece of data is the whole unlock — everything below is generated
   from it.
2. **Generate** the `Glyph` enum (or its codepoint table) **and** the name lookup from that one
   source — build script, macro or generated table. The backlog's words: *"a hand-maintained 1:1
   match of hundreds of icons is a bug farm."* The enum and `glyph_from_name` must not be able to
   diverge.
3. **`Icon::new("name")` in grid-ui.** Today `Icon::new` takes the `Glyph` enum
   (`heca-grid-ui/src/widgets/icon.rs:224`) and the only name lookup lives in `heca-view-realize`,
   **above** grid-ui, so grid-ui cannot reach it. With a generated table the lookup can live in
   grid-ui and `heca-view-realize` can drop its stopgap and call it.
   ⚠️ **Do not silently swap `Glyph` for a string.** A `Glyph` typo is a compile error; a name typo
   resolves to `None` and draws nothing — the same invisible failure as the missing `.nav_key(..)`
   that opened no menu with no error and no failing test. Decide with Antonio whether the string
   form is additive (both) or a replacement.
4. **Turn `font_coverage` into a check over the generated data** rather than a hand-written list, so
   every generated name is proven present in the embedded `cmap`.
5. **Document the names for authors** — `docs/widgets.md` icon table, `docs/chrome-and-ui.md` — and
   update the showcase icon gallery.
6. **Plugin registration validates at registration time.** A plugin naming an icon cannot be caught
   by a build-time test, so the registration path must reject an unknown name rather than let the
   renderer draw an empty box.

# Ordering

The backlog's condition — *"Run this last in the plugin arc, once the widget/`realize`/overlay
surface is settled, so the iconset is filled against the final set of consumers"* — is met by T395,
which settles the menu/overlay surface. It is filed here for that reason.

# Not in scope, deliberately

Fonts a plugin ships itself (`FontRole` would stop being a closed enum and become a font registry:
loading, ids, duplicate families, licensing, atlas lifetime) and arbitrary image/SVG icons (a
texture path, not a glyph — `heca-renderer/src/image.rs` exists for kitty graphics but nothing wires
it to widgets). Both are real features, not extensions of this one.

# Edge cases

- Duotone means **two** codepoints per icon; a generated table must carry the secondary and derive
  the primary via `PRIMARY_OFFSET`, not assume one codepoint per name.
- The embedded face's range runs to `U+EE83` and includes non-icon codepoints (the count starts at
  `U+0000`) — generate from Phosphor's own map, not by walking the `cmap`.
- Expanding `Glyph` to ~1,500 variants makes any exhaustive `match` on it unmaintainable; check for
  existing exhaustive matches (`Glyph::ALL`-style walks, the coverage guard, any icon picker) before
  expanding, and prefer a table to enum variants where a match would otherwise explode.

### 📋 787ba99d-c2e9-4dd0-bd28-323ec208c898 — T398 — Plugins must be able to build EVERY widget — no host-only exceptions

Status: 📋 `planned`

**Decided by Antonio 2026-08-07**, twice and emphatically: *"plugins cannot build everything? that's a problem. We need API for plugin to use all widgets."* then, on being shown the list: *"Most of these are essentials for plugins. If they want a progressbar they cant, or a dialog, or flex... WE MUST SUPPORT ALL."*

**There is no host-only list. Every widget gets a `WidgetKind`.**

# What is NOT the problem — read this first

**The authoring ergonomics already exist and are good.** `heca-view/src/build.rs` is the typed SwiftUI-style builder (plugin-task-ui-2, done): a type per kind, so `Label::new("x").title("y")` does not compile, children only on kinds that take them, and `every_widget_property_is_reachable_from_the_sdk` fails when a property is unreachable from it.

**The `WidgetKind` enum being closed is also not the problem.** `realize` must turn a kind into a real Rust widget compiled into heca; a plugin cannot ship a Rust type over the wire, so the buildable set is whatever the host binary contains. An open string kind would only turn "missing" into "renders nothing".

**The problem is coverage, and nothing else: 32 kinds for ~70 exported types.** A plugin writes lovely code and has no `Dialog`, no `ProgressBar`, no `Flex`, no `Menu` to write. Do not re-litigate the enum or the SDK — add the kinds.

# The gap, measured

`heca-grid-ui/src/widgets/mod.rs` exports **70** public types. `WidgetKind` (`heca-view/src/lib.rs:38`) has **32** variants.

Stripping the enums/config/aliases (`*Variant`, `Glyph`, `NfGlyph`, `ScrollInfo`, `ScrollAxes`, `MenuAnchor`, `MenuEntry`, `Orientation`, `RegionMode`, `RevealAlign`, `LabelSide`, `DotStatus`, `Ellipsis`, `ActiveMarker`, `GridCell`, `Command`, `Toast*`, `TooltipSide`, `Container` = alias of `Flex`), the **18 widgets with no kind** are:

`Menu` · `MenuItem` · `ContextMenu` · `Dialog` · `Tooltip` · `ProgressBar` · `Spinner` · `CardGrid` · `FocusScope` · `Visibility` · `NfIcon` · `PaneFrame` · `Flex` · `CommandPalette` · `Pane` · `ChromeRegion` · `ScrollRegion` · `ToastStack`

# Why the gap was invisible

`every_widget_kind_realizes_to_a_live_widget_except_the_host_only_ones` walks `WidgetKind::ALL` and proves every declared kind maps to a live widget. **One direction only** — a widget with no kind is invisible to it. That is why AGENTS' "realize coverage is COMPLETE" is true and still leaves half the library unreachable: it means "no kind is a dead end", not "every widget is reachable".

# ⚠️ The settled rule this task supersedes

AGENTS says: *"A widget whose state is a live host signal is HOST-ONLY — static serializable data cannot drive a signal, so a declarative one would be a dead control. `ScrollBar` is the case (plugins use `Scroll`)."*

Correct **for a model that can only carry literals**. It stops being correct once a node can name a value key — **P085(F003)/T360** (`58SE7`), whose step 5 is exactly that. So a declarative `ProgressBar` is not a dead control: its `value` names a key, the plugin writes the key, the bound signal updates in place. **The host-only category was a missing mechanism, not a property of the widgets.**

**T360's binding spelling is DECIDED (2026-08-04, Antonio) — do not re-ask, and do not repeat the old "open question" line:**

```rust
struct ViewNode {
    kind, props,
    events:   Map<EventName, Intent>,   // already exists — a name → an indirection
    bindings: Map<PropName, String>,    // prop name → value key. THE SAME SHAPE.
    children,
}
```

A `bindings` map beside `events`, because the node already expresses this indirection for behaviour. `PropValue` is left alone. The literal in `props` is the **fallback**, shown until the plugin's first write. `realize` reads the literal, then lets a binding override it via `container_value(mount, key)`. **Rejected:** `PropValue::Text("@key")` (a sigil collides with a legitimate `@handle`) and `PropValue::Binding(String)` (grows the wire vocabulary; kept only as a fallback if two maps prove worse).

**Consequence: T360 is a hard dependency for the signal-driven widgets** (`ProgressBar`, `ScrollBar`, `ScrollRegion`, `CommandPalette`, `ToastStack`, `Pane`, `ChromeRegion`). The rest need nothing and go first.

**Update the AGENTS ⭐ block when this lands**, so the host-only rule is not re-applied by a later session reading a superseded line.

# What to build

1. **A `WidgetKind` + `realize` arm for every widget in the list**, following the settled process: *"Extending the vocabulary is host-side work (widget + `realize` arm + showcase + `docs/widgets.md`); plugins only compose existing kinds."*
2. **Guard the OTHER direction** — the reason this will not need redoing. A test that walks every widget `heca-grid-ui` exports and **fails if it has no `WidgetKind`**. Today a widget can be added with no kind and nothing notices. Mechanism open (an inventory the crate exposes, a macro-collected list, a source-walking test); the requirement is that it cannot be forgotten.
3. **Showcase + `docs/widgets.md`** for every new kind. The SDK follows automatically.

# Order of work

**First — `Menu` / `MenuItem`**, the case that surfaced this and the one T395 is settling. `heca-view` has **no menu concept at all** (no kind, no `context_menu` prop; `heca-view-realize` never touches one), so a plugin's own row opens **nothing** on right-click: the same silence as the missing `.nav_key(..)` that motivated P084 — no error, no failing test.

Shape, using conventions that already exist — **no new mechanism**:
- `WidgetKind::Menu` + `WidgetKind::MenuItem`.
- Attach with the settled slot convention (*"a widget with several places for children takes a `slot` prop on the CHILD"*): `slot: "context_menu"`. **Not** a menus map, **not** a second children vector.
- A composed row is just `children` on the `MenuItem` node; behaviour is `on_press → Intent`.
- `realize` fills the existing `Base::context_menu` slot (`heca-grid-ui/src/component.rs:238`, `Fn() -> ContextMenu`) with a closure that re-realizes the described menu per opening. **One slot, both paths.**

**Symmetry worth keeping:** `MenuItem::child` takes a builder closure only because native code must rebuild an owned subtree per opening. A `ViewNode` is data and re-realizable by construction, so the declarative path gets composed rows **with no closure at all**.

**Then** the ones needing nothing new: `Dialog`, `Tooltip`, `Spinner`, `CardGrid`, `PaneFrame`, `Flex`, `Visibility`, `FocusScope`.

**Last** the signal-driven ones, behind T360: `ProgressBar`, `ScrollRegion`, `CommandPalette`, `ToastStack`, `Pane`, `ChromeRegion`.

# Constraints (settled — do not re-open)

- `heca-grid-ui` never learns about `ViewNode`; the dependency runs app → library only.
- Behaviour crosses as an `Intent` (action id + args), never a callback.
- A slot/child is `impl Component` — never narrowed to a closed enum.
- A realized subtree enters a widget via a `*_boxed` setter (`Dialog::body_boxed` is the precedent), because `Box<dyn Component>` is not itself `Component`.

# Edge cases

- `Flex`/`Container` may already be covered by `VStack`/`HStack` — check before adding a third spelling of the same box.
- `Visibility` and `FocusScope` are wrappers, not visuals — decide whether they are kinds or **props** on the wrapped node (a prop is probably right and cheaper). Either way a plugin must be able to express them.
- `NfIcon` needs glyph-by-name — see **T397** (the generated name↔`Glyph` mapping).
- Adding a kind is not free: `WidgetKind::ALL`, the drift guard (`heca-grid-ui/tests/prop_drift.rs`), the SDK's reachability test and the showcase all walk the vocabulary.
- `Pane` and `ChromeRegion` wrap app concepts (a terminal surface, a chrome region). Check what a described one would mean before forcing a kind on them — but the default is a kind, and "it is awkward" is not a reason to leave a hole.

# The defect — a shipped feature plugins cannot have

`prefix+/` (the universal hint picker) is registered like this today:

```rust
let id = hints.register(InteractionIntent::FocusPaneThenAction { … });  // heca/src/chrome/mod.rs:851
button.hint_target(id)                                                   // …and carry an id around
```

Three things a caller must know: a registry exists, they must pre-register, and `InteractionIntent` — which is **`pub(crate)`** (`heca/src/app/interaction.rs:99`).

**There are two doors, and they are not equal:**

| door | takes | who can use it |
|---|---|---|
| `HintTargetRegistry::register` (`heca/src/chrome/mod.rs:2808`) | `InteractionIntent` | **host only** (crate-private enum) |
| `HintTargets::register` (`heca-view-realize/src/lib.rs:69`) | `Intent` (name + args) | anyone, incl. plugins |

The top bar (`chrome/mod.rs:1816`) and the pane header (`:851`) use the **first**. A plugin can construct **no** variant of `InteractionIntent`, so it can only register a plain `Intent` naming an action — and a component's selection-dependent actions declare `ActionPolicy::ContainerFocused`, which **refuses** them unless the container already holds the keyboard. `FocusContainerThenAction` exists precisely to satisfy that, and a plugin cannot say it. So a plugin's row hint is blocked with no way to express the fix: a second-class version of a shipped feature.

# What to build

**`on_peek` as a universal slot on `Base`**, written with `EventExt` like `on_click` / `nav_key` / `context_menu`:

```rust
Row::new().child(Label::new(&pane.name)).on_peek(move || cursor_to(row_id));
```

The framework owns everything behind it: collecting targets from the tree (`collect_hint_targets` already walks `Base`), assigning the letter, drawing it, and firing the handler on a pick. No id, no registry, no host type at a call site.

**Then the declarative half**, which is the point of the rule: `on_peek` is an event like `on_press`, so `ViewNode.events` maps it to an `Intent` and `realize` wires it. A plugin writes the same line in a described tree and gets identical behaviour. **One door — delete the other.**

# What this replaces (delete, do not leave beside)

- `Base::hint_target(id)` and `NavExt`/`HintExt`'s id-passing form.
- `HintTargetRegistry` in the app (`heca/src/chrome/mod.rs:2800`-ish) and `ViewHintTargets` (`:2848`).
- `crate::chrome::named_press` (`:2877`) — **the specific conflation that caused the bug below**.
- `BuildCx.hints` threading through every builder that only exists to carry the registry.

### 📋 320728e2-821f-4b13-83a0-46fb7b544ec6 — T400 — The event model becomes the DOM's — delete the self-describing predicates

Status: 📋 `planned`

**Decided with Antonio 2026-08-07, point by point.** The trigger: he noticed `takes_raw_keys`, `routes_own_subtree` and `hit_bounds` and said *"i didn't notice all of these and i don't like. I want transparent APIs that provide clear interface not forcing the developer to discover uncommon things. SO always prefer common and well known APIs… can be derived, and that is true for all the other names you pointed."*

This is **RULE ZERO** (`AGENTS.md`) applied to the event model: a widget author should not have to answer questions about themselves so the framework can route correctly.

# The four decisions

## 1. Delivery follows focus and bubbles — DELETE `takes_raw_keys` and `takes_text_input`

The DOM has no such flags: a key goes to the focused element and bubbles. heca already has focus and both phases (`on_event_capture` / `on_event`, F004/P084/T394). So delivery is: **the focus owner, then up the ancestor chain.** Nobody declares anything.

`takes_text_input` was added on 2026-08-07 and is **already obsolete under this decision** — it was a flag working around the real defect: `ContextMenu` ended its match with

```rust
_ => Handled::Yes,   // "swallow all other input while open"
```

three arms below its own comment saying *"Modal capture is the HOST's job (the overlay branch swallows), not a `Handled::Yes` hardcoded here."* The widget contradicted itself, ate `Event::TextInput`, and the host returned before the key path — so **every context-menu quick-pick letter did nothing**. Remove the catch-all and the flag has no reason to exist.

Files: `heca-grid-ui/src/component.rs` (`takes_raw_keys` ~:558, `takes_text_input`, `deaf_to_raw_key` ~:799), `heca-grid-ui/src/widgets/input.rs:546`, `command_palette.rs`, `dialog.rs`, `context_menu.rs` (the catch-all).

## 2. `bounds === what is drawn === what is clickable` — DELETE `hit_bounds` and `damage_bounds`

Both exist for one reason: a widget draws **outside its own bounds**, so its input surface and damage rect had to be described separately. That is the *exception* to an invariant this phase already states in its own description.

**A floating widget places itself instead of describing itself.** `ContextMenu` is the worked example and the evidence: after T395 its rows are real children and `place_panel()` shifts the whole subtree to the anchor (the `shift_subtree` trick `Overlay` / `Select` / `ScrollRegion` already use), so its `bounds` **are** the panel — and its two overrides now just return `base.bounds`, i.e. they are already redundant.

Cost, accepted: every other overlay widget gets the same treatment — `Select` (open panel), `Tooltip`, `Dialog`, `ToastStack`, `CommandPalette`. Same refactor the menu already went through.

## 3. `routes_own_subtree` — DELETE; always traverse

Antonio: *"maybe always traverse ma if no children are listening it does nothing?"* — which is exactly the DOM. A child with no handler returns unhandled and nothing happens; the cost is walking nodes that do nothing.

Its two users need the ordinary expression instead:
- **`Select`** — closed option rows are placed children that must not take input. They are not "unroutable", they are **not interactive right now**: `disabled`, or not mounted while closed (`pointer-events: none` in DOM terms).
- **`Dialog`** — routes through an overlay-aware focus scan. Under decision 1 that is the framework's job.

## 4. One handler spelling, always carrying the event AND `stop_propagation`

Today there are two, and only one can stop the walk:

```rust
.on_click(|e: &PointerEvent| { … })                 // has the event, CANNOT stop
.on(EventKind::Click, |cx| cx.stop_propagation())   // can stop — the "general form"
```

The named builders consume the event for you, so `on_click` cannot say "don't consume". The DOM has one spelling and it always carries both. Antonio: *"would be great to have an event like in the dom to stop the propagation. `on_click(|e| { e.stop_propagation(); })` and have an event_listener in all widget… this could be used to intercept key press, hint letters etc."*

Target: **one handler argument carrying the event and the control**, for every kind, with `.on(kind, …)` being the same function with the kind as a parameter — not a different API.

```rust
.on_click(|e| { e.stop_propagation(); … })
.on_key(|e| { … })
```

This also removes the last reason a widget writes a swallow-everything catch-all — the thing that broke the quick-picks.

# Already true (do not rebuild)

- `EventCx::stop_propagation()` exists (`heca-grid-ui/src/event.rs:783`).
- Handlers live on `Base` for **every** widget via `EventExt` — no opt-in, no trait to implement.
- Capture and bubble phases exist (T394).

# ⚠️ Supersedes documented behaviour

`AGENTS.md` → the **SETTLED input model** block describes `takes_raw_keys` and "handlers live on `Base`" as the model. Update it when this lands, or a later session will re-apply the superseded rule — that already happened once today with the host-only rule.
