Close **ViewNode coverage for the whole widget vocabulary**, on the model the user chose (2026-07-13): an option is **a node with a value and arbitrary content**, and options are **children** — not a `props["options"]` list of strings.

## Why this phase exists (supersedes `viewnode-task-1`)
`viewnode-task-1` ("complete realize coverage") assumed the 8 missing kinds only needed *structured props*. Investigation showed they split into three different gaps, and the option-shaped ones need a **widget refactor**, not a prop:
- `Select` (`heca-grid-ui/src/widgets/select.rs:77`) is **self-contained**: `new(options: Vec<String>)`, paints its dropdown rows itself and hit-tests them by arithmetic — no child components.
- `Tabs` (`widgets/tabs.rs:51`) likewise "lays its own segments from monospace metrics (no child components)".
Both **hand-draw their content**, so both are refactor targets under the standing rule (AGENTS.md ⭐ WIDGET ARCHITECTURE: a widget's content is composed from child `Component`s, never hand-drawn). Exactly the `Button` refactor (`07d4c1a`, PR #237), twice.

## The model (LOCKED with the user)
```
ViewNode::new(WidgetKind::Select)
    .prop("selected", PropValue::Int(1))
    .on("change", Intent::new("set_level"))
    .child(ViewNode::new(WidgetKind::Choice).prop("value", PropValue::Text("low".into()))
        .child(ViewNode::new(WidgetKind::Row)
            .child(ViewNode::new(WidgetKind::Icon).prop("icon", PropValue::Glyph("circle".into())))
            .child(ViewNode::new(WidgetKind::Label).text("LOW"))))
```
- **`Choice`** = a selectable, **value-carrying** container whose content is **arbitrary children** (like `<option value=…>` / SwiftUI `.tag()`). Named `Choice` because a widget named `Option` would shadow `std::Option` at every call site.
- **`Choice` and `Item` COEXIST** (user decision): `Item` is a *row layout* (leading / label / trailing); `Choice` is *any content + a value*. Both must be documented so the difference is unmistakable — including when to use which.
- One option primitive, four consumers: `Select`, `Tabs`, and later `ContextMenu` / `CommandPalette`.
- **Values flow into the intent**: the widgets keep tracking a selected **index** internally; `realize` captures each `Choice`'s `value` prop and dispatches the `change` intent with `args["value"]`, so a plugin receives `{"value":"high"}` rather than an opaque index.
- After this, **`PropValue::List` is needed only by `Grid`** (`areas` = list of strings, tracks = list) — it shrinks from "the core mechanism" to a `Grid` detail.

## Decisions already taken
- `ScrollBar` is **host-only, not plugin-authorable**: its state is live host signals (`content_extent` / `viewport_extent` / `offset`) that static, serializable data fundamentally cannot drive. A plugin uses `Scroll` (a `ScrollRegion`), never a raw scrollbar. To be *documented as such*, not realized.
- Grid tracks are **CSS-like strings** parsed by `realize` (`"1fr"` → `Track::Fr(1.0)`, `"22px"` → `Track::Px`, `"auto"`/`"min"`/`"max"`); unknown tokens degrade to `Auto` (realize stays total for untrusted input). No new schema invented.
- Named child slots (`DockFrame`'s `header` vs body; `Item`'s leading/trailing) via a **`slot` prop on the child node** — no change to the `ViewNode` shape, and it generalizes.

## How the hard part was solved
**taffy measures, `Select` places.** The options are `Choice` children laid out in the trigger's flow — where the engine measures them (each hugs its content; `flex_shrink: 0` is already the library default, so they keep their natural heights). `Select` then *places* them, baking the offset from that flow into their bounds — the `ScrollRegion` trick, now shared: `shift_subtree` was promoted from `scroll_region.rs` to `component.rs` (`pub(crate)`).

Invariant: **bounds === what is drawn === what is clickable.** Picks go through `choice_at()` (real bounds, never row arithmetic). Rows outside the visible window — and every row while closed except the chosen one — are **collapsed to zero size**, so no stale rect can swallow a click. Placement is re-derived in `on_layout`, idempotent (absolute targets; never compounds).

- Row heights are **measured, not arithmetic** (`natural_h`, captured post-layout) → a two-line option stacks correctly. The flip/cap fit test reserves the *tallest* row (conservative → never clipped).
- The control's horizontal insets ride on the rows as **margins** (not padding on the Select): that widens the control around them *and* keeps option content clear of the chevron + scrollbar lane. Padding could not do both.
- Trigger **width hugs the widest option** (engine-measured, icons included — the char-count estimate is gone); **height** hugs the tallest option, so it can stand any of them in it.

## The trigger shows the chosen option ITSELF (icon and all), open or closed
Closed, the option *is* the trigger's content — `place_options` stands that child in the trigger slot. Open, it has moved into the list (a component is laid out in exactly one place), so the trigger draws a second **image** of its content via the new `PaintCx::with_translate`. Only content is echoed, never the row's chrome (the trigger's box is its chrome; a pill inside it would be a box in a box) — hence `sync_option_states` ties "selected" to `open`.

## 3 generic library additions (all forced by the above, all documented in `docs/widgets.md` + rustdoc)
- **`PaintCx::with_translate(dx, dy, |cx| …)`** — paint a subtree somewhere else. One choke point (`PaintCx::placed`) covers every draw helper + the cull test, so **no renderer change**. Rule written into the docs: what it draws is **NOT interactive** (no bounds ⇒ not hit-tested/focusable/hoverable); never use it to *move* a widget — that is `shift_subtree` + `on_layout`, which keeps bounds honest.
- **`Component::text_summary()`** — accessible name of composed content (default: first child that has one; `Label` supplies it). Powers `selected_label()`: a control reading the *text* of content whose type it cannot see.
- **`Style::align_self` + `LayoutExt::align_self`** (CSS `align-self`). Without it an `Auto`-width control silently goes full-width in a column parent (default `align: Stretch`) — the width hug would have been a regression.
