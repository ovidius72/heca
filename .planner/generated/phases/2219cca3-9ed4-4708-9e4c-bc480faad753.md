A provider or plugin can register an action, but nothing binds it to a key from config or shows it in the command palette. The plan's Phase 11 half that has no phase.

Added 2026-07-26 after auditing docs/chrome-and-ui.md against the planner. This is the
half of the plan's "Phase 11 — Config / Keybinding / Command Palette Integration" that no phase
covers. F003/P007 (plugin-09) covers the CONFIG half. F003/P013 (menu-nav) is about navigating
inside a list or menu, which is a different thing entirely.

═══ WHAT ALREADY EXISTS — BUILD ON IT, DO NOT REINVENT ═══
The action side is DONE (F003/P003, plugin-04):
- `ActionRegistry` + `ActionCatalog` (`heca/src/actions.rs`) — one runtime registry. A name-keyed
  action registers through `register_dynamic(registry, catalog, meta, handler)`.
- `ActionMeta` carries `name`, `label`, `description`, `category`, `default_binding`, `icon`,
  `policy`, and an optional `confirm`. **`default_binding` already exists on the metadata** — that
  is the hook this phase consumes.
- `ActionCatalog::describe_all()` / `describe(name)` → `ActionInfo` (serde). Introspection is
  already there, which is what a palette needs to list things.
- `unregister_dynamic` + an RAII `ActionHandle`, so a contributed action disappears when its
  provider unmounts.

═══ WHAT IS MISSING ═══
- A contributed action's `default_binding` is never read by the keymap. Registering an action does
  not make a key work.
- `keybindings.default.toml` and the user's keybindings only speak to built-in `WmAction`s. There
  is no path for a user to bind a provider's or plugin's action by name.
- The command palette does not list contributed actions. It should, since `describe_all()` already
  returns them.
- Nothing resolves a collision between a contributed default binding and an existing one, and
  nothing tells the user when a contributed binding is refused.

═══ WORK ═══
1. Read `default_binding` from `ActionMeta` when an action registers, and offer it to the keymap.
2. Let a user bind ANY action by name in config, contributed ones included — the same syntax as a
   built-in. The registry is keyed by name already, so this is a lookup, not a new mechanism.
3. Feed the palette from `ActionCatalog::describe_all()` so contributed actions are listed,
   searchable and runnable, with their label, icon and category.
4. Decide collision behaviour with the user: does a contributed default lose to an existing
   binding, or win? Whatever is chosen, the user must be TOLD, not silently ignored — the
   Improvements feature (F010) already covers notifying about blocked keybindings.
5. Honour `ActionPolicy` at dispatch, exactly as a built-in does. A contributed action must not
   bypass the policy system.
6. Unbinding on unmount: when a provider goes away its bindings must go with it, through the
   existing RAII handle.

═══ RULES THAT APPLY ═══
- Input parity (AGENTS.md, grid-ui plan P2): an action reachable from the palette must also be
  bindable and reachable over RPC. All three or none.
- Never hardcode a binding. It goes through `KeymapRegistry` like everything else.
- Follow the full Adding-New-Actions checklist in AGENTS.md for anything new this phase adds.

═══ DEPENDS ON ═══
F003/P003 (done) for the registry. Best done alongside or after F003/P009 (config-file plugins),
which is the other half of the plan's Phase 11 and will produce contributed actions to bind.
