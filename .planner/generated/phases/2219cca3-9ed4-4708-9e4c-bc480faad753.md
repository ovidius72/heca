# 2219cca3-9ed4-4708-9e4c-bc480faad753 — P080 — plugin-10: Keybinding + command-palette integration for contributed actions

**Status:** 🚧 `in-progress`
**Created:** 2026-07-26T08:38:21.132Z
**Updated:** 2026-08-04T19:36:06.896Z

A provider or plugin can register an action, but nothing binds it to a key from config or shows it in the command palette. The plan's Phase 11 half that has no phase.

Added 2026-07-26 after auditing docs/chrome-and-ui.md against the planner. This is the
half of the plan's "Phase 11 — Config / Keybinding / Command Palette Integration" that no phase
covers. F003/P007 (plugin-09) covers the CONFIG half. F003/P013 (menu-nav) is about navigating
inside a list or menu, which is a different thing entirely.

═══ WHAT ALREADY EXISTS — BUILD ON IT, DO NOT REINVENT ═══
The action side is DONE (F003/P003, plugin-04):
- `ActionRegistry` + `ActionCatalog` (`heca/src/actions.rs`) — one runtime registry. A name-keyed
  action registers through `register_dynamic(registry, catalog, meta, handler)`.
- `ActionMeta` carries `name`, `label`, `description`, `category`, `default_binding`, `icon`,
  `policy`, and an optional `confirm`. **`default_binding` already exists on the metadata** — that
  is the hook this phase consumes.
- `ActionCatalog::describe_all()` / `describe(name)` → `ActionInfo` (serde). Introspection is
  already there, which is what a palette needs to list things.
- `unregister_dynamic` + an RAII `ActionHandle`, so a contributed action disappears when its
  provider unmounts.

═══ WHAT IS MISSING ═══
- A contributed action's `default_binding` is never read by the keymap. Registering an action does
  not make a key work.
- `keybindings.default.toml` and the user's keybindings only speak to built-in `WmAction`s. There
  is no path for a user to bind a provider's or plugin's action by name.
- The command palette does not list contributed actions. It should, since `describe_all()` already
  returns them.
- Nothing resolves a collision between a contributed default binding and an existing one, and
  nothing tells the user when a contributed binding is refused.

═══ WORK ═══
1. Read `default_binding` from `ActionMeta` when an action registers, and offer it to the keymap.
2. Let a user bind ANY action by name in config, contributed ones included — the same syntax as a
   built-in. The registry is keyed by name already, so this is a lookup, not a new mechanism.
3. Feed the palette from `ActionCatalog::describe_all()` so contributed actions are listed,
   searchable and runnable, with their label, icon and category.
4. Decide collision behaviour with the user: does a contributed default lose to an existing
   binding, or win? Whatever is chosen, the user must be TOLD, not silently ignored — the
   Improvements feature (F010) already covers notifying about blocked keybindings.
5. Honour `ActionPolicy` at dispatch, exactly as a built-in does. A contributed action must not
   bypass the policy system.
6. Unbinding on unmount: when a provider goes away its bindings must go with it, through the
   existing RAII handle.

═══ RULES THAT APPLY ═══
- Input parity (AGENTS.md, grid-ui plan P2): an action reachable from the palette must also be
  bindable and reachable over RPC. All three or none.
- Never hardcode a binding. It goes through `KeymapRegistry` like everything else.
- Follow the full Adding-New-Actions checklist in AGENTS.md for anything new this phase adds.

═══ DEPENDS ON ═══
F003/P003 (done) for the registry. Best done alongside or after F003/P009 (config-file plugins),
which is the other half of the plan's Phase 11 and will produce contributed actions to bind.

`action_ref_from_config` (`heca/src/app/registry.rs:32`) resolves a config binding by name: built-in with args → `ActionRef::Builtin`, bare built-in → `ActionRef::Builtin`, and **anything else → `ActionRef::Dynamic(intent)`**, carrying the `args` table as `PropValue::Text`. The comment at `registry.rs:21` states the rule: "Anything else ⇒ `ActionRef::Dynamic` — **not an error** (plugin-04 G3). That is exactly what this task asked for: same syntax as a built-in, a lookup rather than a new mechanism, and a user who never has to know whether an action is built in or contributed.

### ✅ 58a4843a-f15c-4313-86a4-e694f82f8921 — T324 — Command palette lists contributed actions

Status: ✅ `done`

`ActionCatalog::describe_all()` already returns `ActionInfo` (serde) with label, icon and category — everything a palette needs. The palette does not read it. Feed it from there so contributed actions are listed, searchable and runnable.

---
**Completion summary:**
Closed 2026-08-04 by a reconciliation pass — **delivered by P085(F003)/T358**, which was written after this task was filed and went further than it asked.

`heca/src/chrome/palette.rs::entries` builds every row from `catalog.all()`, so a contributed action is listed with its label, description, icon (via `catalog.icon`, which falls back to the category's glyph so no row is blank) and its bindings. It is searchable through the shared `SearchModel` like any other row.

T358 also solved the part this task did not anticipate: a contributed action usually declares `ActionPolicy::ContainerFocused`, so merely *listing* it would produce an entry that is refused when chosen. `InteractionIntent::FocusContainerThenAction` focuses the owning placement first and then performs, which satisfies the policy instead of bypassing it. Rows are labelled with the owning component's title (`"Containers › Restart Container"`), and actions with a **required** argument are not offered at all — arity, read off the `args` every action declares.

Note this task had earlier been raised as a possible cancellation; it is closed as **done**, not cancelled, because the capability exists and is shipped.

**Checklist:**

### ⏳ dfcecf3d-05fc-43f1-a08d-a827d0e8a337 — T335 — Binding collisions + ActionPolicy at dispatch (NEEDS A DECISION)

Status: ⏳ `waiting`

⛔ Originally: "does a contributed default binding LOSE to an existing one, or WIN? Ask the user first." **Reconciliation pass 2026-08-04 — two thirds of this is already settled and shipped.**

## 1. The collision decision: MADE, and implemented. Config wins.

`Provider::keybindings()` (`heca/src/providers/mod.rs:196`) states the rule: "Whatever the user's file says still wins: a registration never overwrites a combo the config already bound, and never adds a second key to an action the user has rebound."

Enforced in `register_component_keybinding` (`heca/src/app/registry.rs`): it returns early when the `BindingIndex` already knows the action, and skips any combo the layer already resolves. So a contributed binding **loses**. Do not re-open this.

## 2. `ActionPolicy` at dispatch: HONOURED, no bypass.

`dispatch_action_ref` (`heca/src/app/interaction.rs:918`) sends `ActionRef::Dynamic(intent)` through `dispatch_intent(… InteractionIntent::View(intent) …)` — the same policy-routed door as a built-in. A contributed action is judged exactly like one of heca's own. P085/T358 went further and added `FocusContainerThenAction` so a `ContainerFocused` action is *satisfied* rather than refused.

## 3. What is actually left: the user is never TOLD a binding was refused.

This is the whole remaining scope. A registration that loses a collision is dropped **silently**, which is the defect the task named ("never silently dropped").

It is a notification producer, so it belongs to **F009 🔔 Notification System**, which is entirely unstarted (0/60). Ordering: P061 model → P056 store → P060 toast rendering → P059 dispatch → P062/P055 producers. Do not build an ad-hoc message for this — it is the same mistake T381 is filed to avoid, and F010 (Improvements) was already noted as covering "notify about blocked keybindings".

**When resuming:** the only code to write is the producer call at the point of refusal in `register_component_keybinding`, plus whatever F009 settles as the draft/severity API. Everything else here is done.

**Checklist:**
- [ ] BLOCKING: settle collision behaviour with the user
- [ ] Refused bindings are reported to the user
- [ ] ActionPolicy honoured at dispatch
- [ ] Policy spot-check tests
