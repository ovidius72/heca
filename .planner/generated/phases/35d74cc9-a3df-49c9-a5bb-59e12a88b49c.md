### 📋 e73685a2-4e0e-4287-965a-796c64ee8f2d — T349 — Resize handle: a widget between two siblings that drags the split

Status: 📋 `planned`

# What it is

A **handle placed between two containers** that lets the user drag the split between them —
vertically, horizontally, or either, according to the axis it sits on — **and the same split moved
from the keyboard** through the resize mode. Requested by the user 2026-07-28, after two containers
sharing a sidebar landed (F003/P011/T021).

# Where it goes and what it replaces

**A widget in `heca-grid-ui`, not app code.** The app hand-rolls this for its dividers today:
`heca/src/mouse/resize.rs` (`mod resize` at `heca/src/mouse.rs:14`) tracks a divider drag,
`mouse.rs:30-42` gates DnD and focus-follow while one is in flight, and `resize::cursor_for`
(`mouse.rs:58`) picks the OS cursor for the divider under the pointer. It emits a **parameterized
resize action** through the registry rather than mutating state directly — the right shape, worth
keeping.

**Absorb, don't duplicate:** decide explicitly whether `mouse/resize.rs` becomes a thin caller of the
widget or is deleted. Leaving both is the failure this task exists to avoid. `RegionState.size`
(`heca/src/chrome/state.rs`) plus the existing action already persist a sidebar's width — that
persistence model is the precedent to follow.

# What it must sit between

- **`VStack` / `HStack`** — a handle adjusts two siblings on the stack's axis.
- **A region's container stack** — `build_region_content` (`heca/src/chrome/mod.rs`) stacks containers
  and interleaves a `Separator`; a handle is the draggable form of that rule.
- Check what else genuinely applies: `Grid` (tracks, not siblings — a different problem),
  `Pane`/`PaneFrame`, and the sidebar↔content divider resized today.

# ⌨️ The resize mode — ✅ DECIDED BY THE USER 2026-07-28

The mode **already exists** and is config-defined, not an `InputMode` variant (an earlier note in this
task claimed there was no resize mode — wrong, and that is why: looking at the enum misses it):

```toml
# keybindings.default.toml:329 — prefix+r → sticky resize mode
[[keys.mode]]
name = "resize"
trigger = "prefix+r"
sticky = true                                   # stays until Esc
[[keys.mode.bindings]]
action = "resize"
keys = "h"
args = { target = "column", axis = "x", amount = "-50" }
```

A mode is a **sub-keymap**: while active its bindings apply instead of the normal ones. Built-ins are
`resize`, `sidebar`, `selection` (`:291`), and the blocks work in `config.toml` too — both files merge
before being read.

The decisions:

1. **It ships as a default app keybinding and stays customizable.** `prefix+r` is the shipped default;
   every binding inside the mode stays overridable in `config.toml`. The **container bindings are
   defaults too** — not something a user must add to get the feature.
2. **Any resizable area, both axes.** Not columns and panes only: a container, a region, two siblings
   of a stack — anything the handle can sit between. `ResizeTarget` (`heca/src/input.rs:18`, today
   `Column | Pane`, `EnumArg::VALUES = ["column", "col", "pane"]`) grows variants; `axis` already
   covers x and y through `ResizeAxis`. Vertical **and** horizontal for every target that has both.
3. **The keybinding file declares a FIXED amount; the proportion is worked out internally, per
   target.** The config keeps writing plain numbers exactly as it does now (`"-50"`, `"40"`) — that unit
   does **not** change, so **no config migrates and nothing a user has written breaks**. What changes
   is inside: the handler converts that fixed step into a **proportional** change for the target it was
   given, and what gets stored is the proportion. So a resize behaves the same on a small window and a
   large one, and a container's split survives a window resize because it moved shares (`flex_grow`,
   F003/P011/T021) rather than pixels.
   - One conversion, in one place, taking the target + its current extent + the fixed amount. The drag
     and the key must both go through it; two conversions will drift.
   - The knowledge of what a step means for a given target lives with the target, which is why this is
     "per target" and not a constant.
4. **A binding may pass its own amount, or leave it out for the default.** `amount` becomes an
   **optional** argument with a documented default, so the shipped bindings stay terse and a user who
   wants coarser steps writes a number. Side effect worth knowing: with no required args left, `resize`
   becomes legal as a *bare* binding too — the rule that blocked that was about required arguments
   (F003/P010/T006).

Other resize actions for reference: `resize_to` (absolute, `actions.rs:1832`), `resize_increase` /
`resize_decrease` (bare, `prefix+=` / `prefix+-`, **column-specific**), `resize_column_by` /
`resize_pane_height_by` (`:2000`, `:2012`). Ask whether they route through the same conversion, and if
not, say why in their descriptors.

## Which area it acts on

"The focused one" needs **F003/P011/T020** (`FocusDock` — chrome keyboard focus as a container id).
Until that lands a binding names its target explicitly, which mode bindings do anyway since they carry
args.

# What a drag changes

A drag moves the **shares** of its two neighbours, never px sizes — through the same conversion the
keyboard uses. Work out:

- how a pixel delta becomes a change in two grow factors (the pair's sum is the invariant);
- the floor: an area must not be draggable or keyable to zero — a minimum, and whether it snaps shut;
- where it persists: per **placement**, keyed by container id in `SharedChromeState`, like the scroll
  offsets, so it outlives a tree rebuild and two placements resize independently.

# Also

- **Axis from the parent's direction** where possible rather than the caller restating it; explicit
  override for the two-axis case.
- **Cursor feedback** already exists for dividers (`resize::cursor_for`) — reuse it.
- **Declarative surface** comes free via `#[prop]` + the drift guard, so a described tree can carry a
  resizable split. The drag callback is host-only, like every callback.

# Acceptance

- One implementation: the app's divider resizing goes through the widget, or is gone.
- A handle between two areas drags their split; the split survives a window resize.
- **`prefix+r` then a key resizes a container** by default, both axes, through the existing mode and
  the existing `resize` action — and RPC does the same, one code path.
- The config still declares fixed amounts; **no existing binding changes meaning**. The proportional
  conversion is internal, one function, shared by drag and key.
- Nothing can be reduced to nothing.
- Whole workspace green, clippy 0 warnings.
- **The USER drags it and keys it in the app** — interaction, so tests are not verification.

### ⏸️ d92a629d-5310-4beb-97db-c13a929e0cd9 — T390 — A picker widget, extracted from CommandPalette — the second consumer that proves the search seam

Status: ⏸️ `deferred`

Proposed by Antonio 2026-08-04, after asking whether a `FilterableSelect` was needed to use the search API. **Deferred by Antonio 2026-08-04** — see the motivation. Everything needed to restart is below.

## Why extraction, not a new widget

The command palette **already is a picker**: a query line, a filtered and ranked list, keyboard navigation, per-row marks, and now a query history. Building a `FilterableSelect` beside it would duplicate every one of those and the two would drift — which is the same defect this whole feature set has been correcting (the palette hand-rolled truncation, wrapping, match highlighting and a matcher, each because the shared piece did not exist).

So: pull the picker **out** of `heca-grid-ui/src/widgets/command_palette.rs` — the query `Input`, the filtered list, the selection, the row placement, the history keys — and leave `CommandPalette` as a thin specialization that supplies commands and runs the chosen one.

## Why it is worth doing

`heca-grid-ui/src/search.rs` (P092/T384) is written to be embedded by any widget: `rank` takes a closure yielding `(Option<id>, text)` and names no widget type, scopes are keyed so each surface has its own memory, and `WidgetIntent::MenuHistoryUp`/`Down` are shared vocabulary. A second consumer is what finds the wrong assumptions, and a picker also gives the app a reusable surface for "switch workspace", "move pane to…", "open file", and anything a plugin wants to offer — the fzf / telescope shape.

## ⚠️ What T393 changed about the premise — read this first

The original filing said the palette was `search.rs`'s **only** consumer, so its generality was "designed rather than demonstrated". T393 (done, commit `0ded6ed`) partly changed that, and partly did not:

- **It did stress the seam.** The palette now drives **three scopes** (`command`, `pane`, `workspace`) through one `SearchModel`, using `with_scope` to derive siblings. Per-scope history, per-scope frecency and per-scope `record_run` all work. So `SearchModel`'s scope design is now demonstrated, not just designed.
- **The two assumptions the task predicted would break did NOT break**, but one bent:
  - *"`rank` assumes a flat, indexable list"* — still true, and it needed handling. `results()` now filters to the active mode, ranks the filtered subset, then **maps `Ranked.index` back into the full `commands` list**, because the row children, the mark signals and the measured heights are all keyed by position. Any second consumer with a filtered view will hit exactly this. Consider whether `rank` should return the caller's own key rather than an index.
  - *"`handle` assumes the widget owns a single query string"* — held, but the palette now passes the **effective** query (sigil stripped) rather than the raw field, and re-attaches the sigil on recall. A picker that owns its field must decide whether that transform belongs to it or to its specialization.
- **But every caller still lives inside `command_palette.rs`.** Panes and workspaces became *modes of one widget*, not separate mounts. So the extraction still lacks a genuinely external consumer. **Do not treat T393 as having supplied the second caller** — it supplied a harder single caller. The first real external consumer should be chosen deliberately (a sidebar filter is the obvious one, since it is not an overlay and would force the panel question below).

## Decisions — settled 2026-08-04, do not re-open without reason

These were the task's three "open questions". Answered:

| Question | Answer |
|---|---|
| Does the picker own its query field? | **Yes.** `handle` already assumes it, and a caller driving the field from outside is the hand-driven-widget defect. A caller filtering from elsewhere pushes text in instead. |
| Does it own the overlay panel? | **No — this is the important one.** The picker is a plain **in-flow** widget (query line over a filtered list) that mounts anywhere. `CommandPalette` keeps the overlay, `TOP_FRAC` / `BOTTOM_FRAC` / `panel_metrics` and the shift-into-panel placement. Those are palette policy, not picker policy, and a sidebar filter is not an overlay. |
| Preview pane / multi-select? | **Not in the first cut**, but keep rows as real children and the selection readable as an index so neither is precluded. |

**Why the in-flow answer also simplifies the code:** the palette's manual machinery exists *because* it draws on the overlay layer — `place_rows` bakes absolute bounds into children and `visible_rows` measures against the viewport by hand. An in-flow picker gets real measured layout from the engine and needs none of that; the shifting stays behind in `CommandPalette`, where the overlay actually is.
