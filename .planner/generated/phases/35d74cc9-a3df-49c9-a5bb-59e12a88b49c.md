# What it is

A **handle placed between two containers** that lets the user drag the split between them —
vertically, horizontally, or either, according to the axis it sits on — **and the same split moved
from the keyboard** through the resize mode. Requested by the user 2026-07-28, after two containers
sharing a sidebar landed (F003/P011/T021).

# Where it goes and what it replaces

**A widget in `heca-grid-ui`, not app code.** The app hand-rolls this for its dividers today:
`heca/src/mouse/resize.rs` (`mod resize` at `heca/src/mouse.rs:14`) tracks a divider drag,
`mouse.rs:30-42` gates DnD and focus-follow while one is in flight, and `resize::cursor_for`
(`mouse.rs:58`) picks the OS cursor for the divider under the pointer. It emits a **parameterized
resize action** through the registry rather than mutating state directly — the right shape, worth
keeping.

**Absorb, don't duplicate:** decide explicitly whether `mouse/resize.rs` becomes a thin caller of the
widget or is deleted. Leaving both is the failure this task exists to avoid. `RegionState.size`
(`heca/src/chrome/state.rs`) plus the existing action already persist a sidebar's width — that
persistence model is the precedent to follow.

# What it must sit between

- **`VStack` / `HStack`** — a handle adjusts two siblings on the stack's axis.
- **A region's container stack** — `build_region_content` (`heca/src/chrome/mod.rs`) stacks containers
  and interleaves a `Separator`; a handle is the draggable form of that rule.
- Check what else genuinely applies: `Grid` (tracks, not siblings — a different problem),

# ⌨️ The resize mode — ✅ DECIDED BY THE USER 2026-07-28

The mode **already exists** and is config-defined, not an `InputMode` variant (an earlier note in this
task claimed there was no resize mode — wrong, and that is why: looking at the enum misses it):

```toml
# keybindings.default.toml:329 — prefix+r → sticky resize mode
[[keys.mode]]
name = "resize"
trigger = "prefix+r"
sticky = true                                   # stays until Esc
[[keys.mode.bindings]]
action = "resize"
keys = "h"
args = { target = "column", axis = "x", amount = "-50" }
```

A mode is a **sub-keymap**: while active its bindings apply instead of the normal ones. Built-ins are
`resize`, `sidebar`, `selection` (`:291`), and the blocks work in `config.toml` too — both files merge
before being read.

The decisions:

1. **It ships as a default app keybinding and stays customizable.** `prefix+r` is the shipped default;
   every binding inside the mode stays overridable in `config.toml`. The **container bindings are
   defaults too** — not something a user must add to get the feature.
2. **Any resizable area, both axes.** Not columns and panes only: a container, a region, two siblings
   of a stack — anything the handle can sit between. `ResizeTarget` (`heca/src/input.rs:18`, today
   `Column | Pane`, `EnumArg::VALUES = ["column", "col", "pane"]`) grows variants; `axis` already
   covers x and y through `ResizeAxis`. Vertical **and** horizontal for every target that has both.
3. **The keybinding file declares a FIXED amount; the proportion is worked out internally, per
   target.** The config keeps writing plain numbers exactly as it does now (`"-50"`, `"40"`) — that unit
   does **not** change, so **no config migrates and nothing a user has written breaks**. What changes
   is inside: the handler converts that fixed step into a **proportional** change for the target it was
   given, and what gets stored is the proportion. So a resize behaves the same on a small window and a
   large one, and a container's split survives a window resize because it moved shares (`flex_grow`,
   F003/P011/T021) rather than pixels.
   - One conversion, in one place, taking the target + its current extent + the fixed amount. The drag
     and the key must both go through it; two conversions will drift.
   - The knowledge of what a step means for a given target lives with the target, which is why this is
     "per target" and not a constant.
4. **A binding may pass its own amount, or leave it out for the default.** `amount` becomes an
   **optional** argument with a documented default, so the shipped bindings stay terse and a user who
   wants coarser steps writes a number. Side effect worth knowing: with no required args left, `resize`
   becomes legal as a *bare* binding too — the rule that blocked that was about required arguments
   (F003/P010/T006).

Other resize actions for reference: `resize_to` (absolute, `actions.rs:1832`), `resize_increase` /
`resize_decrease` (bare, `prefix+=` / `prefix+-`, **column-specific**), `resize_column_by` /
`resize_pane_height_by` (`:2000`, `:2012`). Ask whether they route through the same conversion, and if
not, say why in their descriptors.

# What a drag changes

A drag moves the **shares** of its two neighbours, never px sizes — through the same conversion the
keyboard uses. Work out:

- how a pixel delta becomes a change in two grow factors (the pair's sum is the invariant);
- the floor: an area must not be draggable or keyable to zero — a minimum, and whether it snaps shut;
- where it persists: per **placement**, keyed by container id in `SharedChromeState`, like the scroll
  offsets, so it outlives a tree rebuild and two placements resize independently.
