# Action Interaction Architecture — confirmation dichiarativa + response buttons

## 1. OBIETTIVO
Ogni azione dichiara **COME DATO** se ha bisogno di un prompt (conferma / scelta) e quali response button + outcome. Un solo gate centrale al chokepoint di dispatch legge la dichiarazione e pilota `OverlayHost::open_modal`. Built-in e plugin dichiarano allo STESSO modo. Il call-site non re-implementa mai la conferma: la guardia sta sull'**azione**, non sul chiamante.
Esempi: Close/Delete → conferma sì/no (2 bottoni, danger).

## 2. DECISIONI LOCKED (2026-07-07)
1. **`Outcome::Callback` nativo incluso SUBITO**, native-only, documentato meticolosamente (§6).
2. **Registry runtime ORA** (sostituisce il catalogo `const ALL`).
3. **Config: tabella generica `[confirm]`** keyed per nome azione (`[confirm].<name> = bool`), così anche un'azione di plugin è confermabile senza codice nuovo.
4. **`ConfirmSpec` è un tipo DATI puro** (serializzabile, plugin/RPC-safe, disaccoppiato da chrome/overlay). Il gate converte `ConfirmSpec → ModalSpec` all'apertura.
5. Il prompt riusa `ViewNode`; gli outcome dichiarativi riusano l'`Intent` (action name + args).

## 3. IL MODELLO (dati puri)
Vive in un layer basso che sia `heca` sia i plugin possono dipendere (candidati: un crate `heca-actions` oppure `heca-config` — da decidere in Fase A). Tutto `serde`-serializzabile **tranne** il `Callback` nativo, opaco attraverso WASM/RPC.
```
ActionMeta {
    name: String,                 // identità di config ("close", "delete_column", id di plugin)
    label: String,
    description: String,
    category: ActionCategory,
    default_binding: String,
    icon: Option<Glyph>,          // nome del Glyph attraverso il confine
    confirm: Option<ConfirmSpec>, // la dichiarazione di interazione
}
ConfirmSpec {
    prompt: ConfirmBody,          // Message(String) | View(ViewNode) — default: messaggio su una riga
    buttons: Vec<ResponseButton>, // 2, 3, N
    default_button: usize,        // focus iniziale (scelta SICURA, es. Cancel)
    config_name: String,          // chiave sotto [confirm]; override on/off dell'utente
    default_enabled: bool,        // valore quando [confirm].<config_name> è assente
}
ResponseButton {
    id: String,                   // torna in ModalResult::Action { id }
    label: String,
    role: ButtonRole,             // Default | Cancel | Danger  (focus/tinta/mappatura Esc)
    outcome: Outcome,
}
Outcome =
    Proceed                                     // esegue l'azione ORIGINALE gated ("sì, fallo")
  | Cancel                                      // niente
  | Dispatch { action: String, args: PropMap }  // dispatcha un'altra azione per nome (dichiarativo)
  | Callback(ActionCallback)                    // SOLO NATIVO (§6); opaco attraverso WASM/RPC
```
- `ButtonRole::Cancel` = il bottone su cui mappano Esc/scrim; `Danger` = tinta distruttiva; `Default` = la scelta sicura inizialmente focalizzata.
- `ActionCallback = Rc<dyn Fn(&mut AppState, &ActionRegistry)>` (handle nativo; NON serde).

## 4. ARCHITETTURA
### 4.1 ActionRegistry runtime (decisione 2a)
Unificare lo split odierno (`handlers: HashMap<Discriminant, fn>` + descriptor `static ALL`) in **UN SOLO registry runtime**:
```
ActionEntry { meta: ActionMeta, dispatch: Dispatch }
Dispatch =
    Native(ActionHandler)   // fn(&mut AppState, &WmAction) — built-in
  | Declarative             // name+args → instradata sul path Intent/ViewNode (plugin)
```
- **Keying**: i built-in mantengono la chiave `Discriminant<WmAction>` per dispatch + lookup del confirm (le varianti parametrizzate condividono il discriminante). Un indice **name → entry** preserva `icon/label/find/by_category/count`. Le azioni di plugin non hanno variante `WmAction` → chiave per **nome**, dispatch sul path dichiarativo esistente (`dispatch_view_intent`).
- **Popolamento**: i built-in si registrano **allo startup** (i dati escono da `const ALL` e vanno in `register_builtins()` — stessi valori, ora runtime). I plugin si registrano al load via host API.
- **Back-compat**: `icon/label/find/by_category/count` continuano a funzionare (ora leggono la mappa runtime). Il catalogo metadata oggi `#[expect(dead_code)]` diventa VIVO (command palette + introspezione RPC).
- **Confirm lookup**: `registry.confirm_spec(action) -> Option<&ConfirmSpec>` per discriminante/nome.
> NB (nome↔variante): l'azione di chiusura pane (`ClosePane` + `ClosePaneById`) mappa sullo STESSO `ConfirmSpec` sotto la chiave `delete_pane` (distinta dal nome descrittore `close`), così entrambi i dispatch confermano identicamente.

### 4.2 Il gate generico
`maybe_confirm` data-driven al posto di `maybe_confirm_destructive`:
```
fn maybe_confirm(state, registry, action) -> bool {
    let Some(spec) = registry.confirm_spec(action) else { return false };
    if !confirm_enabled(&state.config, &spec.config_name, spec.default_enabled) { return false }
    let resolved = resolve_target(state, action);   // es. ClosePane → ClosePaneById{focused}
    let modal = build_modal_spec(spec, state);      // ConfirmSpec → ModalSpec
    open_modal(state, modal, move |state, registry, result| {
        run_outcome(state, registry, spec, &resolved, result);
    });
    true
}
```
Sta nel ramo `Allow(ActivateAction(act))` di `dispatch_intent` (dov'è il gate attuale): `if !maybe_confirm(...) { registry.execute(&act, state); }`.
- **`resolve_target`**: fissa l'azione concreta al momento del prompt (oggi serve solo a `ClosePane`→`ClosePaneById{focused}`; ogni altra risolve a se stessa). Mappa piccola ed esplicita, NON logica per-call-site.
- **Loop-safety**: `Outcome::Proceed` esegue l'azione risolta via **`registry.execute(&resolved, state)`**, che chiama l'handler grezzo — il gate vive SOLO in `dispatch_intent`, quindi `registry.execute` non ci rientra mai. (Generalizza il vecchio `run_destructive_now`.) Elimina il bisogno di un flag `confirmed`.

### 4.3 Conversione ConfirmSpec → ModalSpec (tiene puliti i layer)
Il gate (layer chrome di `heca`) converte il dato puro in `ModalSpec`: `prompt → body ViewNode`; ogni `ResponseButton{id,label,role}` → `ModalAction{id,label,danger = role==Danger}`; `default_button`/ruolo `Cancel` → focus iniziale del Dialog + mappatura del dismiss. `open_modal` costruisce già `Button` reali, hintabili, con tooltip dall'id (il path centralizzato).

### 4.4 run_outcome
Su `ModalResult::Action{id}` trova il `ResponseButton` per id ed esegue il suo `Outcome`:
- `Proceed` → `registry.execute(&resolved, state)`;
- `Cancel` / `Dismissed` → niente (Esc/scrim mappano sul bottone con ruolo `Cancel`);
- `Dispatch{action,args}` → `dispatch_action` (rientra normalmente nel gate per la NUOVA azione);
- `Callback(cb)` → `cb(state, registry)`.

### 4.5 Config (decisione B)
- Nuova tabella `[confirm]`: `delete_pane = true`, `delete_column = true`, `delete_workspace = true`, `<plugin_action> = false`, … keyed per `ConfirmSpec.config_name`. Assente → `default_enabled`.
- **Migrare** `confirm_close_pane` / `confirm_delete_column` / `confirm_delete_workspace` da `[settings]` a `[confirm]`. Documentare lo spostamento; back-compat delle vecchie chiavi da decidere in Fase B.
- `config.default.toml` guadagna la sezione `[confirm]` con tutte le azioni confermabili (regola cardinale: ogni setting sta nel file di default).

### 4.6 API di registrazione (nativa + plugin)
- **Nativo**: una sola chiamata dichiara dispatch + metadata + interazione:
```
registry.register(ActionSpec {
    action: WmAction::ClosePaneById { .. },   // discriminante → handler
    handler: handle_close_pane_by_id,
    meta: ActionMeta { name: "close", label: "Close Pane", icon: Some(XSquare), ..,
        confirm: Some(ConfirmSpec {
            prompt: Message("Close pane?".into()),
            buttons: vec![ ResponseButton::cancel("cancel", "Cancel"),
                           ResponseButton::new("confirm", "Close", Danger, Outcome::Proceed) ],
            default_button: 0, config_name: "close".into(), default_enabled: true,
        }),
    },
});
```
  I callback nativi sono disponibili (`Outcome::Callback`) per logica interna all'app.
- **Plugin (WASM)**: dichiara azione + `ConfirmSpec` come **dati serializzati**; outcome limitati a `Proceed / Cancel / Dispatch`. Un adapter host first-party la registra come azione **Declarative** (name-based, dispatchata sul path `Intent`). I plugin **NON possono** usare `Callback`.

## 5. `Outcome::Callback` — documentazione meticolosa (decisione 1)
**È una via di fuga SOLO NATIVA. Va documentata in codice + AGENTS.md + docs:**
- **Firma**: `Rc<dyn Fn(&mut AppState, &ActionRegistry)>`. Gira una volta sola, quando il suo bottone viene scelto.
- **Native-only per costruzione**: una closure non è `serde`-serializzabile e non attraversa il confine WASM/RPC. **I plugin non devono usarla**: il builder plugin-facing non la espone. Quando i metadata di un'azione vengono serializzati per RPC/introspezione, un outcome `Callback` è reso **opaco** (es. `{"outcome":"native"}`) — MAI silenziosamente droppato.
- **Quando usarlo vs `Dispatch`**: preferire `Dispatch{action}` (portabile, testabile, guidabile da RPC). Usare `Callback` SOLO quando la logica non può genuinamente essere un'azione con un nome (raro). Se stai per usare `Callback`, chiediti prima se una piccola azione nativa + `Dispatch` non sia più pulita.
- **Nessun re-routing di policy**: come la completion della conferma, un `Callback` gira DOPO che l'utente ha già scelto — esegue direttamente, non rientra nella interaction policy. Documentare che NON va usato per contrabbandare lavoro distruttivo non-gated (per quello si compone `Dispatch`/`Proceed`).
- **Lifetime/capture**: lo stato catturato dev'essere owned/`'static` (`Rc`), coerentemente con le completion di `open_modal`.
- **Test**: un unit test che un outcome `Callback` parta ESATTAMENTE una volta sul suo bottone e NON su cancel/dismiss.
