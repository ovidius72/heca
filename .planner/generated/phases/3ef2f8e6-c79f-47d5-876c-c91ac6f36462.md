# 3ef2f8e6-c79f-47d5-876c-c91ac6f36462 — P079 — gridui-08: Drag a container between chrome regions — DnD hooks + the plugin escape hatch

**Status:** 📋 `planned`
**Created:** 2026-07-26T08:37:59.875Z
**Updated:** 2026-08-06T15:34:50.806Z

The drag framework ships but only the left sidebar is a drag surface. Regions and DockFrame have no hooks, so a container cannot be moved between regions.

Added 2026-07-26 after auditing docs/chrome-and-ui.md and docs/chrome-and-ui.md against
the planner. This was designed in both files (grid-ui plan §3, the old "G6") and tracked NOWHERE.

═══ WHAT EXISTS ═══
The drag-and-drop framework SHIPPED and the app uses it: `heca-grid-ui/src/drag/` holds
`context.rs`, `item.rs`, `math.rs`, `resolve.rs`, `state.rs`.
- `DragSurfaceId` — a closed enum of drag surfaces.
- `DragItem { surface, id: DragItemId, kind: DragItemKind, pane_id }`.
- `SurfaceDragState { phase, hover_item, source_item, ghost_label }`, phase Idle → Starting → Dragging.
- `DragContext { active_surface, surfaces }` — one mouse means one active surface, but EVERY
  surface updates `hover_item`, so several drop targets can highlight at once. That is already the
  cross-region model; nothing new is needed in the framework itself.
- Dispatch and meaning are app-side (`heca/src/mouse/`), and every drop goes through the action
  registry.

═══ WHAT IS MISSING (verified in code 2026-07-26) ═══
- `DragSurfaceId` has exactly ONE variant: `LeftSidebar`. Grep across heca/src and
  heca-grid-ui/src finds no other. There is no right sidebar, no top/bottom bar, no region surface.
- `DockFrame` (heca-grid-ui/src/widgets/dock_frame.rs) has NO drag handle. The widget was specified
  with one ("title bar + collapse toggle + drag handle + header-controls slot") and it was never
  built.
- `ChromeRegion` sets no `hover_item`, so nothing can be dropped into it.
⇒ A container cannot be moved from one region to another by any means. The plan calls this a
core capability of pluggable chrome (chrome plan §2.9: moving a container between regions is a
host concern).

═══ WORK ═══
1. Add region drag surfaces additively (right sidebar, top bar, bottom bar).
2. Give `DockFrame` a drag handle that drives `SurfaceDragState` carrying a `DragItem`.
3. Make `ChromeRegion` and the gaps between docks receive: set `hover_item` when they can accept.
4. Render the ghost and the insertion line in the existing overlay layer.
5. App side: on drop, DISPATCH AN ACTION (`chrome.dock.move_to_region`, `chrome.dock.reorder_before`)
   through the registry. Never mutate directly.
6. THE SAME MOVE MUST BE REACHABLE BY KEYBOARD AND RPC — grid-ui plan P2, and AGENTS.md's
   input-parity rule. Drag is only the mouse surface for an action that must already exist. Build
   the action first, then the drag on top of it.

═══ THE PLUGIN ESCAPE HATCH (folded in from the same audit) ═══
`DragSurfaceId` and `DragItemKind` are closed enums, so a plugin cannot add one at runtime. The
agreed fix, recorded in grid-ui plan §3 and never tracked: ONE open variant each —
`DragItemKind::Custom(u32)` so non-workspace containers do not inherit window-manager nouns, and
`DragSurfaceId::Plugin(PluginSurfaceId)` funnelling dynamic surfaces through runtime dispatch while
built-ins keep the fast path. Not needed until plugins exist (F003/P001), but it belongs to this
phase because it is the same code and the same decision.

═══ THE RULE THAT MUST NOT BE BROKEN ═══
Extend the framework ADDITIVELY. Add variants and files. NEVER modify or re-type an existing drag
type (keep `(f32,f32)` as-is, do not swap it for `Rectangle`) and NEVER remove or rename a variant.
The app constructs these types and matches on them exhaustively — adding a variant changes no
behaviour and the compiler simply asks for new match arms, which is the point of the closed enum.

═══ VERIFICATION ═══
Dragging is visible, interactive behaviour. Green tests are not verification: build it and have the
user drag a container between two regions, and confirm the same move works from the keyboard.

# Why the old plan is dead

Adding variants makes the enum longer, not open. A closed enum of **regions** cannot describe a
drag inside a pane, inside an overlay, or inside a plugin's own subtree — and a plugin cannot add a
variant at runtime, which is what T330 was invented to paper over.

The reason it looked like a region problem is historical: the app's drag predates the framework
having any, so it was built where the mouse events were, one handler per surface.

# What exists now (F004/P084/T394, 2026-08-06)

- `Base::drag_source` / `Base::drop_target` — universal, on **every** widget, declared with
  `DragExt::draggable(id)` / `.drop_target(id)`.
- The router emits `DragStart` / `Drag` / `DragEnd` / `DragEnter` / `DragOver` / `DragLeave` /
  `Drop` to whichever widget is under the pointer, with `DragEvent::side` (Before/Onto/After)
  already computed. It hit-tests **every mounted tree**, so this works in a pane, an overlay,
  either sidebar or a plugin subtree today — nothing in it names a region.
- 8 px threshold, capture, and the end-of-gesture guarantee (`DragEnd` always fires) are the
  framework's.

# The work

1. **Delete the region layer**: `DragSurfaceId`, `DragContext`, `SurfaceDragState`,
   `heca/src/mouse/drag.rs`, `heca/src/mouse/surface_left.rs`, `heca/src/mouse/target.rs`, the drag
   half of `heca/src/mouse/release.rs`, and `sidebar_bounds`. Also the early return at
   `heca/src/mouse.rs` (`if point_in_right_sidebar(...) { ...; return None; }`) — the reason the
   right sidebar could not drag at all while the left one could, with identical widgets.
2. **The ghost and the insertion line move INTO `heca-grid-ui`.** The app paints both per surface
   today; they are one drag visual for every drag, and a plugin cannot draw them. This is the only
   part that moves rather than being deleted.
3. **The workspace drop logic moves to `heca/src/providers/workspaces/`** — beside the rows it is
   about. The container declares its rows draggable, answers `Drop` with an action through the
   registry, and nothing named `surface_left.rs` exists.
4. `DragItemKind` — decide whether it survives at all; the payload is the host's, keyed by the
   opaque `DragItemId` the container itself registered.
5. T330 (plugin open variants) **dissolves** if this lands: there is no enum left to open.

Status: 📋 `planned`

# What exists

- **App-side, per surface.** `SurfaceDragState.ghost_label: Option<DragLabel>` carries the chip's
  text and a hand-maintained `x`/`y` (`heca/src/mouse/drag.rs` sets it on threshold and moves it on
  every cursor step); `heca/src/app/render.rs` paints it. The insertion indicator is drawn from
  `DropHit { bounds, side }` at the app's own call sites.
- `DragLabel` and `DropSide`/`DropHit` already live in `heca-grid-ui/src/drag/`, so the *types* are
  in the right crate; only the drawing and the position bookkeeping are not.
- Since F004/P084/T394 the framework owns the gesture: `DragStart`/`Drag`/`DragEnd` on the source,
  `DragEnter`/`DragOver`/`DragLeave`/`Drop` on the target, with `DragEvent::side` computed for it.

# Why it moves

A plugin's widget can be draggable (it declares one id) but **cannot draw the drag**: the ghost and
the insertion line are painted by app code that knows which sidebar it is in. One drag should look
like one drag wherever it happens, and the widget author should write none of it — the same bargain
as `Base::hovered` and the focus ring.

# The work

1. A framework-owned overlay for the in-flight drag: the ghost follows the pointer (the router
   already has every move), and the insertion line draws against the current drop target's bounds
   and `side`. Both painted through `PaintCx::with_overlay`, so they composite above everything, and
   both read every colour/radius/width from the `Theme` — no magic numbers, per the widget rules.
2. What the ghost *shows* is the widget's to say, not the framework's: reuse
   `Component::text_summary()` (the accessible-name path) for the default, with an explicit
   override for a source that wants something else. **Do not** re-introduce a host-supplied string
   that the app has to keep in step with the row it came from
   (`heca/src/mouse/drag.rs::drag_ghost_label` re-derives it from the session on every drag start).
3. Delete `SurfaceDragState.ghost_label` and its two writers, and the ghost paint in
   `heca/src/app/render.rs`.
4. Showcase: a drag demo that is not a sidebar — two lists in a panel — so the "works anywhere"
   claim is visible and not just asserted.
5. Docs: `docs/widgets.md` drag section + rustdoc, per the mandatory both-audiences rule.

# Edge cases

- A drag that ends over nothing still clears the ghost (`DragEnd` always fires — the framework
  guarantees it).
- The pointer leaving the window mid-drag (`Event::pointer_cancelled()`) clears both visuals.
- A source removed mid-drag (a rebuild during the gesture) must not leave a ghost painted.
