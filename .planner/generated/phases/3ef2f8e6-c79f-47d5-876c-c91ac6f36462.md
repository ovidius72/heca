# 3ef2f8e6-c79f-47d5-876c-c91ac6f36462 — P009 — gridui-08: Drag a container between chrome regions — DnD hooks + the plugin escape hatch

**Status:** 📋 `planned`
**Created:** 2026-07-26T08:37:59.875Z
**Updated:** 2026-07-27T11:40:15.495Z

The drag framework ships but only the left sidebar is a drag surface. Regions and DockFrame have no hooks, so a container cannot be moved between regions.

Added 2026-07-26 after auditing docs/chrome-and-ui.md and docs/chrome-and-ui.md against
the planner. This was designed in both files (grid-ui plan §3, the old "G6") and tracked NOWHERE.

═══ WHAT EXISTS ═══
The drag-and-drop framework SHIPPED and the app uses it: `heca-grid-ui/src/drag/` holds
`context.rs`, `item.rs`, `math.rs`, `resolve.rs`, `state.rs`.
- `DragSurfaceId` — a closed enum of drag surfaces.
- `DragItem { surface, id: DragItemId, kind: DragItemKind, pane_id }`.
- `SurfaceDragState { phase, hover_item, source_item, ghost_label }`, phase Idle → Starting → Dragging.
- `DragContext { active_surface, surfaces }` — one mouse means one active surface, but EVERY
  surface updates `hover_item`, so several drop targets can highlight at once. That is already the
  cross-region model; nothing new is needed in the framework itself.
- Dispatch and meaning are app-side (`heca/src/mouse/`), and every drop goes through the action
  registry.

═══ WHAT IS MISSING (verified in code 2026-07-26) ═══
- `DragSurfaceId` has exactly ONE variant: `LeftSidebar`. Grep across heca/src and
  heca-grid-ui/src finds no other. There is no right sidebar, no top/bottom bar, no region surface.
- `DockFrame` (heca-grid-ui/src/widgets/dock_frame.rs) has NO drag handle. The widget was specified
  with one ("title bar + collapse toggle + drag handle + header-controls slot") and it was never
  built.
- `ChromeRegion` sets no `hover_item`, so nothing can be dropped into it.
⇒ A container cannot be moved from one region to another by any means. The plan calls this a
core capability of pluggable chrome (chrome plan §2.9: moving a container between regions is a
host concern).

═══ WORK ═══
1. Add region drag surfaces additively (right sidebar, top bar, bottom bar).
2. Give `DockFrame` a drag handle that drives `SurfaceDragState` carrying a `DragItem`.
3. Make `ChromeRegion` and the gaps between docks receive: set `hover_item` when they can accept.
4. Render the ghost and the insertion line in the existing overlay layer.
5. App side: on drop, DISPATCH AN ACTION (`chrome.dock.move_to_region`, `chrome.dock.reorder_before`)
   through the registry. Never mutate directly.
6. THE SAME MOVE MUST BE REACHABLE BY KEYBOARD AND RPC — grid-ui plan P2, and AGENTS.md's
   input-parity rule. Drag is only the mouse surface for an action that must already exist. Build
   the action first, then the drag on top of it.

═══ THE PLUGIN ESCAPE HATCH (folded in from the same audit) ═══
`DragSurfaceId` and `DragItemKind` are closed enums, so a plugin cannot add one at runtime. The
agreed fix, recorded in grid-ui plan §3 and never tracked: ONE open variant each —
`DragItemKind::Custom(u32)` so non-workspace containers do not inherit window-manager nouns, and
`DragSurfaceId::Plugin(PluginSurfaceId)` funnelling dynamic surfaces through runtime dispatch while
built-ins keep the fast path. Not needed until plugins exist (F003/P001), but it belongs to this
phase because it is the same code and the same decision.

═══ THE RULE THAT MUST NOT BE BROKEN ═══
Extend the framework ADDITIVELY. Add variants and files. NEVER modify or re-type an existing drag
type (keep `(f32,f32)` as-is, do not swap it for `Rectangle`) and NEVER remove or rename a variant.
The app constructs these types and matches on them exhaustively — adding a variant changes no
behaviour and the compiler simply asks for new match arms, which is the point of the closed enum.

═══ VERIFICATION ═══
Dragging is visible, interactive behaviour. Green tests are not verification: build it and have the
user drag a container between two regions, and confirm the same move works from the keyboard.
