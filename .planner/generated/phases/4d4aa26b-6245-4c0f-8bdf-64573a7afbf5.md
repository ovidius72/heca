# 4d4aa26b-6245-4c0f-8bdf-64573a7afbf5 — P017 — plugin-ui-gaps: Close the declarative model's capability gaps + make the translator self-maintaining

**Status:** 🚧 `in-progress`
**Created:** 2026-07-25T19:12:29.404Z
**Updated:** 2026-07-27T08:31:41.422Z

Widgets can do things the ViewNode model cannot say. Close the gaps and remove the hand-written prop list in realize so they cannot come back.

═══ WHY THIS PHASE EXISTS ═══

Split out of F003/P011/T006 (typed builder SDK) on 2026-07-25, after research the user asked for.
T006 was going to build a typed builder on top of the CURRENT prop vocabulary. That would have
frozen a set of holes into a compile-checked API — the builder would make it *impossible* to write
a padding, which is worse than today's silent ignore. This phase corrects the model first; T006
then builds the typed builders on top of a corrected model.

═══ THE CORE DEFECT ═══

`heca/src/chrome/realize.rs` hand-writes a reader for every property, per widget. When someone adds
a builder to a widget in `heca-grid-ui`, nothing forces the matching reader to be added. It has
been forgotten repeatedly. The capability exists in the widget and is unreachable from a
`ViewNode` — silently, with no warning, no log, no test failure.

Verified by listing every property-name string literal `realize.rs` actually reads and diffing it
against the widgets' real builder APIs (2026-07-25, on main @ d698916).

═══ THE FULL GAP LIST (each verified in code) ═══

REAL GAPS — the widget can do it, a ViewNode cannot say it:

1. `padding` (and `justify`, `width`, `height`, `direction`, margins, spacing tokens).
   `realize_flex` (realize.rs:440-459) reads ONLY `gap` and `align`. Everything else on `Style`
   is unreachable. NOTE: the original design doc writes `Column::new().gap(8).padding(12)` at
   docs/chrome-and-ui.md:340 — the very line introducing the builder SDK. Padding was
   intended from day one and simply never got a property. This is an oversight, not illustration.

2. `Input` placeholder. `Input::placeholder()` exists (heca-grid-ui/src/widgets/input.rs:122) and
   the showcase uses it twice, including the command palette (showcase.rs:264, 698). The realize
   arm (realize.rs:163-176) reads only value + `name` + change intent.

3. `Scroll` axes. `ScrollRegion` supports both axes: `new()` (vertical), `horizontal()`, `both()`,
   `axes(ScrollAxes)` (scroll_region.rs:186-247). The showcase depends on it — its entire root is
   `ScrollRegion::new().both()` (showcase.rs:1897) plus a `.both()` grid demo (showcase.rs:1401).
   realize maps `WidgetKind::Scroll` to a bare `ScrollRegion::new()` (realize.rs:133), so anything
   declarative is vertical forever.

4. The clickable `Row` widget is unreachable, AND ITS NAME COLLIDES.
   `heca-grid-ui/src/widgets/row.rs` is a focusable, clickable container — hover tint, active
   marker with `ActiveMarker`, press flash, focus ring, `on_activate` (mouse + Enter/Space),
   described as `Item`'s open cousin for rich clickable dock rows.
   `WidgetKind::Row` does NOT map to it. It maps to `Flex::row()` — a plain horizontal box with no
   interactivity (realize.rs:124). Two different things share one name, and the interactive one has
   no declarative spelling at all. docs/chrome-and-ui.md example 2 writes exactly this
   (`Row::new().gap(12)...on_press(intent(...))`) against a kind that cannot do it.

5. `Separator` has no `WidgetKind`. The widget exists (heca-grid-ui/src/widgets/separator.rs —
   `horizontal()`, `vertical()`, `length()`); the vocabulary has no entry. docs/chrome-and-ui.md
   example 2 uses `Separator::new()`.

6. `PropValue::Color` is DEAD. Declared in the model (view.rs:201-202, documented as "#rrggbb /
   #rrggbbaa, or a theme color token name") and read by NOTHING — grep of realize.rs finds only
   `glyph_prop`, never a colour reader. Either wire it to theme token names or remove it.

DOC ERRORS — the docs promise things that have no native equivalent either:

7. `Panel::new().title("Hello")` (docs/chrome-and-ui.md example 1, README). There is no Panel widget:
   `WidgetKind::Panel` realizes to a plain `Surface` (realize.rs:129-131, comment says so), and
   `Surface` has no title (surface.rs — only `new`/`row`/`column`). `Card` is the titled one.

8. `Label::new(..).variant(Variant::Muted)` (docs/chrome-and-ui.md example 2). `Label` has no variant
   natively (label.rs — align/color/bold/italic/underline/strikethrough/font_size/font_scale), and
   `ViewVariant` is button-shaped: Primary, Secondary, Destructive, Outline, Ghost, Link — no
   Muted (view.rs:169-176). Muted text is a COLOUR, which ties this to gap 6.

═══ THE PLUMBING DECISION (user-driven, 2026-07-25) ═══

The user rejected "just add the missing readers": adding a reader per property means the next
property is forgotten too. They also rejected a single `apply_style_props()` function, correctly
noting it STILL needs a line per new field — it moves the drift, it does not remove it.

Agreed direction: the property list must BE A TYPE that a generator reads, never a function body
someone remembers to update. That splits by layer:

LAYER A — layout settings. They do not live on the widgets. They all live on one `Style` struct
(heca-grid-ui/src/style.rs:211) hanging off `Base`, which every widget embeds. Make `Style`
(the layout part) able to read and write itself, then merge a node's properties into it. Add a
field later and it works with zero code anywhere.
  PRECEDENT ALREADY IN THE CODE: `realize` (realize.rs:100-112) already applies `align_self` and
  `justify_self` generically for every kind, with the comment "read it once here rather than in
  each arm". The right pattern was started and not finished — that is exactly why `gap` works only
  inside `realize_flex` while `align_self` works everywhere.

LAYER B — settings that belong to one widget (placeholder, axes, checked, severity, value). These
are fields on individual widget structs; nothing generic reaches them. A small code generator over
the widgets' own builder methods writes the translation.

After both, realize.rs contains NO property-name list at all and cannot fall behind.

═══ BLOCKER ON LAYER A: `Style` MIXES LAYOUT WITH VISUALS ═══

A whole-struct merge would hand plugins raw colours. `Style` holds `fill`, `border`, `glow`,
`accent`, `fg`, `radius` (style.rs:289-295) in the same struct as `padding` and `width`.
"Styling is not a property — the plugin picks intent (danger/accent/size), the host resolves the
actual pixels from the Theme" is rule C of docs/chrome-and-ui.md §2.6.1 and is repeated
in AGENTS.md's SETTLED table ("Is styling a prop? NO").
⇒ The layout/visual boundary must become a TYPE, not a reviewer's memory. See T1.

Also note: `heca-grid-ui` currently has NO serialization dependency at all — its dependencies are
heca-core, heca-theme, floem_reactive, taffy (heca-grid-ui/Cargo.toml:8-12), and `Style` derives
only `Debug, Clone, Copy, PartialEq` (style.rs:210). Layer A adds that, plus derives down through
`Length`, `Align`, `Justify`, `Direction`, `Spacing`, `WidgetSize`, `GridCell`.

═══ SETTLED CONSTRAINTS — DO NOT RE-OPEN (AGENTS.md:730-796) ═══

- `heca (app) ──depends on──▶ heca-grid-ui (library)`. NEVER the reverse.
- `heca-grid-ui` must NOT own `ViewNode`, and `Button::new(ViewNode)` is impossible.
- `realize` is the ONE ViewNode→widget bridge, app-side.
- Behaviour crosses as an `Intent` (action id + args), never a callback.
- Styling is not a property; semantic variant/size/align + colour/glyph NAMES only.
- A widget whose state is a live host signal is HOST-ONLY (`ScrollBar`; also individual builders
  like `DockFrame::rail(..)`).
- Any code generator added for Layer B must keep `heca-grid-ui` free of `ViewNode`: the library
  may only gain a NEUTRAL scalar type, never the app's model.

### ✅ 1ea732ca-3582-44f4-be02-245375910948 — T003 — Generated translation for widget-specific settings + a drift test that fails on a missing one

Status: ✅ `done`

Layer B of the plumbing decision. Independent of T1/T2 (which handle layout) but shares their goal:
realize.rs must stop containing a hand-written list of property names.

CURRENT STATE
Settings that belong to ONE widget — placeholder, scroll axes, checked, on, severity, value,
selected, expanded, active, frameless, nav_selected, dismissible, action_text, body — are fields on
individual widget structs. Nothing generic reaches them, so `realize_kind`

literals. When a builder is added to a widget, nothing forces the arm to be updated. That is how
gaps 2 and 3 (placeholder, scroll axes) happened.

WORK
- Add a uniform setter to `heca-grid-ui`: a trait along the lines of
  `fn set_prop(&mut self, key: &str, value: PropInput) -> bool`, plus a small code generator that
  writes the implementation from the widget's own annotated builder methods.
