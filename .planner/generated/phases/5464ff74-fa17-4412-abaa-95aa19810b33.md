═══ WHAT SHIPPED ═══
`heca/src/chrome/layers.rs` exists with `LayerBand` (semantic z bands, no magic numbers),
`LayerKind::{Persistent, OnDemand}`, and `ShowLayer`/`HideLayer`/`ToggleLayer` actions.

═══ WHAT DID NOT — THE FILE SAYS SO ITSELF ═══
layers.rs:11 — "content only; the `ViewNode` content path (plugins) and paint/input wiring land
later." layers.rs:69 repeats it. There is no `LayerContent` enum: a layer holds a native tree, and
nothing can hand it a description.

═══ THE TARGET MODEL (from §9, verbatim intent) ═══
    enum LayerContent {
        Native(Box<dyn Component>),   // built in Rust (chrome, pane header)
        View(ViewNode),               // data- or plugin-described; the host realize()s it
    }
A `Layer` also carries: id, band, kind, `modal` (captures the context, suppressing everything
beneath while active), `visible`, and `parent` — an overlay opened FROM a layer is its CHILD, so it
sits above it. The occluder is read from the realized tree's laid-out bounds, NEVER hardcoded.

`LayerStack` on `AppState` is the single source of truth for layering: layers ordered by
(band, insertion) with parent nesting, plus `active: LayerId` — the active context.

═══ WHY IT MATTERS — TWO GAPS, ONE FIX ═══
1. OVERLAYS SHOW NO KEYHINT. A modal that draws its buttons manually has no child subtree, so
   `collect_hint_targets` finds nothing to hint. The project rule is KeyHint on every action, so
   those buttons must be REAL components carrying `.hint_target(...)`.
2. PLUGINS MUST BE ABLE TO ADD LAYERS — an exposé, a panel, a rich modal — without touching
   paint, input or hint machinery.
Both are the same fix: a layer whose content may be a `ViewNode`, realized by the host, where
every actionable node gets a hint target automatically.

═══ WORK ═══
- Add `LayerContent` with the `View(ViewNode)` arm; realize it through the one bridge
  (`heca/src/chrome/realize.rs`).
- Paint layers in stack order; route input to the active or modal layer. Today only hint
  visibility reads the stack.
- Keep `add_layer` returning a stable `LayerId` a plugin can hold.

═══ BUILD ON, DO NOT DUPLICATE ═══
`OverlayHost` is NOT a second stack — it is built ON this one. `open_modal` realizes the ViewNode
body plus its action buttons into a native tree, pushes it as a Modal-band layer, and resolves the
returned result when a button's intent fires. Its overlays ARE layers here. See
docs/chrome-and-ui.md Part II §4.

═══ THE INVARIANTS THAT MUST SURVIVE (§6 of the deleted file) ═══
- NO hardcoded z or levels anywhere. z is tree position; occluders come from real layout geometry.
  If you are typing a magic number for a layer or a region, stop.
- Buttons NEVER declare a layer. A button inherits its layer from the surface it is mounted in.
  Put it in a pane header and it is in the pane context; put it in a dialog and it is in that
  dialog's context. That is the whole rule.
- The active context is moved ONLY by context surfaces (exposé, modal) — never by zoom, scroll or
  provider selection, so the sidebar stays hintable while a pane is zoomed.
- Occlusion is decided by draw order plus geometry, not by the coarse level. "Same level" is not
  "same z" — two surfaces cannot share a tree position, so there are never ties.
- Overlays and modals are children of their opener, and exclusive when modal.
- ONE rule for visibility. If you find yourself special-casing a surface's hints, the surface is
  mis-modelled — fix the model, do not add a filter.

═══ MIGRATION ORDER (from §9, incremental, no big bang) ═══
1. ~~Introduce the stack, register the existing surfaces, hints read it~~ — DONE.
2. Convert the confirm dialog to a layer with hintable buttons → closes the overlay-KeyHint gap.
   Do it the conformant way: as an `OverlayHost::open_modal` with a ViewNode body and actions,
   not a bespoke modal.
3. `ShowLayer` on-demand layers → the first native exposé.
4. The ViewNode content path → plugins add layers.

═══ VERIFICATION ═══

verification: build it and have the USER confirm a modal's keycaps appear, and that a layer opened
from another sits above it.
