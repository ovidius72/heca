═══ THE TARGET MODEL (from §9, verbatim intent) ═══
    enum LayerContent {
        Native(Box<dyn Component>),   // built in Rust (chrome, pane header)
        View(ViewNode),               // data- or plugin-described; the host realize()s it
    }
A `Layer` also carries: id, band, kind, `modal` (captures the context, suppressing everything
beneath while active), `visible`, and `parent` — an overlay opened FROM a layer is its CHILD, so it
sits above it. The occluder is read from the realized tree's laid-out bounds, NEVER hardcoded.

`LayerStack` on `AppState` is the single source of truth for layering: layers ordered by
(band, insertion) with parent nesting, plus `active: LayerId` — the active context.

═══ WHY IT MATTERS — TWO GAPS, ONE FIX ═══
1. OVERLAYS SHOW NO KEYHINT. A modal that draws its buttons manually has no child subtree, so
   `collect_hint_targets` finds nothing to hint. The project rule is KeyHint on every action, so
   those buttons must be REAL components carrying `.hint_target(...)`.
2. PLUGINS MUST BE ABLE TO ADD LAYERS — an exposé, a panel, a rich modal — without touching
   paint, input or hint machinery.
Both are the same fix: a layer whose content may be a `ViewNode`, realized by the host, where
every actionable node gets a hint target automatically.

═══ WORK ═══
- Add `LayerContent` with the `View(ViewNode)` arm; realize it through the one bridge
  (`heca/src/chrome/realize.rs`).
- Paint layers in stack order; route input to the active or modal layer. Today only hint
  visibility reads the stack.
- Keep `add_layer` returning a stable `LayerId` a plugin can hold.

═══ BUILD ON, DO NOT DUPLICATE ═══
`OverlayHost` is NOT a second stack — it is built ON this one. `open_modal` realizes the ViewNode
body plus its action buttons into a native tree, pushes it as a Modal-band layer, and resolves the
returned result when a button's intent fires. Its overlays ARE layers here. See
docs/chrome-and-ui.md Part II §4.

═══ THE INVARIANTS THAT MUST SURVIVE (§6 of the deleted file) ═══
- NO hardcoded z or levels anywhere. z is tree position; occluders come from real layout geometry.
  If you are typing a magic number for a layer or a region, stop.
- Buttons NEVER declare a layer. A button inherits its layer from the surface it is mounted in.
  Put it in a pane header and it is in the pane context; put it in a dialog and it is in that
  dialog's context. That is the whole rule.
- The active context is moved ONLY by context surfaces (exposé, modal) — never by zoom, scroll or
  provider selection, so the sidebar stays hintable while a pane is zoomed.
- Occlusion is decided by draw order plus geometry, not by the coarse level. "Same level" is not
  "same z" — two surfaces cannot share a tree position, so there are never ties.
- Overlays and modals are children of their opener, and exclusive when modal.
- ONE rule for visibility. If you find yourself special-casing a surface's hints, the surface is
  mis-modelled — fix the model, do not add a filter.

## ✅ DECIDED 2026-08-04 — how a plugin updates a layer it already owns

The question arose from T339: `open_view_layer` realizes **once**, at open, so it was unclear whether the retained `ViewNode` is load-bearing. Four options were put to Antonio; he chose **signals — the plugin never resends the tree.**

**The mechanism is P085(F003)/T360** (`58SE7`, "A component's own signals: a per-mount value store a plugin can write"), which already specifies it: a `(mount, key) → Signal<PropValue>` map on `SharedChromeState`, and — its step 5 — a `ViewNode` that can **name a value key instead of a literal**, so the realized widget binds the signal and updates **in place** with no tree rebuild. Its own open question (the prop spelling: a `PropValue::Binding(String)` versus a `PropValue::Text("@key")` sigil) is still Antonio's to settle.

**Rejected, with reasons:**
- *Replace on update* (`update_view(id, node)` → re-realize and swap) — throws the retained tree away, so caret, selection, scroll, focus and `FormBindings` all die with it. **Do not add `update_view` to `LayerRegistry`**: it would be a second update channel that T360 would then have to kill.
- *Diff and reconcile* — preserves everything, but a reconciler has no precedent in this codebase and would be the largest thing in the plugin path. Not until something demands it.
- *Immutable layers in v1* — was the recommended stepping stone; Antonio chose to go to the signal model directly instead.

**Unaffected either way:** a theme reload can re-realize from the retained node. That is what the node on `LayerContent::View` earns today, independent of plugin updates.

## Consequence for this task

T327 needs a **native** exposé, which updates nothing, so nothing here is blocked by T360. Build `ShowLayer`/`HideLayer` against the registry's existing `show()`/`hide()` (`heca/src/chrome/layers.rs:172`, documented as "`ShowLayer` dispatches here") and do **not** invent an update path along the way.

## What shipped

- **`LayerContent`** with both arms: `Native(Box<dyn Component>)` and `View { node, realized }`. `DynamicLayer.root` became `content: LayerContent`, with `root()` / `root_mut()` accessors so every consumer is arm-agnostic.
- **`LayerRegistry::add_view(band, kind, modal, covers_content, node, realized)`** — the View-arm constructor, mirroring `add`.
- **`chrome::overlay::open_view_layer(state, band, kind, modal, covers_content, node)`** — the host entry point. Realizes through the **one** bridge (`super::realize` → `heca_view_realize::realize`) with the same boundary `build_modal_root` uses: a `ViewHintTargets` sink so the described tree's buttons are KeyHint-reachable, and an emitter that wraps the model's own `Intent` into `InteractionIntent::View` at the edge.

## Design decision — the View arm keeps BOTH the node and the realized tree

The task's literal signature was `View(ViewNode)`. It is `View { node, realized }` instead, for two reasons:

1. **A registry cannot realize.** `realize(node, theme, emit, hints, forms)` needs the theme, an intent emitter, the hint sink and the form bindings; `LayerRegistry` is plain data on `AppState` and holds none of them. So the caller realizes and hands both over — which is why `open_view_layer` exists at all.
2. **Keeping only the tree would throw the description away.** The node is the source of truth a theme reload or a plugin update re-realizes from; the tree is what the host lays out, paints and hint-walks. `LayerContent::node()` exposes it, and the test asserts it survives realization.

## The occluder invariant holds

Nothing is hardcoded and nothing was added: `active_hint_targets` (`heca/src/chrome/mod.rs:2182`) reads `layer.root().base().bounds`, so a View layer's occluder is its **realized tree's laid-out bounds** by construction — it goes through the same accessor as a native one.
