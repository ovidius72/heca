# 5de43f15-8304-4f64-870f-8514d534d5a5 — P085 — Components declare their actions; chrome focus is the mode

**Status:** 📋 `planned`
**Created:** 2026-07-28T12:21:31.986Z
**Updated:** 2026-07-28T12:32:34.023Z

A focused container receives the keyboard directly and runs actions IT declared — no generic verb set, no bespoke sidebar mode. Provider grows kind()/actions()/perform(); a row's nav_key is its one identity (cursor + right-click + drag); bindings live in [keys.<kind>], live only while focused. Retires InputMode::SidebarNav and the 11 sidebar_* built-ins.

# Why

F003/P011/T020 landed chrome focus (a container id, a pick, a focus ring) and it is **inert**: nothing
delivers keys to a focused container, so `prefix+Shift+e` focuses a dock and then you still need
`prefix+e` to do anything with it. Verdict from the user 2026-07-29: *"it has no value if I have to do
prefix+e to interact... it's only more keybindings."*

And the thing it would generalise — `InputMode::SidebarNav` — is not generalisable as written: every
verb in it is app code that knows the workspace tree. `handle_sidebar_up/down` drive
`state.sidebar_tree` (a workspace/column/pane projection, `heca/src/handlers.rs:1562+`) and
`handle_sidebar_right_nav` calls `handle_focus_pane` directly (`handlers.rs:1586`). A second container
inherits none of it.

# ✅ DECIDED BY THE USER 2026-07-29

**The rule the design hangs on: widgets answer gestures; components declare semantics.**

- Wheel, click, drag, hover, and keyboard **scrolling** are answered by the widgets a container
  composes. `ScrollRegion` already answers the eight `WidgetIntent::Scroll*` and *declines* the axis it
  cannot move (shipped `096f06e`). Nothing is declared for these — a container that nests a scroll area
  scrolls; one showing a single number declines.
- What only the component knows is **what its selection means**: rename *this*, delete *this*, restart
  *this*. That is what it declares.

**No generic verb set.** An inherited up/down/select/toggle vocabulary is dead weight for a container
showing one number — "a component knows exactly what it needs" (user). Conventional *ids* (`up`,
`down`, `activate`, `remove`, `add`) are encouraged so docks agree in practice, never enforced in code.

**Focus is the mode.** No `InputMode` variant for it: chrome focus already answers "where do the keys
go", and a mode beside it would be a second fact that can disagree (the defect `nav_selection` vs
`sidebar_tree.cursor` already paid for). Key routing, top to bottom, in every focus state:

1. prefix key → prefix mode → mode triggers → the global `normal` map → **falls through to the focused
   component's layer** → drop
2. global direct bindings (`Alt+Enter`, `Shift+PageUp`, …)
3. if a component holds chrome focus → its `[keys.<kind>]` layer → **swallow** if unbound
4. otherwise → forward to the focused pane's backend

`state.focused_pane` is NOT cleared by chrome focus — only the keyboard is redirected, so `prefix+Enter`
still splits the pane you last worked in, exactly as sidebar mode behaves today.

**Components declare, mostly bind.** A component's keymap maps keys to **any** action id — an existing
built-in (`next_pane`, `zoom_column`, `spawn_command` with args) or one of its own registered ids. It
declares only what does not exist yet, which is the selection-dependent handful.

**`perform`, not one closure per action.** `Provider` gains `perform(id, args, cx) -> Handled`: it is
the shape a WASM component is forced into (an id + args crosses a boundary, a closure does not), it
keeps `&self` available, and `ProviderCx` (read + emit) enforces §2.3 — a raw `DynHandler` hands a
component `&mut AppState`, which is more power than a provider may have.

**A row's `nav_key` is its one identity.** Not a keyboard concern: the keyboard cursor, the right-click
target, and (later) drag are three readers of the same declaration. The host derives the context path
from the owning component's `kind()`.

**kind vs mount.** Bindings and declared actions belong to the component **type** (`kind()`, the config
namespace `[keys.docker]`); cursor, scroll offset and focus belong to each **placement** (`id()`, the
mount). `Hero::new()` twice = two instances of one type. `WorkspacesContainerProvider::placed(id,
region)` currently makes `id()` the mount id with no `kind()`, so this must land before a second
placement exists.

# The worked example — a Docker containers dock, end to end

Two actions only it can do, three keys (one reusing a built-in with args), right-click firing one of
them. ✦ marks API this phase adds.

## The component

// heca/src/providers/docker.rs — app-side. A WASM plugin is the same shape across the boundary.

pub struct DockerProvider {
    /// This PLACEMENT (`docker`, `docker.right`). Cursor/scroll/focus key off this.
    id: String,
    region: RegionId,
    /// The component's own domain state — not app state.
    service: DockerService,
}

impl Provider for DockerProvider {
    fn id(&self) -> &str { &self.id }          // instance
    fn kind(&self) -> &str { "docker" }        // ✦ TYPE → the config namespace `[keys.docker]`
    fn title(&self) -> &str { "Containers" }
    fn supported_regions(&self) -> RegionSet { RegionSet::sidebars() }
    fn default_region(&self) -> RegionId { self.region }
    fn keyboard_navigable(&self) -> bool { true }

    fn build_contribution(&self, ctx: &ChromeCtx<'_>) -> Contribution {
        Contribution::Container(ContainerContribution { /* … */ build: Box::new(build_body) })
    }
}

fn build_body(ctx: &ChromeCtx<'_>, bx: &mut BuildCx<'_>) -> WidgetModel {
    let mut list = Flex::column().gap(4.0);
    for c in ctx.state().containers::<DockerRow>() {
        list = list.child(
            Row::new()
                .nav_key(&c.id)        // ✦ the row's ONE identity: cursor + right-click target (+ drag later)
                .on_activate(/* click = attach */)
                .child(Label::new(&c.name)),
        );
    }
    // Scrolling is the widget's: nested here, it answers PageUp/Down/Home/End with nothing declared.
    Box::new(ScrollRegion::new().grow(1.0).child(list))

## Its two actions ✦

```rust
impl ProviderActions for DockerProvider {
    /// ONLY what nothing else can do. Everything else it wants is an existing action it binds.
    fn actions(&self) -> Vec<ActionMeta> {
        vec![
            ActionMeta {
                name: "docker.restart_selected".into(),
                label: "Restart Container".into(),
                description: "Restart the selected container.".into(),
                category: ActionCategory::Chrome,
                default_binding: "r".into(),      // the field already exists — unused today
                icon: Some(Glyph::ArrowClockwise),
                policy: ActionPolicy::Global,
                args: vec![],                      // acts on the selection; nothing to pass
                confirm: None,
            },
            ActionMeta {
                name: "docker.stop_selected".into(),
                label: "Stop Container".into(),
                description: "Stop the selected container.".into(),
                category: ActionCategory::Chrome,
                default_binding: "s".into(),
                icon: Some(Glyph::Stop),
                policy: ActionPolicy::Global,
                args: vec![],
                // Destructive → the CENTRAL confirm gate prompts on every surface. Free.
                confirm: Some(ConfirmSpec::destructive("docker_stop", "Stop")),
            },
        ]
    }

    /// One entry point. The selection is the component's own, keyed by THIS mount.
    fn perform(&self, action: &str, _args: &Intent, cx: &mut ProviderCx<'_>) -> Handled {
        let Some(id) = cx.selected() else { return Handled::No };   // nothing selected ⇒ decline
        match action {
            "docker.restart_selected" => { self.service.restart(id); Handled::Yes }
            "docker.stop_selected"    => { self.service.stop(id);    Handled::Yes }
            _ => Handled::No,
        }
    }
}
```

`perform` never touches `AppState`: its own service, or `cx.dispatch("focus_pane", args)` to reach an
app action.

## The one host-side piece

```rust
// on mount, once — the HOST, not the component (a provider never mutates app state)
for meta in provider.actions() {
    let kind = provider.kind().to_string();
    let default_keys = meta.default_binding.clone();
    let id = meta.name.clone();
    handles.keep(register_dynamic(registry, catalog, meta, Some(Rc::new(route_to_owner))));
    keymaps.bind_component_default(&kind, &default_keys, &id);   // ✦ user config wins
}

// and the bridge, written once for every component that will ever exist
fn route_to_owner(state: &mut AppState, intent: &Intent) {
    let Some(mount) = owning_mount(state, &intent.action) else { return };  // focused, else last-focused of that kind
    let store = state.chrome_state.clone();        // Rc alias — no borrow of AppState held
    let mut cx = ProviderCx::new(&mount, store, state.intent_sink());
    if let Some(p) = state.chrome_host.provider(&mount) {
        p.perform(&intent.action, intent, &mut cx);  // &self available; no &mut AppState alive
    }
    cx.drain_into(state);                          // emitted intents applied by the host
}
```

# The gap, precisely

- Nothing turns `ActionMeta.default_binding` into a binding (the keymap is built from config at load,
  before any provider activates).
- Nothing scopes a binding to "while this component has focus".
- Right-click resolves its `(ContextPath, ContextTarget)` by **matching a closed domain enum**:
  `mouse.rs:143` matches `ChromeDragItem::{Pane,Column,Workspace}`, and `ContextTarget` is closed too.
  A plugin row cannot be expressed, so a `container.docker` path could never be produced.
- `resolve_active_context` (`context_menu.rs:308`) reads `InputMode::SidebarNav` + the sidebar cursor —

### 📋 81da3d2d-ffb8-493a-9149-107dfd27bb01 — T351 — FocusScope: a container's subtree takes keyboard events only while focused

Status: 📋 `planned`

# What

Make the wrapper the host already puts around every mounted container the **keyboard gate**: pointer
events always enter; `Event::Key` and `Event::Widget` enter only while that container holds chrome
focus. This is what makes "the keys go to the focused component" implementable at all — without it the
host would have to know where each container sits in the retained tree.

# Current state

`FocusRing` (`heca-grid-ui/src/widgets/focus_ring.rs`, landed F003/P011/T020) wraps every container in
`focus_and_pick` (`heca/src/chrome/mod.rs`) and is bound to that mount's `keyboard_target` signal
(`SharedChromeState::container_keyboard_target`). It only **paints** — it does not gate anything.

`ScrollRegion::keyboard_target` (`heca-grid-ui/src/widgets/scroll_region.rs:476`) gates scroll intents
per region and stays useful for several scroll areas *inside* one container, but it is the wrong place
for the container-level gate (every future widget would need its own copy).

# The shape

The routing contract is in `heca-grid-ui/src/component.rs:682` (`dispatch`): `on_event_capture` first,
then the child walk unless `routes_own_subtree()`, then `on_event`. A gate that returns
`Handled::Yes` would stop the **sibling** walk, so the focused container would never be reached. The
expressible form is to own the walk:

```rust
fn routes_own_subtree(&self) -> bool { true }
fn on_event_capture(&mut self, ev: &Event) -> Handled {
    if matches!(ev, Event::Key { .. } | Event::Widget(..)) && !self.focused.get_untracked() {
        return Handled::No;              // not mine — my siblings still get their turn
    }
    route_event(&mut self.base.children, ev)
}
```

`route_event` is `pub(crate)`, which is another reason the gate belongs in the library beside the
wrapper rather than app-side.

# Steps

1. Add the gate to `FocusRing` (renaming it — `FocusScope`? — is a judgement call: the ring is the
   visible half of the same fact, so one widget with two jobs is honest, but the name should say
   scope). Update the rustdoc, `docs/widgets.md` and the showcase entry.
2. `tests/pointer_delivery.rs` **requires** anything claiming `routes_own_subtree` to still deliver
   every pointer kind (press/move/release/wheel) to its children — add the case, and make it pass for
   both focused and unfocused, because a click on an unfocused dock must still work (and should focus
   it: see the mouse task).
3. Tests: a widget intent reaches the focused scope's child and not an unfocused sibling's; an
   unfocused scope does not consume it (the sibling after it still gets it); pointer events enter
   regardless of focus.

# Acceptance

- One gate, in the library, beside the ring it shares a signal with.
- An unfocused container is inert to keys and fully alive to the mouse.
- Whole workspace green, clippy 0 warnings.

### 📋 3752b13d-8b2f-48a1-98c9-95408f78c0f7 — T352 — Focus is the mode: route the keyboard to the focused component (absorbs the keyboard-scroll task)

Status: 📋 `planned`

# What

Make chrome focus decide where unprefixed keys go. No `InputMode` variant: focus is already the fact,
and a mode beside it would be a second one that can disagree.

**This task absorbs CY8C2** ("ScrollRegion keyboard-scroll actions", canceled 2026-07-30 at the user's
request — they said the same thing). Everything CY8C2 still carried is transferred below, verbatim
where it is still true.

# Current state

`handle_keyboard_input` (`heca/src/app/input.rs:34`): `InputMode::Normal` forwards every unbound key to
the focused pane's backend (`:58-88`) after trying the `global` keymap. Prefix mode
(`handle_prefix_mode`, `:208`) resolves mode triggers, then the `normal` map, then **drops** the key
(`:275` — the `else if !ctx.key_text.is_empty()` arm just exits prefix). `InputMode::SidebarNav` is a
bespoke arm delegating to the `"sidebar"` mode keymap (`handle_sidebar_nav_mode`, `:584`).

# ✅ DECIDED — the order, in every focus state

1. prefix key → prefix mode → mode triggers → global `normal` map → **falls through to the focused
   component's `[keys.<kind>]` layer** (user decision 2026-07-29) → drop
2. global direct bindings (`Alt+Enter`, `Shift+PageUp`, …) — unchanged
3. **if a component holds chrome focus** → its layer → **swallow** if unbound (user decision: a `j`
   leaking into a shell is the worse failure)
4. otherwise → forward to the focused pane's backend, as today

`state.focused_pane` is **not** cleared: chrome focus redirects the keyboard, nothing else, so
`prefix+Enter` still splits the pane you last worked in.

# Steps

1. One branch at the top of the `InputMode::Normal` arm: chrome focus set ⇒ resolve in the component
   layer, else the existing terminal-forward path. Unbound ⇒ consume (do not forward).
2. Prefix fall-through: after the `normal` map misses, try the focused component's layer before
   dropping.
3. Suppress the **double-prefix literal forward** (`prefix_combo_to_literal_input`, `input.rs:224`)
   while a component has focus — nothing there is receiving text, so sending a literal `Ctrl+B` to a
   pane the user is not typing in is a surprise.
4. `Esc` returns focus to the pane (clear `focused_container`); `focus_dock` aimed at the
   already-focused dock toggles focus back off.
5. Status bar: derive the mode word from the focused component's `title()` (`status_mode_parts`,
   `app/render.rs:54`) so unprefixed keys never go somewhere invisible. The focus ring is the other
   half of that guardrail.

# Keyboard scrolling (was CY8C2)

## ✅ SHIPPED — the widget half (`096f06e`), unchanged by anything here

Eight `WidgetIntent` variants: `ScrollPageUp` / `ScrollPageDown` / `ScrollToTop` / `ScrollToBottom`
and the four horizontal ones. `ScrollRegion` acts on them:

- it owns the arithmetic — a page is 0.9 of its viewport, the edges clamp — because it is the only
  thing that knows its viewport and its content;
- it **declines** an axis it cannot scroll (axis off, or content fits), so a nested region or the host
  gets a turn; consuming would make the key silently do nothing;
- handled after the children, so the innermost scrollable region wins, as with the wheel;
- `keyboard_target(Signal<bool>)` gates which instance responds — per instance, position-agnostic,
  unset means yes. Bound to the mount's chrome focus by F003/P011/T020
  (`StateView::container_keyboard_target`).

**The logic lives in the widget, once.** Every `ScrollRegion` anywhere — any container, any nesting
depth, any region, any one added later — behaves identically with no per-usage code. That is the
standing requirement (user, 2026-07-28): *a widget holds its logic like a React component; move it
around the app and it works the same, without reinventing anything.* The host will only ever say
"one page down, this axis"; the widget decides everything else.

## ⚠️ THE ROUTE CHANGED — 2026-07-29, by the user. This supersedes the 2026-07-16/27 keys.

**Superseded:** vertical `prefix+Home/End/PageUp/PageDown`, horizontal `prefix+Shift+` the same four.
That shape existed only because there was no other way to stop the keys reaching the terminal.

**Now:** while a component holds chrome focus nothing is forwarded to a backend, so **plain
`PageUp` / `PageDown` / `Home` / `End` are free** and are the container's scroll keys; the existing
`Shift+` variants stay exactly as they are for the focused *pane*'s scrollback.

### 📋 b5acb77d-0ade-4eeb-979d-f7e922278a4f — T353 — Provider gains kind(), actions() and perform() — a component declares what only it can do

Status: 📋 `planned`

# What

The trait every component that wants actions adheres to. It declares **only** what nothing else can do
(selection-dependent semantics); everything else it wants is an existing action it *binds*.

# ✅ DECIDED — `perform`, not one closure per action (user, 2026-07-29)

```rust
fn kind(&self) -> &str;                      // the TYPE — config namespace `[keys.docker]`
fn actions(&self) -> Vec<ActionMeta>;        // declaration only; empty is a real answer
fn perform(&self, id: &str, args: &Intent, cx: &mut ProviderCx<'_>) -> Handled;
```

Why `perform` over `Vec<(ActionMeta, DynHandler)>`:

- **It is the shape a WASM component is forced into** — an id + args crosses the boundary, a closure
  does not. Native and plugin stay one design.
- `&self` is available (the host is calling *into* the component); a closure outlives `actions()` and
  must hoist every piece of state it needs into `Rc`s at registration.
- `DynHandler` is `Fn(&mut AppState, …)` — **full mutable app state**, which §2.3 forbids a provider.
  `ProviderCx` (read + emit) enforces the contract in the type instead of by discipline.
- "Which instance?" is answered once, by the host, rather than captured per closure.

The closure form stays for the **host's own** dynamic actions (the chrome placement ones), which
legitimately take `&mut AppState`.

# Current state

- `Provider` (`heca/src/providers/mod.rs:35`): id, supported_regions, default_region, default_order,
  title, movable, grow, collapsible, keyboard_navigable, build_contribution, context_menus,
  on_activate. No kind, no actions.
- `register_dynamic` (`heca/src/actions.rs:409`) + `ActionMeta` (`:2063`, carrying an unused
  `default_binding`) + `ActionHandle` + `unregister_dynamic` all exist and are exercised by tests only.
- `ProviderHandles` (`providers/mod.rs:100`) is documented as where the unregister handles join.
- `WorkspacesContainerProvider::placed(id, region)` (`providers/workspaces.rs:69`) makes `id()` the
  **mount** id — there is no `kind()`, so two placements look like two unrelated components.

# Steps

1. `Provider::kind() -> &str`, defaulting to `id()` for the single-placement case; workspaces returns
   `"workspaces"`. Bindings and declared actions key off `kind()`; cursor/scroll/focus key off `id()`.
2. `ProviderActions` (or the same trait) with `actions()` + `perform()`. Default `actions() = vec![]`
   so a container that declares nothing compiles and behaves — that is the one-number-widget case.
3. `ProviderCx<'_>`: the **mount id**, the shared store (an `Rc` alias — no borrow of `AppState`
   held), `selected() -> Option<&str>` (this mount's cursor row), `state()` (the read-only
   `StateView`), `dispatch(name, args)` / `emit(intent)` queued and drained by the host after
   `perform` returns.
4. The host bridge, written **once** for every component that will ever exist:
   ```rust
   fn route_to_owner(state: &mut AppState, intent: &Intent) {
       let Some(mount) = owning_mount(state, &intent.action) else { return };
       let store = state.chrome_state.clone();
       let mut cx = ProviderCx::new(&mount, store, state.intent_sink());
       if let Some(p) = state.chrome_host.provider(&mount) { p.perform(&intent.action, intent, &mut cx); }
       cx.drain_into(state);
   }
   ```
   Borrow note: the provider lives *inside* `state.chrome_host`, so no `&mut AppState` may be alive
   during `perform` — `ProviderCx` holds only clones and a queue.
5. `owning_mount`: the focused mount if it owns the id, else the **last-focused instance of that kind**,
   else the first mounted. Written down once, not decided per call site.
6. Register on mount / retire on unmount: `on_activate` returns the declared metas in
   `ProviderHandles`; the **host** calls `register_dynamic` (a provider never mutates app state) and
   `unregister_dynamic` on unmount.
7. `ActionMeta.default_binding` stops being dead code — consumed by the config task.

# Edge cases

- Re-registering the same id on remount replaces the previous entry (already the documented behaviour).
- Two placements of one kind share declared actions and bindings; `perform` is called on the placement
  `owning_mount` picked, and reads *its* cursor.
- `perform` returning `Handled::No` (nothing selected) is a legitimate silent decline; a later
  `can_perform` could grey out a menu entry — do NOT build it now.

# Acceptance

- A component declares two actions and a five-line `perform`, and gets keys, RPC, palette, context menu
  and the confirm gate from that alone.
- No component can reach `&mut AppState`.
- Whole workspace green, clippy 0 warnings.
