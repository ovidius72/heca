## What exists

There is no `heca/src/components/`. App-level composition lives in `heca/src/chrome/mod.rs` (4960 lines) and inside providers.

The **chrome action button** is the highest-frequency inline composition and the best first subject, because AGENTS already documents it as a two-step recipe every caller repeats by hand (AGENTS § "Chrome buttons → action, tooltip, KeyHint"):

1. `action_tooltip(button, action_name, label, &state.action_shortcuts)` — `heca/src/chrome/mod.rs:521` — composes `"<label>  <shortcut>"` from the action's **name**.
2. `hints.register(InteractionIntent::…)` + `.hint_target(id)` + `.on_click(move || emit(…))` — the same intent registered twice, once for the pick and once for the click.

Call sites doing this by hand include `build_pane_header()` :782 (per configured `PaneAction`, via `pane_action_spec()` :549), `sidebar_toggle_button`, and the overlay's action buttons (`heca/src/chrome/overlay.rs:431`, which already funnels through `action_tooltip`).

## The contract to fix here

- A component takes **plain data plus the app seams it binds** — `Intent` / `ChromeIntentEmitter`, `&mut BuildCx` (drag, hints, signals), an action **name**, a theme. **Never `&AppState`**: it cannot be constructed in a test (it needs a window), so a component that takes it is a component that cannot be tested. Same split that made `route_in_domain`, `cursor_follow` and `resolve_context_for` testable.
- A component **never** spells a shortcut, picks a glyph, or hardcodes a measure. Name the action; the catalog and `ActionShortcuts` answer.
- If a proposed component binds **no** app concept, it is a widget in the wrong crate — send it to `heca-grid-ui` instead.

## Test pattern to establish

Headless, asserting the built tree or the painted scene — not a flag. Follow `heca/src/providers/mod.rs::the_shared_context_carries_nothing_of_one_components_domain` (builds through `ChromeCtx::for_build`, asserts children and what the host registries received) and `heca-grid-ui/tests/phase_a.rs` (paint into a `Scene`, assert `DrawCommand`s). For the action button, assert: the tooltip carries the action's live shortcut, a hint target was registered, and click + pick carry the **same** intent.

## Behaviors to preserve

Identical pixels; identical hint ids (monotonic, ranges still removed on rebuild); identical tooltip text; the existing `pane_action_spec` mapping of `PaneAction` → (glyph, action, label, focus-first) stays the single source of what a header button is.

### 📋 bbd49c69-6b48-41cd-9bb9-4b95ef1cd53d — T374 — The chrome action button becomes a component — one call, not a two-step recipe

Status: 📋 `planned`

The first extraction, chosen because it is the composition the app repeats most and the one AGENTS already has to explain step by step.

## What exists

AGENTS § "Chrome buttons → action, tooltip, KeyHint" documents a **two-step recipe every caller performs by hand**:

1. `action_tooltip(button, action_name, label, &state.action_shortcuts)` — `heca/src/chrome/mod.rs:521` — composes `"<label>  <shortcut>"` from the action's **name** (never a hand-picked key string), resolving through `ActionShortcuts` so a rebind updates every tip.
2. `let hint_id = hints.register(InteractionIntent::…)` then `.hint_target(hint_id)` **and** `.on_click(move || emit(same intent))` — the same intent registered twice, once for the `prefix+/` pick and once for the click, so they can never diverge.

Call sites doing this by hand: `build_pane_header()` :782 (per configured `PaneAction`, whose glyph/action/label/focus-first come from `pane_action_spec()` :549), `sidebar_toggle_button` (the AGENTS-cited complete example), and the overlay's dialog buttons (`heca/src/chrome/overlay.rs:431`).

Note `pane_action_spec` also returns **`needs_focus`**: an active-targeted button (zoom/float — the `WmAction` carries no pane id) must emit `FocusPaneThenAction`, while pane-parameterized ones use `ActivateAction`. The component has to carry that distinction, not flatten it.

## What to build

An action-button component taking: the action **name**, the `Intent`/`InteractionIntent` it fires, a label, an optional explicit glyph (default: `ActionCatalog::icon(name)`), a `WidgetSize`, and the seams (`&ActionShortcuts`, `&mut BuildCx` for the hint id, the emitter). It returns the tooltip-wrapped, hint-registered, click-wired button as one value.

Then **delete the hand-wiring at every call site above in this same task** — an extraction that leaves the recipe behind has achieved nothing.

## Test (headless, asserts the visible thing)

- The tooltip text carries the action's **live** shortcut from `ActionShortcuts`, and is the label alone when unbound.
- A hint target was registered, and the intent behind the hint id is **identical** to the one `on_click` emits.
- With `needs_focus`, the emitted intent is the focus-then-act composite, not the bare action.
- The glyph comes from the catalog when none is passed.

## Behaviors to preserve

Pixel-identical buttons; hint ids stay monotonic and their ranges are still removed when a tree rebuilds (`HintTargetRegistry::remove_range`, see `render.rs` for the chrome tree and `sync_pane_headers` for the per-pane header trees); `pane_action_spec` remains the single source of what a header button is; the config's `[pane] title_actions` (and any future plugin-added button) keeps flowing through the same dynamic vector — never a per-action `match` in the build loop.
