Write the widget-vs-component boundary into AGENTS and docs, and make "an app file composing widgets inline" something a check can see rather than something a reviewer must notice.

An extraction that is not defended gets undone by the next feature written in a hurry. This phase is what keeps `components/` from becoming another folder nobody remembers.

## What to write down

- **The boundary**, in AGENTS' ⛔ block beside the existing pre-flight: a **widget** is primitive, generic and self-contained and lives in `heca-grid-ui` — *if it can be built there, it belongs there* (a UI library ships `CommandPalette`, `ContextMenu`, `Select`, `Dialog`). A **component** composes widgets **and binds app concepts** (`Intent`, an action name, a drag id, a hint id, a chrome signal, a nav key) and lives in `heca/src/components/`. A composition binding none of those is a widget in the wrong crate.
- **In `docs/chrome-and-ui.md`**: the component catalog — what exists, what each takes, what it must never take (`&AppState`).
- The existing "Chrome buttons → action, tooltip, KeyHint" recipe in AGENTS becomes "use the component", with the recipe kept only as the explanation of what it does internally.

## What to make mechanical

`heca-grid-ui/tests/prop_drift.rs` is the precedent: a test that fails when a widget grows a builder without a generated property surface, with an **explicit exception list** naming each escape and why. The same shape here — an allowlist of app files permitted to compose widgets inline (`components/` itself, plus whatever genuinely cannot move yet), each with a reason, so a new inline composition is a deliberate edit to that list rather than the silent default.

Scope it to what a test can actually see (e.g. `Flex::`/`Item::new`/`Row::new` occurrences per file outside the allowlist). A blunt check that is honest beats a clever one that rots.

## Behaviors to preserve

The guard must not fight the plugin path: `realize()` builds widget trees from `ViewNode` for anyone, and a provider describing its own body is not an inline composition to be flagged.

## The precedent to copy

`heca-grid-ui/tests/prop_drift.rs` — `every_builder_bearing_widget_has_a_generated_property_surface` plus `every_exception_still_names_a_real_type`: a scan with an **explicit exception list**, each entry carrying a reason, and a second test proving the exceptions still refer to something real (so the list cannot rot into lies).

## What to build

The same shape for app-level composition: scan `heca/src/**` for widget-construction sites (`Flex::`, `Item::new`, `Row::new`, `Label::new`, `Icon::new` …) and fail on any file outside the allowlist. The allowlist starts as `heca/src/components/**` plus every file that genuinely cannot move yet — each with a written reason and, where it applies, the planner id of the task that will move it.

Keep the check blunt and honest rather than clever: a per-file count of construction sites is something a reviewer can verify by eye. A precise AST-level rule that nobody trusts is worse than a crude one that fails loudly.

## Edge cases — do not let the guard fight the architecture

- `realize()` (heca-view-realize) builds widget trees from `ViewNode` for anyone: a provider **describing** its own body is not inline composition and must not be flagged.
- Test modules construct widgets constantly — scan non-test code, or exclude `#[cfg(test)]` blocks.
- `heca-grid-ui` itself is out of scope: composing widgets is what the library is for.
