Dynamic action registry: string action IDs + runtime registration, ACCANTO all'enum WmAction (compatibilità piena). Una sola porta d'ingresso (dispatch per nome), un solo registry runtime (il const ALL viene ritirato), policy DICHIARATA per le azioni name-keyed, keybinding config verso ID dinamici. Sblocca context-menu-5, plugin-05 (app.actions.dispatch) e plugin-08 (WASM).

## PERCHÉ QUESTA FASE
`WmAction` è un enum CHIUSO: un plugin/provider non può creare un'azione. Finché resta così:
- un menu-item di plugin non ha niente da dispatchare (→ context-menu-5 BLOCCATO, verificato 2026-07-14: `DropdownItem.action` è un `WmAction`, heca/src/chrome/overlay.rs:220);
- `app.actions.dispatch(id, args)` (plugin-05) non ha un registry a cui parlare;
- il bridge WASM (plugin-08) non ha ID stabili da marshallare.

## ✅ DECISIONI GIÀ LOCKED (NON ri-derivare, NON ri-discutere)
**D1 — Una sola porta d'ingresso, due back end** (plan riga 483). Il dispatch per NOME risolve: built-in via `action_from_name` → `WmAction` → registry enum esistente (invariato, policy-routed); altrimenti azione name-keyed. NESSUN percorso di dispatch parallelo. NON è stata decisa nessuna migrazione totale a stringhe: l'enum resta, con compatibilità piena.

**D2 — UN SOLO registry runtime** (action-interaction-plan §5.1, decision 2a). Si unifica l'attuale split (`handlers: HashMap<Discriminant, fn>` + `static ALL` descriptor):
```
ActionEntry { meta: ActionMeta, dispatch: Dispatch }
Dispatch = Native(ActionHandler)  // fn(&mut AppState, &WmAction) — built-in, per discriminante
         | Declarative            // nessun handler host: inoltrata al proprietario (WASM, plugin-08)
```
- **Keying**: i built-in mantengono la chiave `Discriminant<WmAction>` (le varianti parametrizzate condividono il discriminante) + un indice **name → entry**. Le azioni di plugin non hanno variante → chiave per **NOME**, dispatch via `dispatch_view_intent`.
- **Popolamento**: i built-in si registrano **allo startup** — i dati escono da `const ALL` e finiscono in `register_builtins()` (stessi valori, ora runtime). ⇒ `ActionMeta.name` è una `String` OWNED: **il `const ALL` viene RITIRATO, quindi NON serve nessun `Cow<'static,str>`** (idea scartata il 2026-07-14 proprio perché il const array sparisce).
- **Back-compat**: `ActionRegistry::icon/label/find/by_category/count` continuano a funzionare (ora leggono la mappa runtime). Il catalogo metadata oggi `#[expect(dead_code)]` diventa VIVO (command palette + introspezione RPC).

**D3 — Confirm gate uniforme** (action-interaction-plan §4/§5.2/§5.6). `ActionMeta.confirm: Option<ConfirmSpec>`; `maybe_confirm` data-driven nel ramo `Allow(ActivateAction)` di `dispatch_intent`; `registry.confirm_spec(action)` per discriminante/nome. Un plugin dichiara il `ConfirmSpec` come DATI puri; i suoi `Outcome` sono limitati a `Proceed / Cancel / Dispatch`. **`Outcome::Callback` è NATIVE-ONLY per costruzione** (una closure non è serde: non attraversa WASM/RPC) e il builder plugin-facing non lo espone.
⚠️ SOVRAPPOSIZIONE: il registry runtime di §5.1 è lavoro CONDIVISO con la fase `action-interaction` (che ha ancora 1 task planned). Coordinare: chi arriva primo costruisce `ActionEntry`/`ActionMeta`, l'altro ci si innesta. NON costruire due registry.

## ✅ DECISIONI PRESE NEL GRILL 2026-07-14 (mancavano in TUTTI i doc)
**G1 — ActionPolicy per le azioni name-keyed: CAMPO OBBLIGATORIO, nessun fallback.**
Oggi `action_policy()` (heca/src/app/interaction.rs) è un match ESAUSTIVO su `WmAction`: dimenticare di classificare una variante è un ERRORE DI COMPILAZIONE (garanzia citata in AGENTS.md). Un'azione name-keyed non ha variante → niente la costringerebbe a essere classificata.
DECISIONE: `policy: ActionPolicy` è un campo NON-Option su `ActionMeta` → `register` non è chiamabile senza. Il router legge la policy da UNA sola funzione:
```
fn policy_of(registry, action_ref) -> ActionPolicy {
    match action_ref {
        Builtin(a)  => action_policy(a),                    // match esaustivo ✓
        Dynamic(id) => registry.meta(id).policy,            // dichiarata ✓
    }
}
```
**NIENTE default permissivo.** L'utente ha chiesto "un fallback ActionPolicy::All?" → NO: un default significherebbe che "l'autore ha dimenticato di classificare" si risolve silenziosamente nella policy PIÙ PERMISSIVA del sistema — l'esatto contrario della garanzia attuale. Un'azione che riordina colonne partirebbe mentre una pane floating possiede il dominio, e nessuno lo vedrebbe.
NB: l'azione che "deve sempre funzionare" ESISTE già: `ActionPolicy::Global` (es. `ReloadConfig`). Si DICHIARA. ⚠️ Trappola documentata in AGENTS.md: `AlwaysAllowed` è un nome ingannevole — il router lo BLOCCA quando c'è una floating; `Global` è l'unico davvero sempre permesso.

**G2 — Fiducia: il plugin dichiara, l'host onora** (incluso `Global`). Oggi i "plugin" sono provider FIRST-PARTY compilati dentro heca: sono già pienamente fidati (potrebbero chiamare qualunque cosa) → un confine di fiducia qui sarebbe teatro. Il confine diventa reale con WASM (plugin-08) e va progettato LÌ, dove esiste una sandbox.

**G3 — Keymap: `ActionRef`, built-in risolti al load, sconosciuti differiti al press.**
Vincolo che decide tutto: **la config viene caricata PRIMA che i provider/plugin registrino le loro azioni** → un binding verso `plugin.docker.restart` NON è risolvibile al load. Un nome sconosciuto NON deve diventare un errore di config.
```
enum ActionRef { Builtin(WmAction),   // risolto al load (comportamento ODIERNO: stessi errori, stesso build_action per gli args, costo zero al press)
                 Dynamic(Intent) }    // { id, args } — risolto al PRESS
KeymapRegistry: HashMap<mode, HashMap<KeyCombo, ActionRef>>
```
Sconosciuto anche al press = il warning debug già esistente, non un crash.

**G4 — Terzo variant di Dispatch: `NativeDyn`** (scelto 2026-07-14; supportato da BACKLOG plugin-task-11 che chiede letteralmente `register(id, metadata, handler)`).
```
Dispatch = Native(ActionHandler)                    // fn(&mut AppState, &WmAction) — built-in, per discriminante
         | NativeDyn(Rc<dyn Fn(&mut AppState, &Intent)>)  // per NOME, senza variante WmAction  ← NUOVO
         | Declarative                              // nessun handler host: inoltrata al proprietario (WASM, plugin-08)
```
Serve perché un provider first-party deve poter contribuire un'azione PROPRIA già in plugin-04, prima che esista qualunque WASM. `&mut AppState` è onesto: §2.3 vieta a un provider di mutare lo stato dal path di BUILD/observe — un action handler È il path di scrittura sanzionato.

**G5 — Unregistration: RAII, come le subscription.** Già scritto nel codice: `ProviderHandles` (heca/src/providers/mod.rs) tiene i `ChromeSubscription` e desottoscrive al drop, e il suo commento dice già "(Dynamic-action unregister handles join here in **plugin-04**.)" → `register` restituisce un handle, il provider lo `keep`, l'unmount lo droppa, l'azione si deregistra.
