# 8f760a9b-3ce8-4932-8286-67d742397f2e — P068 — context-menu: Contextual menu → OverlayHost + plugin-declarable

**Status:** ✅ `done`
**Created:** 2026-07-09T09:24:46.628Z
**Updated:** 2026-07-27T11:40:15.511Z

Context menus as a host-owned, context-resolved overlay. Foundation: ContextPath (dotted) + ContextMenuRegistry (built-in providers + plugin Contribution::ContextMenu) + resolve_active_context (keyboard implicit) + unified open_context_menu_for + overlay_origin_mode (mode-restore after close). Keyboard prefix+> works everywhere via prefix arm in SidebarNav; after close the user returns to the origin mode (e.g. stays in sidebar). Mouse right-click refactored to the same unified path (parity preserved, Open-link via target hyperlink). Plugin menus attach by context_path and appear when that context is active/clicked.

Context menus become a host-owned, context-resolved overlay (not hardcoded pane-vs-sidebar branches in the handler). The keyboard-open (`OpenContextMenu` / `prefix+>`) and the mouse right-click both resolve to a `(ContextPath, target)` pair and go through one unified `open_context_menu_for` that looks up registered providers (built-in + plugin `Contribution::ContextMenu`) merged by weight.

Architecture (locked 2026-07-09):
- **ContextPath**: dotted string (`pane`, `sidebar.pane`, `sidebar.column`, `sidebar.workspace`, `floating_pane`, future plugin paths). Target is opaque data (pane_id / ws_idx / …) passed to the provider's `build(ctx, target)`.
- **ContextMenuRegistry**: built-in providers for the 4 paths (migrated from `mouse::open_context_menu` / `open_sidebar_context_menu` item-build) + plugin `Contribution::ContextMenu { context_path, weight: Vec<i64>, build }` (context-menu-5, C1/C2/C3). Lookup collects all matching providers, merges by weight (Dewey), opens one dropdown.
- **resolve_active_context(state)**: keyboard implicit resolver — `InputMode::SidebarNav`+current item → `sidebar.<kind>`; `Normal`+focused pane → `pane`; future modes plug in.
- **pending_context**: `Option<(ContextPath, Target, Option<InputMode>)>` — captured in the sidebar prefix arm BEFORE transitioning to Prefix (because `handle_prefix_mode` sets Normal before dispatch, input.rs:277). `handle_open_context_menu` reads `pending_context.take()` as an override of `resolve_active_context`.
- **open_context_menu_for(state, path, target, anchor, source, origin)**: unified open. Mouse passes `origin=None` (capture current if restorable); keyboard-from-mode passes the explicit origin.
- **overlay_origin_mode: Option<InputMode>**: restorable mode. On open: capture current if restorable (SidebarNav whitelist) or use explicit origin; don't overwrite if already set (stack). On `resolve()` close (chrome/overlay.rs:362): if no overlay remains AND origin set → `input_mode = origin.take()`. Satisfies: open menu from sidebar → close → stay in sidebar. Modal owns keys while open (events.rs:125), so mode is frozen during.
- **Prefix arm**: `handle_sidebar_nav_mode` gets `else if ctx.is_prefix` (mirrors `handle_selection_mode`, app/input.rs:738) → `InputMode::Prefix` + arm timeout + capture pending_context. So `prefix+>` resolves via `handle_prefix_mode` → `keymap.resolve("normal", prefix+>)` → `OpenContextMenu`.

Mouse consequences: refactored to produce `(path, target)` and call `open_context_menu_for`; parity preserved for built-in menus; "Open link" (mouse-only) preserved via `PaneTarget { pane_id, hyperlink: Option<String> }` (keyboard target has `None` → no link entry). Plugin menus appear on right-click once registered (new capability, no regression for built-in).

Plugin contract: declares `context_path` + `weight` + `build(target)`; does NOT pass mode/origin (host-internal). Host includes the plugin menu when the context is active (keyboard) or clicked (mouse).

Code refs: overlay.rs (open_dropdown:253, resolve:360, DropdownSpec:233, DropdownItem), mouse.rs (open_context_menu:115, open_sidebar_context_menu:166, right-click dispatch:441/452), handlers.rs:190 handle_open_context_menu, app/input.rs (handle_sidebar_nav_mode:601, handle_selection_mode:694, handle_prefix_mode:234), app/events.rs:125 (modal owns keys), interaction.rs:265 (OpenContextMenu policy FocusedPaneLocal), actions.rs:299 descriptor.

Edge case (noted): if the menu deletes the selected item (e.g. "delete workspace"), the sidebar cursor points to a gone item; the tree rebuilds each frame so the cursor is clamped/reset — no crash, at worst no visible selection.

  - Rationale: Plugin-friendly (stringa in config/Contribution), type-safe lato host.
  - Implementation: ContextPath: String; target: enum/opaque struct passato al provider build(ctx, target).

## COSA È STATO FATTO
Un provider può contribuire voci a qualunque context menu, e quelle voci possono dispatchare le AZIONI PROPRIE del provider. Il blocco era un enum chiuso: `DropdownItem.action` era un `WmAction`, quindi una voce di plugin poteva solo eseguire azioni già esistenti in heca. plugin-04 ha reso le azioni name-keyed ⇒ la voce ora porta un `Intent` (nome azione + args).

- **`DropdownItem { id, label, intent, danger, enabled }`** (heca/src/chrome/overlay.rs): `id` = identità VISIVA (risolve l'icona), `intent` = ciò che ESEGUE — separati DI PROPOSITO: la voce sidebar "Delete pane" mostra l'icona `close` ma esegue `close_pane_by_id` sul pane di quella riga. Costruttori `new(id,label)` (id≡azione) e `with_intent(id,label,intent)` (identità≠comportamento). Il dispatch della voce scelta passa da `dispatch_intent(InteractionIntent::View)` — la porta unica — quindi policy e confirm gate valgono come per un tasto.
- **`Provider::context_menus(ctx) -> Vec<ContextMenuContribution>`** (heca/src/providers/mod.rs): il provider dichiara *dove* (`context_path`) e *cosa* (`build`), mai *quando*. L'host apre il menu (right-click / `prefix+>`), risolve il contesto e fonde per weight Dewey ⇒ le voci di plugin si incastrano TRA i built-in (`[1,1,1]` tra `[1,1]` e `[1,2]`), non appese in fondo.
- **`MenuBuild = Rc<dyn Fn(&ChromeCtx, &ContextTarget) -> Vec<DropdownItem>>`** (heca/src/chrome/context_menu.rs): UNA firma per built-in e plugin. I builder leggono l'app via il facade `ChromeCtx` (mai `&AppState`) ⇒ una lacuna del facade la incontrano PRIMA i menu built-in, allo scoperto. `ContextTarget` porta ciò che solo l'host risolve (colonna del pane sidebar, custom_name del workspace), così il builder non tocca mai la session.
- `open_context_menu_for` costruisce un `ChromeCtx::new(App::new(&state.chrome_state))` e chiama `items_for(ctx, path, target, plugin)`; `plugin_providers_for` raccoglie le voci dai provider MONTATI al momento dell'apertura.
- `build_action` guadagna `add_column_to_workspace` e `open_link` (i 2 nomi che i menu built-in servivano a esprimere come intent).

## DUE DEVIAZIONI DALLA TASK (il codice contraddiceva il piano)
1. **NIENTE `Contribution::ContextMenu` variant.** `Provider::build_contribution` restituisce UNA sola `Contribution` — il body montato che il render path proietta ogni frame — e un provider vuole SIA un container SIA voci di menu sulle sue righe. Un variant lo costringerebbe a scegliere. ⇒ i menu sono un hook a sé (`context_menus`). `ContextMenuContribution` è un tipo a sé, non una variante di `Contribution`.
2. **NIENTE installazione "on activation".** `MountedContribution::activate()` è definito ma NON è mai chiamato da nessuna parte — l'attivazione dei provider non è mai stata cablata (residuo plugin-03). Invece di simulare un lifecycle che non gira, le voci si raccolgono dai provider MONTATI all'apertura del menu: sempre fresche, niente da deregistrare, e le voci di un provider smontato non restano appese. `ContextMenuRegistry::items_for` prende un `Vec<ContextMenuProvider>` `plugin` e li rifonde per weight con i built-in.
