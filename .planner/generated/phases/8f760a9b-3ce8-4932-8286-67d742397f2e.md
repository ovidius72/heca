### 📋 3724e701-8519-4dfc-bed2-7aa978b96979 — T005 — context-menu-5: plugin Contribution::ContextMenu (full design now)

Status: 📋 `planned`

New Contribution::ContextMenu variant so a plugin/native provider registers entries for a named context; host merges built-in + contributed entries. DESIGN (locked 2026-07-09): (C1) Context = dotted path, fine-grained: "pane", "sidebar.workspace", "sidebar.column", "sidebar.pane", "sidebar.floating_pane". Host resolves context string from click/open target; registry HashMap<context, Vec<Contributor>>. Plugins can invent new contexts. (C2) Merge = weight Vec<i64> per MenuEntrySpec, Dewey/fractional indexing: entries sort lexicographically by weight vector; a plugin inserts between [10] and [20] via [15] or between [10,1] and [20] via [10,1,1]. Tie-break: equal vectors → registration order (built-in first, then plugins). Separators: MenuEntrySpec::Separator with own weight. (C3) Full design now: native Contribution::ContextMenu { context, build: Fn(&ChromeCtx)->Vec<MenuEntrySpec> } now; WASM later (plugin-08) just deserializes Vec<MenuEntrySpec> — same shape, no API change, since MenuEntrySpec is already serializable data (Option B, no closures).
