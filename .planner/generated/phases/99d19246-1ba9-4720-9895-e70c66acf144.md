# Typed, SwiftUI-style builder SDK over `ViewNode`

An ergonomic authoring layer over the uniform node. Lives in **`heca-view`**, so a plugin can depend
on it — that crate has no dependencies but serde, which is the whole reason it exists.

## ⚠️ The original one-line description was written before the vocabulary was corrected

It said `Column::new().gap(8).child(...)`. **`Column` is not a kind any more.** F003/P017/T006
renamed `WidgetKind::Column` → `VStack` and `Row` → `HStack`, and gave **`Row`** to grid-ui's real
clickable, selectable widget. Builders must follow the corrected vocabulary or this SDK would
reintroduce exactly the confusion that rename removed.

## ✅ DECIDED BY THE USER 2026-07-27

**1. A type per widget kind.** One builder struct per `WidgetKind`, so a method exists only where
the widget really has that property — `Label::new("x").title("y")` is a **compile error**, not a
silently-ignored prop. The shared `Layout`/`Visual` properties come from **one trait implemented for
every builder**, written once, because after F003/P017/T007 those apply to every kind generically.
Rejected: a single generic `node(Kind)` builder — less code, but a nonsense method still compiles.

Target shape:

```rust
use heca_view::build::*;

let tree = VStack::new()
    .gap(8)
    .child(
        Panel::new().title("CONTAINERS").child(
            Row::new()
                .padding(6)
                .on_press(Intent::new("docker.select").arg("id", "web"))
                .child(Label::new("nginx"))
                .child(Badge::new("UP")),
        ),
    )
    .child(Separator::new())
    .child(Input::new().placeholder("filter…").name("q"))
    .into_node();
```

**2. Hand-written, with a drift guard — not generated.** A test in **`heca-view-realize`** (the one
crate depending on both `heca-view` and `heca-grid-ui`) walks `WidgetKind::ALL` against each widget's
`PROP_NAMES` and fails when a builder is missing a property the widget exposes. Fails **closed**, like
`heca-grid-ui/tests/prop_drift.rs`: a new property must reach the SDK unless someone names an
exception and says why. `heca-view` keeps zero dependencies — the guard lives above it.

---

# 📋 INVENTORY — taken 2026-07-27 from the compiler, not from reading. DO NOT RE-DERIVE.

**The guard needs no source parsing.** `PROP_NAMES` / `HOST_ONLY_BUILDERS` are **trait consts on
`SetProp`** (`heca-grid-ui/src/prop.rs:68`), so `<Row as SetProp>::PROP_NAMES` is readable from any
crate above `heca-grid-ui`. That is how this list was produced (a throwaway test in
`heca-view-realize/tests/`), and it is how the guard should read it — `prop_drift.rs` parses sources
only because it must catch builders that have *no* surface at all.

## The shared half — every field is settable by name through `merge_style_half`

**`Layout` (34):** align, align_self, direction, flex_grow, flex_shrink, gap, gap_spacing,
grid_cell, height, hidden, justify, justify_items, justify_self, margin, margin_bottom,
margin_left, margin_right, margin_top, max_height, max_width, min_height, min_width, pad_spacing_x,
pad_spacing_y, padding, padding_bottom, padding_left, padding_right, padding_top, padding_x,
padding_y, size, size_explicit, width

**`Visual` (6):** border, fill, font_scale, font_size, glow, radius

### Findings the Style trait has to deal with

- **`width`/`height`/`min_*`/`max_*` are `Length`**, whose wire form is: a **number** → px, the
  string **`"auto"`**, or a string like **`"50%"`** (`heca-grid-ui/src/style.rs:141` — custom
  Serialize/Deserialize). So the typed setters are `.width(240)`, `.width_pct(0.5)`,
  `.width_auto()`, and there is no need for a `Length` mirror in the model.
- **`border` and `glow` CANNOT be authored today.** They are structs (`Border{color,width}`,
  `Glow{color,radius,intensity}`) and **`PropValue` has no map/object variant** — only Bool, Int,
  Float, Text, Size, Variant, Align, Color, Glyph, List. So they are exceptions with a real reason,
  not an oversight. (`fill` and `radius` *are* proven authorable — tests at
  `heca-view-realize/src/lib.rs:1301` and `:1370`.) If they should become authorable, that is a
  `PropValue` change and its own task.
- **Do not expose:** `size_explicit` (set by the layout pass, not an author), `direction` (the kind
  already says it — `HStack` with `direction: column` is a contradiction), `grid_cell` (Grid
  placement is authored as `area`/`col`/`row` props read by the Grid arm), `pad_spacing_*` /
  `gap_spacing` (theme `Spacing` tokens, no model mirror — see the open question).

## Events, per kind — only the ones `realize` actually reads

- **press:** Row, Button, IconButton, BadgeButton, Item, RailCell, Choice

compiler cannot catch a wrong event *name* (it is a string in the model), so this mapping wants a
test: build through the SDK, realize, dispatch, assert the intent fires.

# ❓ OPEN SUB-QUESTION — put to the user before writing the builders

**Six enum-valued properties have no mirror in `heca-view`:** `ActiveMarker` (Row, Item),
`ScrollAxes` (Scroll), `Orientation` (Separator), `LabelSide` (Checkbox), `ToastSeverity` (Toast),
`AlertVariant` (Alert) — plus `TextAlign` (Label) and `Glyph` (Button/Toast/Icon).

They travel as **their name in snake_case** (the model's own rule; `PropInput::Text(prop_enum_name(..))`).
So a typed builder either:

- **(a)** takes `&str` for these — no new model types, but `Separator::new().orientation("vertcal")`
  compiles and silently does nothing, which is the class of defect F003/P010/T006 spent a whole
  task removing from actions; or
- **(b)** adds mirror enums to `heca-view` alongside the existing `ViewVariant` / `ViewAlign` /
  `ViewSize` — genuinely typed, at the cost of ~6 small enums and a mapping each in `realize`
  (the mapping may already exist there: check, since props currently arrive as text).

**(b) looks right** and matches why `ViewVariant`/`ViewAlign`/`ViewSize` exist at all, but it widens
the task and the user has NOT been asked yet. Do not pick it alone.

# Keyboard scrolling for any scroll area

# ✅ SHIPPED — the widget half (`096f06e`), unchanged by anything below

Eight `WidgetIntent` variants: `ScrollPageUp` / `ScrollPageDown` / `ScrollToTop` / `ScrollToBottom`
and the four horizontal ones. `ScrollRegion` acts on them:

- it owns the arithmetic — a page is 0.9 of its viewport, the edges clamp — because it is the only
  thing that knows its viewport and its content;
- it **declines** an axis it cannot scroll (axis off, or content fits), so a nested region or the host
  gets a turn; consuming would make the key silently do nothing;
- handled after the children, so the innermost scrollable region wins, as with the wheel;
- `keyboard_target(Signal<bool>)` gates which instance responds — per instance, position-agnostic,
  unset means yes. Bound to the mount's chrome focus by F003/P011/T020
  (`StateView::container_keyboard_target`).

**The logic lives in the widget, once.** Every `ScrollRegion` anywhere behaves identically with no
per-usage code. The host only ever says "one page down, this axis".

# ⚠️ THE ROUTE CHANGED — 2026-07-29, by the user. This supersedes the 2026-07-16/27 keys.

**Superseded:** vertical `prefix+Home/End/PageUp/PageDown`, horizontal `prefix+Shift+` the same four.
That shape existed because there was no other way to stop the keys reaching the terminal.

mode"). While a component holds chrome focus nothing is forwarded to a backend, so **plain
`PageUp` / `PageDown` / `Home` / `End` are free** and are the container's scroll keys; the existing
`Shift+` variants stay exactly as they are for the focused *pane*'s scrollback.

1. **One branch at the top of those existing handlers**: chrome focus set ⇒ dispatch the matching
   `Event::Widget(WidgetIntent::Scroll*)` into the chrome tree — the FocusScope (P085/T351) delivers it
   to the focused container and every other container is inert — else the terminal viewport path,
   unchanged. One binding, one meaning: *scroll whatever has focus*.
2. **The four horizontal actions** still need adding (`ScrollPageLeft/Right`, `ScrollToLeftEdge/RightEdge`

   declaration** → `rpc.rs` → README. Reuse `ResizeAxis` (`heca/src/input.rs:40`) if an axis argument is

3. A **declined** intent stops at the chrome; it does **not** fall through to the pane. The

### ✅ 42fc5b3c-1724-4b51-9a5e-cc4370da653b — T348 — Containers scroll by nesting their own scroll area; fractional heights

Status: ✅ `done`

# The model (from the user, 2026-07-27)

A **scroll area is a container**. It can be nested anywhere — including inside another container, for
whatever widgets that one holds. So scrolling is **composed**, not a property some layer owns:

```
┌─ sidebar (a shell) ─┐
│ ┌─────────────────┐ │
│ │ container 1     │ │  ½ height, nests its own scroll area
│ └─────────────────┘ │
│ ┌─────────────────┐ │
│ │ container 2     │ │  ½ height, nests its own scroll area
│ └─────────────────┘ │
└─────────────────────┘
```

**My earlier framing of this task was wrong** and is corrected here: it said the shell must stop
scrolling and its scroll area must be *moved* into the container. Nothing is misplaced. A shell may
have one, a container inside it may have its own, and nesting already decides which acts — the
innermost that *can* scroll the axis wins, the outer gets it only when the inner declines. The wheel
works that way today and the keyboard intents shipped in `096f06e` follow the same order.

# What is actually missing

**No container nests a scroll area, so they all share the shell's.** `build_region_content`
(`heca/src/chrome/mod.rs:1464`) stacks every contribution into one `Flex::column().gap(8.0)`
(`:1481-1489`) and `build_sidebar_shell` wraps the stack in the shell's single `ScrollRegion`
(`:1541`) — the only one in the app crate. Two docks in a sidebar therefore scroll as one column:
scrolling the first slides the second off the bottom. That is a gap in composition, not a
misplacement.

# ✅ DECIDED BY THE USER 2026-07-27

- **Heights are fractional, never fixed.** A container in a shell takes a percentage / fraction of
