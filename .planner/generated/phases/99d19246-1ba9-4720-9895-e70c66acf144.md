## BUG A — nested overlay: a Select opened INSIDE a Dialog (found 2026-07-15, F003/P011/T005 showcase)
Two symptoms, ONE root cause: a descendant overlay's panel is not composited/routed above the Dialog's own LATER siblings.
- SHOW-THROUGH (paint/z-order): Dialog paints panel children in order [title, body(Select), action-row]; the Select queues its open list via `cx.with_overlay`, but the action buttons paint AFTER it in the same pass → buttons land on top of the panel (looks translucent; it is z-order — the `surface` token is opaque). See heca-grid-ui/src/widgets/dialog.rs paint child-loop + select.rs open-list paint (~line 622).
- HOVER FALL-THROUGH (input/occlusion): dialog.rs `event()` PointerMoved (~line 336) forwards to the WHOLE panel subtree with no overlay-first routing, so the button under the open panel still highlights. Select's own occlusion (select.rs:696, consume-move-within-panel_rect) works only at the TOP level, because the host routes to `overlay_active` widgets first (focus.rs deliver_event overlay scan ~line 138); the Dialog does not replicate that for a nested open overlay.
FIX (as part of the base-Overlay rework, "blocking stays a layer property"):
1. Route a nested descendant overlay through the app LayerRegistry / surface-compositor as its OWN layer, so an open Select composites above ALL sibling/ancestor chrome — not just local paint order. Nested `cx.with_overlay` inside another overlay is insufficient.
2. Overlay containers (Dialog + the future base Overlay) must deliver pointer/key to an `overlay_active` descendant FIRST (mirror focus.rs overlay scan) and stop propagation to occluded siblings when the descendant's panel_rect contains the pointer.

## BUG B — Dialog off-screen when mounted in-flow / inside a scrolled container (found 2026-07-15)
In the app the Dialog is the layer root: taffy centering (root Pct(1.0)² + Justify/Align Center) centers it on the viewport correctly — NO bug there. In the SHOWCASE it is mounted as `.child(dialog)` inside a vertically-scrolled column, so its box is an in-flow slot and taffy centers the panel inside that slot → off-screen when the trigger is scrolled near the bottom.
FAILED FIX ATTEMPT (2026-07-15, reverted): added `Dialog::on_layout` that shifted the panel to `cx.viewport()`-center via `shift_subtree`. It REGRESSED badly: (a) still off-screen, (b) on re-open the scrim/backdrop painted but the panel did not. WHY: the showcase renders its tree with a vertical SCROLL, so a widget's bounds are in scrolled-tree coordinates, NOT screen coordinates; centering on the absolute `cx.viewport()` throws the panel outside the visible content region. `shift_subtree` is destructive and must be re-derived each layout pass — the showcase's re-open/layout cadence left the panel shifted away while the viewport-anchored scrim still painted (→ backdrop-but-no-panel). Lesson: a Dialog cannot self-center on the absolute viewport when it lives inside a scrolled/offset subtree; centering must be relative to the visible region, or the Dialog must be hosted as a real top-level overlay layer.
CORRECT APPROACH (do here, verify INTERACTIVELY in the GPU showcase — do NOT ship unverified widget changes again): make overlays (Dialog included) host through the app LayerRegistry as their own top-level layer above the scrolled content (same mechanism as the app), rather than living as an in-flow child. Then centering on the viewport is correct because the layer is not inside the scroll offset. This unifies with BUG A's fix (nested/all overlays route through the layer stack).
