**Why the ring of copies failed** (4 rounds of GPU verification): a ring is a DISCRETE shell, so the copies read as spokes and arcs, never as light. It also degraded as the radius grew — a fixed tap count spreads thinner, and at `glow_size = large` the copies became a countable lattice. Deriving the tap count from ring circumference fixed the lattice but not the shells. Two rings, 12–46 taps, four tuning constants — still structurally wrong. **Do not reintroduce it.**

═══ WHAT SHIPPED ═══
`Atlas::glyph_blurred(.., sigma)` rasterizes the glyph's coverage mask, pads by 3σ, blurs (three box passes ≈ Gaussian), **renormalizes the peak back to full coverage**, and stores it as its own atlas entry keyed by `(glyph, sigma bucket)`. Emission draws ONE quad per glyph sampling it.
- 24–92 quads/glyph → **1**. Continuous falloff by construction. σ scales with `glow_size` for free.
- `Atlas::clear()` drops the blurred cache too (its UVs would otherwise dangle).
- `PlacedGlyph` carries its `CacheKey` — the layout is cached independently of any glow, so the blurred variant can only be resolved at emission.

═══ THREE BUGS FOUND DURING VERIFICATION ═══
1. **Halo invisible at first (ring era).** Per-tap alpha was `intensity / HALO_TAPS` on the theory that taps "sum back". They sit on a ring and barely overlap, so each contributed 1.5% alpha. Wrong reasoning, not a typo.
2. **Halo vanished entirely on switching to the blur.** Blurring conserves energy, NOT peak: spreading a thin stroke over σ≈4px drops its peak to ~¼, so the halo came out at ~0.03 alpha. FIX: renormalize the blurred mask to full peak — which also makes `intensity` mean *peak alpha*, the same quantity a rect's glow peaks at, so the two are comparable instead of eyeballed. Locked by `a_blurred_mask_is_renormalized_back_to_full_peak`.
3. **Light theme absent.** `grid.wgsl` switches rect glow to a translucent tinted halo on light backgrounds (`glow_alpha_scale`) because ADDING light to a near-white surface does nothing. `enqueue_scene` already computed it; the text path ignored it. The glyph path now mirrors the rect's own curve (`sqrt(base) * glow_alpha_scale`) rather than a linear scale.
Plus a doc bug: `with_content_glow` claimed the published glow was pre-scaled. It is not — `rest_glow()` returns unscaled and the chokepoint scales once; the doc would have led to double-scaling.

═══ CALIBRATION — the load-bearing insight ═══
Matching a lit surface means matching **emitted light**, not peak alpha. Perceived glow scales with the emitting PERIMETER: a glyph's is ~¼ of a button's, so identical peak + identical radius still looks dimmer and tighter (user: "do you see the icon button glow the same as the Top/Bottom/Left/Right buttons?" — no). Final values sit deliberately ABOVE parity, and each constant's rustdoc says so, so they are not "corrected" back later:
- `HALO_RADIUS_FRAC = 0.55` of glyph size (34px glyph → 18.7px reach; Button's rest glow is 12.0). Derived from glyph size, not fixed — a 20px toolbar icon must not get the same absolute halo as a 34px one.
- `HALO_DARK_GAIN = 1.6` (peak 0.189), `HALO_LIGHT_GAIN = 1.6` (peak 0.341). Moved together so the themes cannot drift.
