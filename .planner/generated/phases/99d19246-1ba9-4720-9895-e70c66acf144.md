## BUG A — nested overlay: a Select opened INSIDE a Dialog (found 2026-07-15, F003/P011/T005 showcase) — OPEN, owned by step 4
Two symptoms, ONE root cause: a descendant overlay's panel is not composited/routed above the Dialog's own LATER siblings.
- SHOW-THROUGH (paint/z-order): Dialog paints panel children in order [title, body(Select), action-row]; the Select queues its open list via `cx.with_overlay`, but the action buttons paint AFTER it in the same pass → buttons land on top of the panel (looks translucent; it is z-order — the `surface` token is opaque). See heca-grid-ui/src/widgets/dialog.rs paint child-loop + select.rs open-list paint (~line 622).
- HOVER FALL-THROUGH (input/occlusion): dialog.rs `event()` PointerMoved (~line 336) forwards to the WHOLE panel subtree with no overlay-first routing, so the button under the open panel still highlights. Select's own occlusion (select.rs:696) works only at the TOP level via the host's focus.rs overlay scan (~line 138); the Dialog does not replicate that for a nested open overlay.
FIX (base-Overlay rework, "blocking stays a layer property"): (1) route a nested descendant overlay through the app LayerRegistry / surface-compositor as its OWN layer; (2) overlay containers deliver pointer/key to an `overlay_active` descendant FIRST and stop propagation to occluded siblings (Component::overlay_occludes is usable here).
