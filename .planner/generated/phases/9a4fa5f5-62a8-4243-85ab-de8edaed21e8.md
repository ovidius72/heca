Extract the palette's private matcher into a reusable search module, rank results by how the user has actually used them, and remember past queries per scope — with the scope key in place from day one for VS Code-style `>` / `@` / `:` modes.

The command palette should find things the way the user has already used it: rank by past choices, and let past queries be recalled. Requested 2026-08-03. The point of the phase is that **none of this is palette-specific** — the matcher, the ranking and the history are one seam that `Select`, `ContextMenu` and the later `>` / `@` / `:` modes reuse.

## Current state — what exists, and what is missing entirely

**The matcher is private to one widget.** `heca-grid-ui/src/widgets/command_palette.rs:145` — `fn fuzzy(query, text, case_sensitive) -> Option<(i32, Vec<usize>)>`, a subsequence match scoring consecutive runs (+5), start-of-word (+8) and tightness. It is a free function in the widget's own file, not `pub`, and it is **the only matcher in the workspace** (`grep -rn fuzzy` finds nothing else). `Select` has no filtering at all; `ContextMenu` has a quick-pick but no search.

**Ranking is the match score alone.** `command_palette.rs:273` — `results()` maps `fuzzy` over `self.commands`, then `out.sort_by_key(|m| Reverse(m.score))`, stable so the caller's order survives ties. Nothing knows what was chosen before. With an empty query every command scores 0 and the list is simply the order the host supplied.

**The host's order is the focused-first rule.** `heca/src/chrome/palette.rs:80` `entries()` builds the rows and `:118` `rows.sort_by_key(|(focused, _)| !*focused)` — the focused component's actions lead, everything else keeps catalog order. Settled in P085; frecency composes with it rather than replacing it.

**A `Command` has no identity.** `command_palette.rs:30` — `struct Command { label, description, icon, chords, on_run }`. The label is not a key: the host prefixes it with the owning component's title (`"Workspaces › Delete Row"`, `palette.rs:91`), so it changes with mounting. Frecency needs the action name, which the host has (`PaletteEntry.id`, `palette.rs:43`) and throws away when it builds the widget's `Command` (`palette.rs:200`).

**There is no persistence layer in this project — at all.** `heca-config` only ever *reads*: `heca-config/src/loader.rs:238/246/320` resolve `~/.config/heca/{config,keybindings}.toml`, and the only `fs::write` calls outside tests are `heca/src/app/backend_factory.rs:276` and terminal plumbing. Nothing the user does is remembered across a restart. A search history is the first piece of **runtime state** the app has ever needed to keep, so this phase introduces that file, its location, its schema and its failure behaviour — deliberately, once, rather than as a side effect.

## The keys — verified, not assumed

`[keys.widgets]` (keybindings.default.toml:339) is the cross-widget vocabulary; the names map to `WidgetIntent` in `heca/src/app/registry.rs:266-276`, and the table is consulted only while a modal/overlay is focused. `menu_up = ["ArrowUp", "Ctrl+k"]` and `menu_down = ["ArrowDown", "Ctrl+j"]` (:342-343) — so **every key first proposed for history was already list navigation**. Settled instead: **`Ctrl+p` / `Ctrl+n` and `Shift+ArrowUp` / `Shift+ArrowDown`**, both confirmed free:
- `Ctrl+p`/`Ctrl+n` appear only as `prefix+Ctrl+p`/`prefix+Ctrl+n` (`workspace_prev`/`next`, keybindings.default.toml:115-116) — prefix-gated `WmAction` bindings that cannot reach a modal overlay.
- `Shift+ArrowUp/Down` is unbound; only `prefix+Shift+ArrowLeft/Right` exists (:42-43).
- Neither is swallowed by the query field: `Input` returns `Handled::No` for `Char` with ctrl/meta held (`heca-grid-ui/src/widgets/input.rs:317`) and handles only `ArrowLeft`/`ArrowRight`/`Home`/`End` (:322-325), so vertical arrows and `Ctrl+<char>` fall through to the host keymap — which is exactly the path `menu_up`/`menu_down` already take.

## ActionRegistry: no — with one exception

The history keys are **`WidgetIntent`s, not `WmAction`s**. `WidgetIntent` (`heca-grid-ui/src/component.rs:393`) is the widget vocabulary resolved from `[keys.widgets]`; `WmAction`/`ActionRegistry` is the app's action system with `ActionPolicy`, RPC exposure and palette listing. Recalling a previous query is meaningless outside an open search surface, carries no policy, and has nothing to offer RPC — it belongs beside `MenuUp`/`MenuDown`, which is precisely the precedent. The exception is **store management**: a `clear_search_history` verb *is* an app action (it touches persisted state and a user would want it from the palette and from RPC), and if it is built it goes through the full Adding-New-Actions checklist.

## Behaviours to preserve

- Smart-case (`command_palette.rs:275` — case-sensitive only when the query has an uppercase char) and match-highlight indices, which paint the accent-coloured hits.
- Filtering matches the **label only**, never the description (`command_palette.rs:56`) — a deliberate rule.
- The focused component's actions lead (`palette.rs:118`).
- Arity filtering: an action with a required argument is not listed (`palette.rs:138` `offerable`).
- The palette is rebuilt from scratch on every open (`palette.rs:185`), so the store cannot live in the widget.

## Shape of the work

Three parts, in order: a pure library module with no I/O and no clock; the widget and key wiring; the persisted store in the app. The library half must stay testable without a window and without a filesystem, which is what keeps it reusable.

## 1. The matcher, moved out

`heca-grid-ui/src/widgets/command_palette.rs:145` — `fn fuzzy(query, text, case_sensitive) -> Option<(i32, Vec<usize>)>` is private to one widget and is the only matcher in the workspace (`grep -rn fuzzy` finds nothing else; `Select` has no filtering, `ContextMenu` has none). Move it verbatim — +5 consecutive, +8 start-of-word, tightness penalty — with a named return:

```rust

pub fn fuzzy(query: &str, text: &str, case_sensitive: bool) -> Option<Match>;
/// Case-sensitive only when the query carries an uppercase char.
pub fn smart_case(query: &str) -> bool;
```

`smart_case` is an inline expression today (`command_palette.rs:275`); naming it means the second search surface cannot spell the rule differently. Its unit tests (`:923`, `:950`) move with it.

## 2. Frecency, counted in uses — not seconds

```rust
pub struct Frecency { /* id -> Use, a monotonic `seq`, a cap */ }
struct Use { count: u32, last_seq: u64 }
impl Frecency {
    pub fn record(&mut self, id: &str);   // seq += 1; count += 1; last_seq = seq
    pub fn boost(&self, id: &str) -> i32; // 0 for an id never chosen
}
```

**Recency is distance in the use-sequence, never a timestamp.** No clock in a UI library, no clock skew, no timezone, and a test asserts an exact number instead of sleeping.

`boost = COUNT_WEIGHT * log2(1 + count) + RECENCY_WEIGHT / (1 + (seq - last_seq))`, integer arithmetic, **capped at `BOOST_MAX`**. The cap is the design decision: fuzzy scores are small (a word-start hit is +8), so an uncapped frecency term would let an often-chosen entry outrank one the query actually spells better. Frecency decides ties and near-ties; a clearly better textual match still wins. Keep the three constants together with that reasoning beside them — they will be tuned by eye.

Bounded: cap the table (~500 ids), prune the lowest `boost` on overflow.

## 3. History — a ring with a cursor and a draft

```rust
pub struct History { /* entries, cursor, draft, cap */ }
impl History {
    pub fn push(&mut self, query: &str);
    pub fn older(&mut self, current: &str) -> Option<&str>;
    pub fn newer(&mut self) -> Option<&str>;
    pub fn reset(&mut self);
}
```

- `push` ignores an empty query and a consecutive repeat of the newest entry.
- **The draft**: the first `older()` stashes what the user had typed, and walking back down past the newest restores it instead of stranding the field on the last history item. Every shell prompt does this and its absence is felt immediately.
- Walking past the oldest stops — no wrapping. A wrapped history hides from the user that they have looped.
- Cap ~50 per scope, oldest dropped first.

## 5. `SearchModel` — the part a widget embeds

This is what stops the next widget from reimplementing anything:

```rust
pub struct SearchModel { scope: String, store: Rc<RefCell<SearchStore>>, /* … */ }

pub enum SearchAction { SetQuery(String), None }

impl SearchModel {
    /// Rank any list. The closure yields `(id, searchable_text)`, so the module
    /// never names a widget's item type — `Command`, `MenuEntry` and whatever
    /// comes next all pass through the same call.
    pub fn rank<T>(&self, items: &[T], key: impl Fn(&T) -> (Option<&str>, &str)) -> Vec<Ranked>;

    /// **The two intents, handled once.** A widget forwards the intent and applies
    /// what comes back. This is the whole of history navigation; a widget that
    /// matches `MenuHistoryUp` itself has copied logic that lives here.
    pub fn handle(&mut self, intent: WidgetIntent, current_query: &str) -> SearchAction;

    /// A keystroke leaves history behind.
    pub fn query_changed(&mut self);

    /// On a successful run: the query as typed, and the chosen id if it has one.
    pub fn record_run(&mut self, query: &str, id: Option<&str>);
}
```

`rank` taking `(Option<&str>, &str)` is deliberate: **identity is optional and belongs to the caller**. An entry with no id still matches and still sorts, it just carries no boost — so a widget is never forced to grow an id field to become searchable. (The palette *does* have a stable id to give it, and will.)

`Ranked` carries the item index, the total score and the hit indices, so the caller paints its own highlights exactly as the palette does today.

## What this task does NOT decide

**Grouping is the caller's.** The palette's host sorts the focused component's actions ahead of the rest (`heca/src/chrome/palette.rs:118`, P085's rule) — that is app policy about chrome focus and has no business in a search module. `rank` returns one ordered list by score; a caller that wants groups sorts by `(group, rank_position)` itself. Any other search surface will have different groups, or none.

## Edge cases

- An id recorded but never listed again simply never gets its boost applied — no cleanup pass, no dangling reference; the cap prunes it.
- `boost` on an unknown id is 0, so an empty store reproduces today's ordering **exactly** — that must be recoverable.
- Multi-byte queries: the matcher counts chars; `History` stores `String` and must never slice by byte.
- Two widgets sharing one store and one scope share a history — that is intended (the `>` and `@` modes of one palette are separate scopes; two palettes are not).

## Tests (pure — no window, no fs, no widget)

- The matcher's existing tests, moved, still green.
- `record`/`boost`: chosen 5 times outranks chosen once; a recent single use outranks an old single use.
- **The cap is asserted directly**: a much-used entry with a poor textual match does *not* overtake a clearly better match. That is the property the constants exist to guarantee.
- History: dedupe, the stop at the oldest, and the draft returning on the way down.

## 5. Host wiring, and the one ordering rule — **focus decides until the user types**

`heca/src/chrome/palette.rs:185` passes the store handle and the scope; the build loop (`:200`) sets `Command::id(row.id)`.

Today `palette.rs:118` unconditionally sorts the focused component's actions ahead of everything else (P085's rule). That becomes **conditional on the query being empty**, settled 2026-08-03:

- **Empty query** — the user is browsing, and the only context available is what they have focused. Keep the focused component's actions on top, ordered inside that block by frecency, with everything else below in frecency order. A component's actions are otherwise buried among a hundred built-ins, and there are only a handful of them, so the block pushes almost nothing down. This is also where a flat most-used list helps least: the actions run fifty times a day are the ones that already have keybindings.
- **Non-empty query** — the user has said what they want, and the query is better context than whatever happens to hold focus. **Drop the block entirely** and take `rank`'s order as-is (match score + frecency boost). Keeping it here would actively fight the user: an action whose name they spelled correctly must not sit below one they did not, merely because its component has focus.

Expressed as a sort key of `(query.is_empty() && !focused, rank_position)` or equivalent — one place, host-side. **The search module still knows nothing about blocks**: `rank` returns a single ordered list either way, which is what makes this reversible at no cost.

## Edge cases

- A recalled query matching nothing leaves an empty list — `select_next` already guards `n == 0` (`command_palette.rs:294`).

- Deleting back to an empty query brings the block back. That is a visible reshuffle mid-typing; it is the intended behaviour, but it is the first thing to look at if the ordering ever feels unstable.
- Held Shift while walking history must not smear a text selection through the query line — the field only anchors on `ArrowLeft`/`ArrowRight` (`input.rs:322-325`), so verify rather than assume.
- Two spellings of one key drew a keycap chip twice once before; `chord_caps` dedupes by cap, so check the palette's hint rows if these bindings ever surface there.

### 📋 a1906a6c-7eb4-434f-b603-61aed6117696 — T386 — The app remembers it: the first persisted runtime state — versioned, bounded, corrupt-safe

Status: 📋 `planned`

A history that dies with the process is not a history. This task gives the app its **first piece of persisted runtime state**, and defines the shape once so the next feature that needs it does not invent a second one.

## There is no precedent — that is the point

`heca-config` only ever reads: `heca-config/src/loader.rs:238/246` resolve `~/.config/heca/config.toml` and `keybindings.toml`, `:320` uses `dirs::config_dir()`, and `heca-theme/src/loader.rs:10` does the same. The only `fs::write` calls outside tests are `heca/src/app/backend_factory.rs:276` and terminal plumbing. **Nothing the user does survives a restart today.**

So this does not go in `heca-config`: that crate is the user's hand-written configuration, and machine-written state has different rules (it is rewritten without asking, it may be deleted safely, and a corrupt one must never stop the app). New module `heca/src/search_state.rs`, owned by the app that owns `AppState`.

## Location and format

`dirs::data_dir()/heca/search-history.toml` — `data_dir`, not `config_dir`: `~/.local/share/heca` on Linux, `~/Library/Application Support/heca` on macOS. Deleting it must lose nothing but convenience.

TOML, to avoid adding a serialization dependency for one small file (**check `Cargo.toml` first** — if `serde_json` is already in the tree, JSON is the better fit for machine-written data and the argument for TOML disappears). Either way it carries `version = 1` from the first line written: a `@`/`:` scope arriving later must be able to read or discard an older file deliberately rather than by accident.

The snapshot is `SearchStore` whole (see T384) — the per-scope histories, the frecency counts, and the monotonic `seq`, which **must** be persisted or every restart resets recency to "everything is equally old".

## Behaviour

- **Load once at startup**, into `AppState`. A missing file is an empty store; a corrupt or unreadable one is *also* an empty store, logged once at warn — never a startup failure, and never a dialog. The palette must work identically on a first run.
- **Save after a run records something.** The file is a few KB; there is no need for a background writer or a debounce, and saving at exit alone loses everything on a crash or a `kill`.
- **Atomic**: write a sibling temp file, then rename. A half-written history read at next launch is the corrupt case above, but there is no reason to manufacture it.
- **Bounded on write** as well as in memory (~50 queries per scope, ~500 frecency ids) so the file cannot grow unbounded no matter what the in-memory caps do.

## Settings

`[settings] search_history = true` to turn the memory off entirely — a shared or recorded machine is a real reason, and a user who turns it off expects the existing file to stop being written *and* to stop being read. `heca_config::settings::PaletteSize` (used at `heca/src/chrome/palette.rs:190`) is the precedent for adding a setting and threading it into `AppState`.

## `clear_search_history` — a real action, the full checklist

Unlike `menu_history_up/down` (widget intents, T385), clearing the store **is** an app action: it changes persisted state and a user wants it from the palette and from RPC. It therefore goes through the whole Adding-New-Actions checklist in AGENTS.md — `WmAction` variant, name parsing (`heca/src/input.rs:685` is the pattern), registry handler (`heca/src/app/registry.rs:999`), `ActionPolicy`, `ActionMeta` with label/description/icon/args, RPC name (`heca/src/rpc.rs:617`) — and it takes no arguments, so it is offerable in the palette (`heca/src/chrome/palette.rs:138`). Ask before adding a confirm prompt; it is destructive but trivially rebuilt by using the app.

## Edge cases

- Two windows / two processes writing the same file: last writer wins, and the atomic rename keeps the file valid. Do not build locking for this — say plainly in the module doc that it is last-writer-wins, so nobody later assumes merging.
- A file from a future `version` is discarded, not parsed leniently.
- `dirs::data_dir()` returning `None` disables persistence for the session — in memory only, no panic.
- The store is written from the UI thread: keep it that way and keep it small, rather than introducing a thread for a few KB.

## Tests

- Round-trip through a temp dir: record, save, load, and the ordering that comes back is identical.
- A corrupt file, a truncated file and a future `version` each yield an empty store and no error out of `load`.
- The caps hold on write: recording 200 queries writes 50.
- `search_history = false` neither reads nor writes.
- No test may touch the real `dirs::data_dir()` — the path is a parameter of the loader, exactly so.
