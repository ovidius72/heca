WHY IT DOES NOT WORK TODAY
`heca-renderer`'s `composite.rs` keeps a PERSISTENT scene texture precisely so a frame can
re-render only the changed region (scissored) and let unchanged pixels survive — cheap idle and
animation frames (a cursor blink, a hover glow) instead of repainting the whole UI 60 times a
second. That is a real battery and heat win, especially for an idle terminal.

IT IS NOT REALISED: `render_frame` clears the whole scene every frame and redraws every pane in
full, so there is nothing preserved to build on.

WHAT WAS REMOVED AND WHY
The chrome-level `ChromeDamageMode` (Full / Tracked / ForceFullOnNextRequest) was the app-side gate
for this. Layered over an unconditional per-frame clear it only ever DROPPED chrome content, which
showed up as a dark "re-render flash" on the split button's press animation. Fixed 2026-06-22 by
making chrome always full-repaint (`render.rs`, `damage: None`) and REMOVING the dead
`ChromeDamageMode` machinery — it was unsound as built. Do not resurrect it as-is.

THE FOUR STEPS TO ACTUALLY LAND IT
1. Stop the unconditional per-frame scene clear.
2. Make PANES damage-aware — only re-render changed pane regions. Chrome alone is not enough.
3. Scissor the clear and each renderer to the union damage rect against the preserved scene.
4. Re-introduce an app-side damage gate, designed against the above rather than layered on top.

Renderer-level `GridRenderer::set_damage` and the compositor's preserved scene already exist to
build on.

RISK: rendering correctness — transparent-pane double-blend, stale pixels. GPU ordering is not
unit-tested, so this MUST be verified by running the app, not by a green suite.

RELATED: the reactive-store work noted that feeding signal changes into the
`needs_paint`/`collect_damage` path is "the deep part of the work". Same problem, same place.
