# Niri Compatibility Review

> Analysis of heca's keybinding system and layout management against niri's design.
> Generated by comparing heca source against `.agents/skills/niri/SKILL.md` knowledge base.

**Note:** The project deliberately uses a **tmux-style prefix architecture** (`Prefix + key`) to avoid conflicts with hosted applications. This is a design choice, not a bug. The review evaluates how well the prefix system is *implemented*, and where it falls short of working correctly.

## Part 1: Keybinding Issues

### Critical

#### K1. Prefix Mode Hardcodes `ctrl=false`, Breaking All Ctrl+Key Bindings

**Severity: Critical — 6+ bindings are unreachable**

heca uses a tmux-style prefix architecture (`Ctrl+B → key`). When the user presses a key in prefix mode, the resolve call hardcodes `ctrl=false`:

```rust
// main.rs prefix handling, approximately line 240:
let action = self.bindings.resolve(&key_text, false, false, is_shift, ...);
```

The comment argues the user is "still holding it from the prefix key (Ctrl+B)". But this is incorrect for tmux-style binding: **the user may intentionally press Ctrl+another key after the prefix**, and the Ctrl modifier should be part of the binding match, not discarded unconditionally.

**Reachable analysis:**

| Binding | Config key | Config string | Reachable? |
|---------|-----------|---------------|------------|
| `swap_left` | `Ctrl+h` | Requires `ctrl=true` | ❌ always |
| `swap_right` | `Ctrl+l` | Requires `ctrl=true` | ❌ always |
| `swap_up` | `Ctrl+k` | Requires `ctrl=true` | ❌ always |
| `swap_down` | `Ctrl+j` | Requires `ctrl=true` | ❌ always |
| `tab_next` | `Ctrl+]` | Requires `ctrl=true` | ❌ always |
| `tab_prev` | `Ctrl+[` | Requires `ctrl=true` | ❌ always |

The Ctrl bindings are impossible to trigger regardless of whether the user holds or releases Ctrl after the prefix.

**Why tmux doesn't have this problem:** tmux uses a different key representation — you bind `C-h` (not `Ctrl+h` as a modifier+key char). When the user presses `Prefix C-h`, tmux sees it as a single chord because the prefix defines a separate keymap. heca's config format stores `Ctrl+h` as a bound string, then the resolve function separately checks `ctrl` boolean AND `key` match — but prefix mode discards the ctrl boolean.

**Fix:** Pass `state.modifiers.control_key()` (from the current modifier state) instead of hardcoding `false`. The prefix detection already handles the prefix key itself — the subsequent key's modifiers should be evaluated normally.

---

#### K2. Prefix Key Is Hardcoded to Ctrl+B (Not Configurable)

**Severity: High — violates tmux-style configurability**

The prefix key detection is hardcoded in `main.rs`:

```rust
let is_prefix = key_text == "\u{2}"                         // macOS control char
    || matches!(log_key, winit::keyboard::Key::Character(c) if c == "\u{2}")
    || (is_ctrl && phys == winit::keyboard::PhysicalKey::Code(winit::keyboard::KeyCode::KeyB));
```

There's no config option to change the prefix key. tmux lets users set `set -g prefix C-a` or any other key. heca should let users set `prefix_key` in the config file.

Additionally, **the prefix is not in the keybinding map** — there's no `prefix` action or binding entry. It's a special case in the event handler. This means:
- The hotkey overlay (when implemented) can't display the prefix key
- The `action_priority` system doesn't apply to it
- It can't be unbound or rebound

**Fix:** Add a `prefix_key` config option. Make the prefix detection read from config, not a hardcoded constant.

---

#### K3. No Prefix Timeout

**Severity: Medium — user can get stuck in prefix mode**

tmux has `set -g escape-time 500` — after pressing prefix, if no key is pressed within the timeout, it exits prefix mode. heca has no such timeout. If the user presses Prefix (`Ctrl+B`) and then changes their mind, they stay in prefix until they press a recognizable key or press Ctrl+B again.

**Problematic edge cases:**
- Dead keys (e.g., `^` on US-International layout, or Compose sequences): `key_text` is empty, so the `!key_text.is_empty()` branch doesn't trigger. User stays in prefix mode with no feedback.
- Lock screen / suspend / focus change: no `KeyboardInput` event fires when returning, prefix mode persists silently.
- Non-modifier named keys like `CapsLock`, `NumLock`, `ScrollLock`: the `is_modifier_only` check catches Shift/Ctrl/Alt/Super/Hyper/Meta but NOT these, so pressing them in prefix mode does nothing and leaves prefix active.

**Fix:** Add a timer that resets `InputMode` to `Normal` after ~500ms of inactivity. Also expand the `is_modifier_only` check to include all named key types that shouldn't trigger binding resolution.

#### K4. Shift+Special-Char Bindings Fail on Many Layouts

**Severity: High — `Shift+=`, `Shift+q`, `Shift+-` may not work**

The binding `pane_height_increase` uses `Shift+=`. The resolve logic infers shift ONLY for ASCII uppercase letters (A-Z):

```rust
let key_implies_shift = key.len() == 1 && {
    let c = key.chars().next().unwrap();
    c.is_ascii_uppercase() && c.is_ascii_alphabetic()
};
```

But `Shift+=` on most keyboard layouts produces `+`, not `=` (which is the unshifted character). On US layout, `=` is unshifted, `+` is Shift+=. On other layouts the characters may differ.

The binding key in config is `Shift+=`. If winit reports `key_text = "+"` (the shifted char) or `key_text = "="` (the unshifted char), behavior differs by platform:
- macOS: often reports the rendered character (`+`), not the unshifted key — shift won't be inferred
- Windows/Linux: more likely to report actual text; behavior depends on IME/compose settings

**Same issue:** `swap_select` binds `Shift+q` — works because Q is ASCII uppercase, but ONLY because `key_implies_shift` checks for A-Z. `Shift+-` for `pane_height_decrease` — `-` is not a letter, so shift won't be inferred.

**Fix:** Instead of inferring shift from the character, use the keyboard's reported key location (physical key) or the `ModifiersChanged` state directly. The binding key string `Shift+=` should be parsed to extract the `shift: true` flag and the key `=`, then matched against the reported modifiers (not inferred from character case).

#### K5. Multiple Actions in `execute_action` Are No-Ops

**Severity: Medium — 6 bound actions silently do nothing**

```rust
WmAction::Scratchpad | WmAction::Hide => {}
WmAction::ResizeLeft | WmAction::ResizeUp | WmAction::ResizeRight | WmAction::ResizeDown => {}
```

Six fully-defined `WmAction` variants match to empty blocks in `execute_action()`:

| Action | Config binding | User experience |
|--------|---------------|----------------|
| `Scratchpad` | `s` | Pressing `Prefix s` does nothing |
| `Hide` | `z` | Pressing `Prefix z` does nothing |
| `ResizeLeft` | (unbound by default) | If bound, does nothing |
| `ResizeRight` | (unbound by default) | If bound, does nothing |
| `ResizeUp` | (unbound by default) | If bound, does nothing |
| `ResizeDown` | (unbound by default) | If bound, does nothing |

Four of these are unbound by default — but `Scratchpad` (`Prefix s`) and `Hide` (`Prefix z`) are **bound in the default config** and produce a silent no-op. The user presses keys, enters prefix mode, sees a binding match in the debug log, but nothing happens on screen. No error, no visual feedback.

This is especially confusing because the status bar briefly flashes "PREFIX" then returns to "NORMAL" — the user sees the system respond to their input, but the expected action (scratchpad toggle, hide pane) never occurs.

#### K6. Modifier State Read from Global Cache Instead of Event

**Severity: Low — rare misread but easy to fix**

The `KeyboardInput` handler reads modifiers from the global cached state:

```rust
let is_ctrl = state.modifiers.control_key();
let is_shift = state.modifiers.shift_key();
```

But winit's `KeyboardInput` event carries its own modifier state via `event.state` (an `ElementState` or `Modifiers` depending on winit version). The cached `state.modifiers` is set by a separate `ModifiersChanged` event, which may arrive before OR after the corresponding `KeyboardInput` event.

**Race scenario:**
1. `KeyboardInput(h, ctrl=true)` fires first
2. `ModifiersChanged(ctrl=true)` fires afterward
3. `state.modifiers.control_key()` returned `false` (stale from before Ctrl was pressed)

This can cause:
- `Ctrl+h` being forwarded to the terminal as just `h` instead of backspace (in Normal mode)
- `Ctrl+h` resolving as just `h` in Prefix mode (when K1 is fixed)

**Fix:** Use the modifier state from the event itself. In winit 0.30+, `KeyboardInput` carries `modifiers: ModifiersState`. Read from there instead of the global cache.

```rust
// Instead of:
let is_ctrl = state.modifiers.control_key();
// Use:
let is_ctrl = event.state.modifiers.control_key();  // winit 0.30+
```

#### K7. Prefix Double-Press Doesn't Forward Literal Ctrl+B to Terminal

**Severity: Low — minor tmux behavior difference**

When the user presses `Prefix` (Ctrl+B) while already in prefix mode, the code toggles back to Normal mode but does NOT forward the Ctrl+B keypress to the terminal:

```rust
InputMode::Prefix => {
    if is_prefix {
        state.input_mode = InputMode::Normal;
        return;  // <-- Ctrl+B is swallowed
    }
```

In tmux, pressing `C-b C-b` sends a literal Ctrl+B character to the attached program (e.g., for `nano` paragraph formatting or `vim` scroll-screen). heca's implementation exits prefix mode instead, making it impossible to send a literal prefix key to the terminal.

**Impact:** If a user runs a terminal application that uses Ctrl+B (e.g., `nano`, `screen`, or a nested tmux session), they cannot send that key through heca.

**Fix:** When the prefix key is pressed in prefix mode, forward the control character (0x02 for Ctrl+B) to the active backend:

```rust
if is_prefix {
    state.input_mode = InputMode::Normal;
    if let Some(pane_id) = state.focused_pane {
        if let Some(backend) = state.backends.get_mut(&pane_id) {
            backend.process_input(&[0x02]);
        }
    }
    return;
}
```

#### K8. `action_priority` Catch-All Arm Is Dead Code

**Severity: Informational — cleanup only**

The `action_priority` function has a `_ => 4` catch-all at the end:

```rust
fn action_priority(action: WmAction) -> u8 {
    match action {
        WmAction::FocusLeft | ... => 0,
        // ... all 32 variants explicitly covered ...
        WmAction::PaneHeightIncrease | WmAction::PaneHeightDecrease => 3,
        // Other
        _ => 4,  // <-- dead code, all variants already matched
    }
}
```

All 32 `WmAction` variants are explicitly matched in the priority function. The `_ => 4` arm will never be reached. Not a bug — but it means adding a new variant won't cause a compile error if the author forgets to assign a priority. The compiler won't flag it because of the catch-all. Removing `_ => 4` would make new variants a compile-time error, forcing the developer to consciously assign a priority.

**Fix:** Remove the `_ => 4` catch-all. The compiler will then enforce that every new `WmAction` variant gets an explicit priority.

## Part 2: Layout Management Compatibility

### Critical Design Divergences

#### L1. Violation of Niri Principle: "Opening a New Window Should Not Affect Existing Window Sizes"

**Severity: Critical — core design divergence**

From the niri skill (Design Principles):

> **1. Opening a new window should not affect the sizes of any existing windows.**
> Scrollable tiling alternative: open temporary windows alongside existing ones without reflow.

heca's `add_column()` calls `update_all_column_widths()` every time. While this currently *happens* to return the same values for Proportion widths (since proportions are stored per-column and re-derived against working_width independently), the architectural pattern is wrong:

- Any future change to `resolve_width()` or `update_all_column_widths()` could introduce reflow
- Column widths are "re-derived" instead of "stored" — if widths were set interactively via resize, they should persist as-is, not be re-computed
- `computed_width` is overwritten in every `update_all_column_widths` call, so any manual adjustment to computed_width is lost

**In niri:** Column widths are a **stored property** on each column. They NEVER change unless the user explicitly resizes or runs `set-column-width`. When a new column appears, it gets the default width and existing columns keep their exact pixel widths — even if the total overflows the viewport (that's the point of scrollable tiling).

---

#### L2. Proportion Widths Are Un-Normalized But Not Stored Persistently

**Severity: High — latent reflow bug**

Multiple Proportion columns each compute their width as `(working_width - gaps) * proportion - gaps`. Two columns at 0.5 each take `working_width + gaps` total space — this is correct niri behavior (they overflow).

However, `update_all_column_widths()` is called from every mutation function. If `working_width` changes (window resize), ALL proportion columns recompute based on the new `working_width`. This means:

1. If you resize a column interactively so it's 60% of the old viewport
2. Then resize the window to be wider
3. The column goes back to 50% (its stored Proportion) instead of staying at 60%

In niri, interactive resize changes the column's stored width. Window resize changes the absolute pixel value of all proportion columns proportionally — but the stored *ratio* changes only if you explicitly resize.

**heca's `resize_active_column`:**
```rust
ColumnWidth::Proportion(p) => ColumnWidth::Proportion((p + delta).clamp(0.05, 0.95))
```

This modifies the stored proportion — correct. But then `update_all_column_widths` re-derives all column widths, which is correct for the resized column but also re-derives every other column, which is unnecessary and could mask bugs.

#### L3. Viewport/Chrome Mismatch Causes Layout Off-by-One

**Severity: High — wrong working area sent to layout engine**

```rust
// In main.rs at initialization:
let pane_area = chrome.content_rect(log_w, log_h);
let viewport_size = heca_core::layout::types::Size::new(
    pane_area.w as f64,
    pane_area.h as f64,
);
// This correctly uses content area → GOOD

let mut session = Session::new(..., viewport_size, scale_factor);
// Creates workspace with working_area = (0,0, pane_area.w, pane_area.h)
```

But then in `workspace_geometries()`:
```rust
vec![(self.active_workspace_idx, Rectangle::new(
    Point::default(),
    self.viewport_size,
))]
```

This returns `viewport_size` (which IS the pane area — OK). But the rendering code in `render_backend_data` receives positions from `panes_with_positions()` and adds `pane_area.x` and `pane_area.y` offsets. So:

```
Layout calculation: coordinates in [0, pane_area.w] × [0, pane_area.h] ✅
Rendering:          pane_area.x + col_x, pane_area.y + pane_y ✅
```

This actually works correctly... BUT the view offset computation uses `self.working_area` which starts at `(0, 0, pane_area.w, pane_area.h)`. The view offset targets are computed relative to this working area. When `pane_area.x != 0` or `pane_area.y != 0` (i.e., sidebars are visible), the view offset logic may compute values that center/fit correctly in the content area but the arithmetic involving `area.loc.x` is:

```rust
fn compute_view_offset_fit(&self, idx: usize) -> f64 {
    // ...
    compute_new_view_offset(
        self.target_view_pos() + area.loc.x,
        area.size.w,
        col_x,
        col_w,
        padding,
    ) - area.loc.x
}
```

The `area.loc.x` is always 0 (since working_area loc is (0,0)), so this is fine. But it means the layout engine has NO awareness of chrome offsets — which is fine as long as the coordinates stay consistent. **This is correct as-is**, but fragile: any change to `working_area` location would silently break.

#### L4. Focus Up/Down Crosses Workspace Boundaries Without Explicit Binding

**Severity: Medium — diverges from niri behavior**

```rust
// In Session:
pub fn focus_up(&mut self) -> bool {
    if let Some(ws) = self.active_workspace_mut() {
        if ws.focus_up() {
            return true;
        }
    }
    self.switch_workspace_up()
}
```

In niri:
- **Pane focus** (`focus-window-up/down`, usually Mod+J/K) operates **within the current column** only. When at the top/bottom of a column, nothing happens (no wrap, no workspace switch).
- **Workspace switch** (`focus-workspace-down/up`, usually Mod+U/I) is a **separate action** with dedicated keybindings.

heca conflates the two: focus_up falls through to workspace switch when at the top of a column. This means:
- You cannot have a single binding that focuses up within a column without also switching workspaces
- There's no way to focus the last pane in the previous column (niri wraps focus within the workspace across columns, not across workspaces)

Same issue applies to `focus_down()` falling through to `switch_workspace_down()`.

---

#### L5. Automatic Animation on All View Changes (No Configurable Types)

**Severity: Medium — missing niri feature**

niri has 11 configurable animation types with per-effect configuration:

| niri Animation | Default | heca Equivalent |
|----------------|---------|-----------------|
| `horizontal-view-movement` | Spring (1.0, 800) | Single `AnimationConfig` default (250ms ease-out-cubic) |
| `window-open` | Easing (150ms) | Not animated |
| `window-close` | Easing (150ms) | Not animated |
| `workspace-switch` | Spring (1.0, 1000) | Single AnimationConfig default |
| `overview-open-close` | Spring (1.0, 800) | Same as all others |
| `window-movement` | Spring (1.0, 800) | Same as all others |
| `window-resize` | Spring (1.0, 800) | Not animated |

heca has:
- **No spring physics** — only easing (ease-out-cubic by default)
- **No per-effect configuration** — all animations share the same `AnimationConfig::default()` (250ms, ease-out-cubic)
- **No way to disable animations** — niri has `animations { off; }` and `animations { slowdown 3.0; }`
- **No LazyClock** — `Instant::now()` is called inline per animation, meaning timestamps differ across animations started in the same frame

**The `Animated<T>` design:** The generic `Animated<T>` abstraction supports `Static` and `Animating` variants, but the `Animating` variant only stores a single `Animation` which is hardcoded to easing. Adding spring support would require either:
- A new `Animated::Spring { ... }` variant
- Or making `Animation` itself support both easing and spring

#### L7. Column Width Caching Is Redundant and Fragile

**Severity: Low — design smell**

`Column` stores both `width: ColumnWidth` (the "type" of width) and `computed_width: f64` (the cached value). `ScrollingSpace` also stores `column_widths: Vec<f64>`. These are supposed to be in sync but:

- `column.computed_width` is set in `resolve_width()` 
- `column_widths[i]` is set in `update_all_column_widths()`
- After `add_pane_to_column`, the function calls `update_all_column_widths()` which updates both caches
- But `column_widths` is also manually managed in `add_column`, `remove_column`, `move_column_to`

If they get out of sync, `column_x()` uses `column_widths` while pane rendering uses `column.computed_width` — producing misaligned panes.

In niri, there's no double-caching problem because column widths are single-valued and stored once per column.

---

#### L8. View Offset Restore After Fullscreen Is Fragile

**Severity: Low — potential visual jump**

```rust
pub struct ScrollingSpace {
    pub view_offset_to_restore: Option<f64>,    // written but never read
    pub activate_prev_on_removal: Option<f64>,  // written but never read
}
```

Two fields that are SET in certain code paths but never CONSUMED. `view_offset_to_restore` is set to `None` in `activate_column()` and `remove_column()`, but the restore logic is never implemented. This means fullscreening a column and unfullscreening will snap the view to the active column position instead of restoring the previous scroll position.

In niri, view position is preserved when entering/exiting fullscreen (design principle: "The focused window should not move around on its own").

### Root Causes

1. **Prefix modifier handling is broken**: The `ctrl=false` hardcode in prefix mode is the single biggest bug. It makes 6 of 34 bindings unreachable. The fix is straightforward: pass the real modifier state.

2. **Prefix key is not configurable**: Unlike tmux where `set -g prefix C-a` works, heca hardcodes Ctrl+B. The prefix should be a config entry like `prefix_key "Ctrl+a"`.

3. **Over-eager width recomputation**: `update_all_column_widths()` is called on every mutation instead of storing and persisting column widths. This violates niri's "no reflow" principle and makes the system fragile.

4. **Feature skeleton without wiring**: Tabbed display, maximize modes, preset widths, and focus ring gradients are all defined in the type system but never reachable from user interaction.

5. **Single animation model**: Spring physics are absent. All animations use 250ms ease-out-cubic regardless of effect type, with no configurability.
